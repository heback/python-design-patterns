퍼사드 (Facade)

복잡한 서브시스템 앞에 단순한 정문을 하나 두기

학습 목표

  1. 여러 서브시스템 앞에 단순한 진입점을 두는 퍼사드를 만들고, 퍼사드가 직접 접근을 막지 않는다는 점을 설명할 수 있다.
  2. 퍼사드가 모든 것을 떠안는 거대한 객체로 변하는 징후를 알아챌 수 있다.
  3. 쓰는 쪽이 의존하는 대상의 수로 퍼사드의 효과를 잴 수 있다.
핵심 한 줄 "이 기능은 저 서비스들을 이 순서로 부르는 것"이라는 지식이 여러 곳에 복사되고 있다면 퍼사드를 떠올린다.

1. 상황

'푸른날개항공'은 공항에 셀프 체크인 키오스크를 놓았다. 개발자 지호의 화면 코드는 사내 서비스 다섯 개를 차례로 불렀다. 예약을 찾고, 여권을 확인하고, 좌석을 받고, 미국행이면 승객 정보를 미국에 신고하고, 탑승권을 뽑는다. 서비스마다 담당 팀이 따로 있고, 각자는 잘 만들어져 있었다.

이듬해 모바일 앱에서도 체크인을 하게 되었다. 모바일 팀은 지호의 코드를 열어 호출 순서를 베껴 갔다. 그 뒤 감사에서 두 가지가 드러났다. 모바일 앱은 미국행 신고를 빠뜨렸고, "여권 확인 전에는 좌석을 주지 않는다"는 규정도 순서를 바꿔 어겼다. 같은 시기 좌석 서비스 팀이 API를 새 버전으로 바꾸자 두 화면을 모두 고쳐야 했다.

문제는 어느 서비스의 품질이 아니었다. "체크인이란 이 서비스들을 이 순서와 조건으로 부르는 것"이라는 지식이 화면마다 흩어져 있었다.

2. 순진한 설계와 그 한계

감사 직전의 코드다. 예약·여권·좌석처럼 큰 기능을 이루면서 각자 따로 관리되는 부품들을 서브시스템이라 부른다. 서브시스템은 각자 짧고 단순하다. 문제는 아래쪽 두 화면이다. 코드의 pnr은 항공 예약 번호다. MobileApp.check_in()이 KioskScreen.check_in()과 어디서 달라졌는지 찾아보라.

실행하면 데모 [2]에는 신고 로그가 없고, 데모 [3]에서는 남의 여권으로도 탑승권이 나온다.

  • 흐름 지식이 복사된다. 호출 순서와 실패 조건이 화면마다 따로 있다. 사본은 언젠가 어긋난다.
  • 화면이 너무 많은 것을 안다. 화면 하나가 서브시스템 다섯 개에 직접 기댄다. 좌석 API가 바뀌면 화면을 모두 고친다.
  • 규정 준수가 화면 코드의 줄 순서에 달려 있다. 출입국 규정은 화면이 책임질 일이 아니다.

3. 패턴의 구조

GoF의 의도: "서브시스템의 인터페이스 집합에 대해 하나의 통합된 인터페이스를 제공한다." 호텔 안내 데스크를 떠올리면 된다. 손님은 "체크인해 주세요"만 말하고, 객실·청소·결제 담당을 누가 부르는지는 데스크가 안다.

역할이 장의 클래스하는 일
FacadeCheckInFacade어떤 서브시스템을 어떤 순서·조건으로 부를지 안다.
SubsystemReservationSystem, PassportReader, SeatServiceV2 등실제 기능을 한다. 퍼사드가 있는지 모른다.
ClientKioskScreen, MobileApp퍼사드로 체크인한다.

두 가지를 기억하자. 첫째, 의존은 한 방향이다. 서브시스템은 퍼사드를 모르므로 퍼사드가 여럿이어도 영향이 없다. 둘째, 퍼사드는 서브시스템을 감추지 않는다. 카운터 직원 화면은 좌석 수동 지정을 위해 SeatServiceV2를 직접 부른다. 접근을 정말 막아야 한다면 그것은 9장의 보호 프록시(호출자의 권한에 따라 접근을 허용하거나 거부하는 대리 객체)가 할 일이다.

4. 패턴 적용

지호는 원칙 하나를 세웠다. 퍼사드의 책임은 '조율'뿐이다. 좌석을 고르는 방법처럼 도메인 규칙 자체를 구현한 업무 로직은 서브시스템에 남긴다. 서브시스템은 순진한 코드와 같고 좌석 서비스만 v2(allocate, 직원 전용 override)로 바뀌었다. check_in()의 '규칙 1', '규칙 2' 주석을 보라.

어디를 보면 되는가.

  • check_in()의 규칙 1·2: 화면마다 흩어져 있던 순서 지식이 여기 한 번만 있다. 데모 [1]에서 키오스크와 모바일 모두 신고를 보낸다. 기억해서가 아니라 기억할 필요가 없어졌기 때문이다.
  • 좌석 v2 두 줄: seat_pref를 zone으로 바꾸고 allocate()를 부른다. 화면은 여전히 seat_pref="window"로 부른다.
  • CheckInError: 화면은 서브시스템별 오류가 아니라 이 예외 하나만 처리한다. 데모 [2]는 좌석 배정 전에 멈춘다.
  • 데모 [3]: 카운터 직원은 퍼사드를 거치지 않는다. 화면 하나가 기대는 대상은 다섯 개에서 퍼사드 하나로 줄었다.

주의할 점이 있다. 퍼사드는 "어디 둘지 모르는 코드"가 모이기 쉬운 곳이다. 퍼사드 안에서 계산과 검증이 자라거나, 승객용·직원용·운영용 메서드가 한 클래스에 섞이기 시작하면 신 객체로 가는 신호다. 신 객체는 너무 많은 책임을 떠안아 시스템 대부분이 기대게 된 거대한 클래스다.

5. 파이썬다운 변형

CheckInFacade는 상태가 없다. 서브시스템 참조만 들고 있을 뿐이다. 동료 서윤이 물었다. "그럼 클래스일 이유가 있어?"

아래 코드는 (1) 모듈 수준 함수 하나로 된 퍼사드 check_in()과 (2) 장치의 열기·닫기 순서를 with 한 줄 뒤에 숨기는 kiosk_session()을 보여 준다. 클래스 이름 _Device의 이름 앞 밑줄은 '내부용, 공개 API 아님'을 뜻하는 관례로, 접근을 실제로 막지는 않는다. 데모 [2]에서 예외가 나도 장치가 역순으로 닫히는지 보라.

  • 상태 없는 퍼사드는 함수면 된다. 파이썬에서는 모듈이 곧 퍼사드가 될 수 있다. 모듈이 함수 몇 개만 공개하면 쓰는 쪽에게는 단순한 정문이 된다. 밑줄 이름은 여전히 쓸 수 있으니 "퍼사드는 감추지 않는다"는 원칙과도 맞는다. 장치를 키워드 인자로 받게 한 것은 테스트에서 바꿔 끼우기 위해서다.
  • contextmanager 퍼사드는 순서와 정리를 보장한다. "판독기를 열고, 프린터를 열고, 끝나면 역순으로, 예외가 나도 반드시 닫는다"는 규칙도 체크인 흐름만큼 복사되기 쉽다. with kiosk_session() 한 줄이 이 규칙을 한 곳에 모은다.

6. 트레이드오프와 관련 패턴

얻는 것

  • 쓰는 쪽이 기대는 대상이 줄고, 흐름 규칙이 한 곳에 모인다.
  • 서브시스템이 바뀌어도 퍼사드에서 멈춘다. 고칠 곳이 화면 수만큼 늘지 않는다.

쓰지 말아야 할 때

  • 쓰는 곳이 하나뿐이고 흐름이 단순할 때. 서브시스템 두 개를 한 곳에서만 부른다면 퍼사드는 층만 하나 더한다.
  • 받은 호출을 그대로 넘기기만 할 때. facade.get_seat_map()이 seats.get_seat_map()을 부르기만 한다면 단순화가 아니라 중복이다.
  • 접근 통제가 목적일 때. "직원만 좌석을 바꿀 수 있다"는 요구는 퍼사드로 채워지지 않는다. 퍼사드는 다른 길을 막지 않는다.

퍼사드를 쪼갤지 고민될 때는 "누가, 왜 바꾸는가"를 본다. 승객 화면의 UX(사용자 경험) 개편과 운영 절차 개정처럼 서로 다른 이유로 바뀌는 메서드가 섞였다면 쓰는 사람 기준으로 나눌 때다.

헷갈리는 패턴

  • 어댑터(5장)는 이미 정해진 인터페이스에 맞춰 보통 객체 하나를 바꾼다. 퍼사드는 여러 객체 위에 새로운, 더 단순한 인터페이스를 만든다.
  • 프록시(9장)는 진짜 객체와 같은 인터페이스로 접근을 통제한다. 퍼사드는 통제하지 않는다.

연습문제 전에 알아 둘 말. 예외 연쇄는 새 예외를 던질 때 원인이 된 예외를 함께 남기는 문법(raise 새예외 from 원인)이다.

7. 연습문제

개념 문제 1. 퍼사드와 어댑터

퍼사드와 어댑터는 둘 다 "다른 객체를 감싸서 클라이언트에게 다른 인터페이스를 보여 준다." 그렇다면 둘을 어떻게 구분하는가? 감싸는 대상의 수, 인터페이스를 누가 정하는가, 의도의 세 축으로 설명하라. 그리고 이 장의 CheckInFacade.check_in() 안에서 좌석 v2 API를 다루는 두 줄은 둘 중 무엇의 성격을 띠는지 말하라.

해설 보기
축어댑터퍼사드
감싸는 대상대개 객체 하나(Adaptee)서브시스템, 즉 객체 여럿
인터페이스Target이 이미 존재하며 거기에 맞춘다퍼사드가 새로 정의한다
의도변환: 호환되지 않던 것을 함께 쓰게단순화: 복잡한 것을 쉽게 쓰게
메서드 수Target의 메서드 수와 같다보통 서브시스템 전체보다 훨씬 적다

판별 질문 하나로 줄이면 이렇다. "클라이언트가 기대하는 인터페이스가 퍼사드/어댑터보다 먼저 존재했는가?" 그렇다면 어댑터, 감싸는 쪽이 인터페이스를 새로 만들었다면 퍼사드다.

check_in() 안의 좌석 v2 두 줄(seat_pref → zone, allocate 호출)은 어댑터적 성격이다. 퍼사드가 이미 정해 둔 자기 인터페이스(seat_pref="window")에 맞춰 바뀐 서브시스템 API를 번역하고 있기 때문이다. 실무에서 두 패턴은 이처럼 한 클래스 안에 섞여 나타나는 일이 흔하다. 번역이 커지면 SeatServiceAdapter로 분리해 퍼사드는 조율에만 집중하게 하는 것이 좋다.

흔한 오답: "퍼사드는 메서드를 줄이고 어댑터는 이름을 바꾼다." 현상의 일부만 본 답이다. 메서드 하나짜리 퍼사드도, 이름이 같은 어댑터(단위만 변환)도 있다. 구분 기준은 의도와 인터페이스의 출처다.

리팩터링 문제 2. 동영상 업로드 핸들러

푸른날개항공 기내 엔터테인먼트 관리 콘솔의 업로드 핸들러다. 같은 업로드 흐름이 일괄 등록 CLI에서도 필요해졌다. 퍼사드로 리팩터링하라. 트랜스코딩(동영상을 다른 해상도·형식으로 다시 인코딩하는 작업)이 실패하면 이미 저장한 원본을 지워야 한다는 규칙도 지켜야 한다. 이처럼 뒤 단계가 실패했을 때 이미 끝난 앞 단계의 효과를 되돌리는 처리를 보상 처리라 한다.

def upload_handler(request):
    # 웹 핸들러가 서브시스템 넷을 직접 안다
    storage, transcoder = Storage(), Transcoder()
    thumbs, db = Thumbnailer(), MetadataDb()
    f = request.files["video"]
    url = storage.put(f.filename, f.read())
    try:
        # 기내 화면 규격 프로필 — CLI에도 복제될 지식
        renditions = transcoder.transcode(url, ["720p", "480p"])
    except RuntimeError as e:
        storage.delete(url)          # 보상 처리: CLI에서 빠뜨리기 쉽다
        return 422, str(e)
    thumb = thumbs.capture(url, at_sec=5)
    video_id = db.insert(request.form["title"], renditions, thumb)
    return 201, f"/videos/{video_id}"

퍼사드에 둘 것과 두지 말 것을 구분하라. 트랜스코딩 프로필 목록과 썸네일 시점은 '업로드 흐름의 정책'이므로 퍼사드에 둔다(여러 클라이언트가 공유해야 한다). 반면 HTTP 상태 코드는 웹 클라이언트만의 표현이므로 퍼사드에 두면 안 된다. 퍼사드는 IngestError라는 도메인 예외를 던지고, 그것을 422로 바꾸는 일은 핸들러의 몫이다.

해설 코드의 트랜스코더는 지원하지 않는 코덱(영상·음성을 압축하고 푸는 방식)이면 실패한다고 흉내 낸다.

흔한 오답: 퍼사드가 (status, message) 튜플을 돌려주게 만드는 것. CLI는 HTTP 상태 코드가 무의미하므로 그것을 다시 해석해야 하고, 퍼사드가 특정 클라이언트(웹)에 결합된다.

판단 문제 3. 메서드 30개짜리 퍼사드

2년 뒤 CheckInFacade의 메서드가 30개가 되었다. 승객용(체크인, 좌석 변경, 수하물 추가), 직원용(수동 좌석 지정, 오버부킹 처리, 탑승 마감. 오버부킹은 좌석 수보다 예약을 더 받는 항공사 관행이다), 운영용(통계, 장비 상태)이 섞여 있다. (가) 퍼사드를 쪼갠다, (나) 서브시스템을 재설계한다, (다) 그대로 둔다 중 무엇을 택할지 정할 판단 기준을 제시하라.

해설 보기

메서드 수 30은 그 자체로 문제가 아니다. 기준은 "누가, 왜 바뀌는가"다.

  • (가) 쪼갠다: 메서드들이 서로 다른 클라이언트군에 쓰이고, 서로 다른 이유로 바뀐다면(승객 UX 개편 vs 운영 절차 개정) SRP·ISP 관점에서 쪼갠다. 기준은 클라이언트 역할이다. 이 사례는 여기에 해당한다. 쪼갠 퍼사드들은 서브시스템 인스턴스를 공유하므로 상태가 갈라지지 않는다. 덤으로 승객용 퍼사드에는 직원 전용 기능이 없으므로 승객 퍼사드를 통해서는 그것을 부를 길이 없다(아래 실행 [3]). 다만 퍼사드는 접근을 막지 않으므로 서브시스템을 직접 쓰는 것까지 차단하려면 보호 프록시나 서브시스템의 권한 검사가 필요하다(9장).
  • (나) 서브시스템 재설계: 퍼사드 메서드 다수가 여러 서브시스템을 복잡하게 엮어 '업무 로직'을 수행하고 있다면, 퍼사드가 서브시스템의 설계 결함을 메우고 있는 것이다. 예를 들어 오버부킹 처리가 퍼사드에서 좌석·예약·보상 서비스를 열 번 오가며 계산한다면, 그 로직은 오버부킹 전용 서비스(새 서브시스템)로 내려가야 한다.
  • (다) 그대로 둔다: 30개가 모두 한 클라이언트군의 한 흐름(예: 체크인의 세부 단계들)이고, 각 메서드가 얇은 조율만 한다면 둘 수 있다. 쪼갬 자체가 목적이 되면 안 된다.

실무 신호: "이 메서드를 바꾸면 어느 팀의 테스트가 깨지는가"를 메서드별로 적어 보라. 결과가 두 개 이상의 군집으로 나뉜다면 (가), 대부분의 메서드가 서브시스템 셋 이상을 엮어 계산한다면 (나)다.

흔한 오답: "메서드가 많으니 서브시스템별로 퍼사드를 하나씩 만든다(SeatFacade, BaggageFacade…)." 이는 퍼사드의 존재 이유인 '여러 서브시스템을 엮는 흐름'을 다시 클라이언트로 돌려보내는 것이다. 나누는 축은 서브시스템이 아니라 클라이언트다.
