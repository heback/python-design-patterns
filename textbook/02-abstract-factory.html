추상 팩토리 (Abstract Factory)

함께 쓰여야 하는 객체들을, 섞이지 않게 한 번에

학습 목표

  1. "함께 쓰여야 하는 객체들(제품군)"이 섞이는 문제를 알아보고, 추상 팩토리로 그 일관성을 사람의 기억이 아닌 코드 구조로 보장할 수 있다.
  2. 새 제품군 추가는 쉽고 새 제품 종류 추가는 어렵다는 비대칭을 설명할 수 있다.
  3. 파이썬에서 생성 함수 묶음으로 제품군을 가볍게 표현하고, 그 대가로 무엇을 잃는지 판단할 수 있다.
핵심 한 줄 제품들이 서로 섞이면 안 될 때, "어느 제품군인가"를 팩토리 하나를 고르는 결정으로 단 한 번만 내리게 한다.
처음이라면 이 그림부터 이사 간 집의 방을 꾸민다고 하자. 가구 브랜드가 "원목 세트"와 "화이트 세트" 두 가지이고, 각 브랜드 매장에는 침대·책상·의자가 그 브랜드 스타일로 다 갖춰져 있다. 나는 "어느 매장에서 살까"를 한 번만 정하고, 그다음에는 그 매장에 "침대 주세요, 책상 주세요"라고만 말한다. 그러면 침대는 원목, 책상은 화이트처럼 섞일 수가 없다. 추상 팩토리가 이것이다. 매장(팩토리)이 한 세트의 제품을 모두 만들어 주고, 손님(클라이언트 코드)은 어느 매장인지만 고를 뿐 제품의 구체적인 이름은 모른다. 아래 클라우드 이야기는 이 그림을 코드로 옮긴 것이다.
이 장에서 무엇을 챙길까
  • 꼭 알아야 하는 것 ① 서로 맞아야 하는 제품들(제품군)이 섞이면 사고가 나는데, 순진한 코드는 "섞지 말자"를 사람의 기억에 맡긴다. ② 팩토리 객체 하나를 받아 거기서만 제품을 꺼내면, "어느 제품군인가"는 팩토리를 고르는 한 번의 결정으로 끝난다. ③ 비대칭: 새 제품군(클라우드)은 클래스를 더하기만 하면 되지만, 새 제품 종류(CDN)는 모든 팩토리를 고쳐야 한다.
  • 알면 좋은 것 5절처럼 클래스 대신 "생성 함수 묶음"(데이터)으로 만들면 가볍지만, 섞임 검사를 직접 해야 한다. 팩토리를 생성자 인자로 받는 방식은 테스트에 가짜를 끼우는 데도 쓰인다.
  • 처음 읽을 때는 몰라도 되는 것 구체 제품 9개의 이름(같은 모양의 반복이다), ABC·@abstractmethod의 세부, frozen과 __post_init__의 내부 동작, composition root라는 말("프로그램 시작 지점"으로 읽으면 된다). 연습문제를 풀 때 다시 찾아보면 된다.

1. 상황

파일 공유 스타트업의 엔지니어 도현은 업로드 서비스를 만들었다. 사용자가 올린 파일은 클라우드 저장소에 들어가고, 별도 프로그램인 썸네일 처리기가 그 파일을 읽어 작은 그림을 만든다. 처음에는 AWS(아마존의 클라우드. 구글의 것은 GCP다) 하나만 썼다. 저장소는 AWS의 파일 저장 서비스 S3였고(GCP의 것은 GCS), 코드 곳곳에서 S3Storage()를 그냥 만들었다.

그러다 큰 고객사가 "GCP에서만 돌려 달라"고 했다. 동료가 만드는 곳마다 if CLOUD == "gcp"를 붙여 나갔는데, 썸네일 처리기의 한 줄을 빠뜨렸다. 배포는 성공했다. 첫 파일이 올라오자 업로드는 GCP 형식의 URL(파일의 주소)을 넘겼고, 처리기는 AWS 저장소로 그 주소를 읽으려다 실패했다. 장애는 세 시간 뒤 고객의 전화로 알려졌다. 노트북에서 클라우드 없이 돌리는 세 번째 조합도 필요해졌다.

핵심은 저장소·작업 대기열·비밀 값 저장소가 같은 클라우드끼리만 서로를 이해한다는 점이다. 그런데 "섞이면 안 된다"는 규칙이 코드 어디에도 없고, 사람의 기억에만 있었다.

2. 순진한 설계와 그 한계

GCP 전환을 반쯤 끝낸 코드다. 실제 클라우드 대신 주소 형식만 흉내 냈다. 맨 위 CLOUD는 배포 설정값으로, 실제로는 환경 변수(프로그램 바깥에서 이름=값으로 넣어 주는 설정)에서 읽는다. UploadService와 ThumbnailWorker의 __init__을 비교하고, 데모 [2]에서 실패가 언제 드러나는지 보라.

데모 [1]의 "시작 OK"가 가장 위험하다. 두 저장소는 모두 멀쩡한 객체라서 만들 때는 아무 문제가 없다. 틀린 조합은 두 객체가 주소를 주고받는 순간에야 드러난다.

  • 분기가 생성 지점마다 복제된다. 환경 수 × 생성 지점 수만큼 고쳐야 하고, 하나만 빠뜨려도 장애다.
  • 일관성을 지킬 장치가 없다. 생성 함수를 make_storage(), make_queue()로 따로 모아도, 호출자가 서로 다른 클라우드를 넘겨 부를 수 있다. 1장의 단순 팩토리로는 이 문제가 풀리지 않는다.

3. 패턴의 구조

GoF의 의도는 이렇다. "구체 클래스를 지정하지 않고, 서로 관련되거나 의존하는 객체들의 군(family)을 생성하기 위한 인터페이스를 제공한다." 팩토리 메서드가 제품 하나의 생성을 미뤘다면, 추상 팩토리는 제품군의 생성 메서드를 한 객체에 묶는다. 클라이언트는 팩토리 하나만 받으므로, 팩토리를 고르는 순간 제품군 전체가 정해진다.

이 장의 제품 종류는 셋이다. 저장소, 작업 대기열인 큐(먼저 넣은 것을 먼저 꺼내는 대기열), 비밀 값 저장소다. 큐는 AWS에서는 SQS, GCP에서는 Pub/Sub라는 서비스가 맡는다.

역할이 장의 클래스
추상 팩토리(Abstract Factory)CloudFactory: 제품 종류마다 생성 메서드 하나
구체 팩토리(Concrete Factory)AwsFactory, GcpFactory, LocalFactory: 한 제품군만 만든다
추상 제품(Abstract Product)BlobStorage, MessageQueue, SecretVault
구체 제품(Concrete Product)S3Storage, SqsQueue, GcsStorage 등 9개
클라이언트(Client)UploadService, ThumbnailWorker: 팩토리 하나를 받는다

표를 격자로 보면 비대칭이 보인다. 제품군(클라우드)을 하나 더하는 것은 열을 하나 추가하는 일이라 기존 클래스를 건드리지 않는다. 제품 종류를 하나 더하는 것, 예컨대 CDN(파일을 사용자 가까운 서버에 복제해 빠르게 보내 주는 서비스)을 넣는 것은 행을 추가하는 일이다. CloudFactory에 메서드를 넣는 순간 모든 구체 팩토리를 고쳐야 한다.

4. 패턴 적용

제품군을 CloudFactory 계층으로 묶은 코드다. 길지만 구체 제품 부분은 같은 모양의 반복이다. 세 곳을 보라. 구체 팩토리가 자기 제품군만 만드는지, 클라이언트에 구체 클래스 이름이 남아 있는지, 분기가 어디에 남는지. 문법 몇 가지: @abstractmethod를 붙인 메서드는 "본문이 비어 있고, 구체 팩토리가 반드시 채워야 하는 약속"이다. 하나라도 빠뜨리면 팩토리를 만드는 순간 TypeError가 난다. class SqsQueue(MessageQueue):처럼 설명글만 있는 클래스는 "부모와 같은 모양에 이름만 다른 제품"이라는 뜻이고, 클래스 안에 바로 쓴 scheme = "s3"는 그 클래스의 모든 객체가 공유하는 값이다. 데모 [1]의 {env:5}는 글자 수가 모자라면 공백을 채워 5칸으로 맞추라는 출력 서식이다.

  • 데모 [1]에서 같은 클라이언트 코드가 세 환경에서 그대로 돈다. ThumbnailWorker는 저장소를 업로드와 같은 팩토리에서 받으므로 다른 클라우드의 저장소를 가질 길이 없다.
  • 섞인 조합을 만들려면 GcpFactory의 정의 자체를 틀려야 한다. 일관성 규칙이 "모든 생성 지점의 약속"에서 "한 클래스의 정의"로 좁혀졌다.
  • UploadService는 __init__(self, cloud)의 인자로 팩토리를 받기만 한다. 순진한 코드는 __init__ 안에서 GcsStorage() 같은 객체를 직접 만들었다. 이렇게 필요한 객체를 안에서 만들지 않고 바깥에서 생성자 인자로 받는 방식을 생성자 주입(의존성 주입의 가장 흔한 형태)이라 한다. 쓰는 쪽이 구체 클래스 이름을 몰라도 되고, 테스트에서는 가짜 객체를 넘겨 바꿔 끼울 수 있다. 다만 제품 세 개를 따로 받으면 호출자가 다시 섞어 넘길 수 있어서, 제품 대신 팩토리 하나를 받게 했다.
  • make_cloud_factory()에는 분기가 남는다. 괜찮다. 문제는 분기가 복제되는 것이었다. 프로그램 시작 지점(composition root) 한 곳에서 팩토리를 하나 만들어 모두에게 나눠 준다. 팩토리가 하나면 된다고 싱글턴으로 만들 필요는 없다(4장).
왜 팩토리 "하나"를 받을까? 더 단순한 방법이면 안 될까? 두 가지 쉬운 길이 있지만 둘 다 섞임을 막지 못한다. ① 저장소와 큐를 각자 인자로 받는 방법(UploadService(storage, queue))은 간단하지만, 호출자가 GCP 저장소와 AWS 큐를 넘겨도 막을 수 없다. ② 1장의 단순 팩토리로 make_storage(cloud), make_queue(cloud)를 따로 두면 분기는 모이지만, 호출자가 두 함수에 서로 다른 cloud 값을 줄 수 있다. 팩토리 하나를 받으면 저장소와 큐가 같은 객체에서 나오므로 섞을 길 자체가 없다. 생성 코드를 한곳에 모으는 것이 핵심이 아니라, 한 세트를 한 객체에서만 꺼내게 하는 것이 핵심이다.

5. 파이썬다운 변형

패턴 코드는 클래스가 16개다. 파이썬에서는 팩토리를 "생성 함수 몇 개의 묶음"으로 보고, 클래스 계층 대신 값 하나로 표현할 수 있다.

4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 한 클라우드의 제품을 한꺼번에 만들어 섞이지 않게 하는 것이다. 4절은 팩토리를 클래스(CloudFactory 계층)로 만든다. "GCP 제품만 만든다"는 보장이 GcpFactory라는 클래스의 정의에서 나오고, 섞이면 그 정의가 틀린 것이다. 5절은 팩토리를 생성 함수들을 담은 데이터(CloudKit)로 만든다. 클래스가 훨씬 적지만, 데이터는 누구나 섞어 만들 수 있어서 같은 보장을 실행 중 검사로 직접 지켜야 한다.

아래 코드는 팩토리를 frozen 데이터클래스 CloudKit으로, 구체 팩토리를 묶음을 만드는 함수 aws_kit(), gcp_kit()로 바꾼다. __post_init__은 데이터클래스가 자동으로 만든 생성자가 필드를 채운 직후 불러 주는 메서드로, 여러 필드에 걸친 검사를 넣는 자리다. 이것이 왜 필요한지는 데모 [2]가 답한다. 처음 나오는 표기도 읽어 두자. Callable[[], SchemeStorage]는 "인자 없이 부르면 SchemeStorage를 돌려주는 것"이다(맨 끝이 돌려주는 값, 앞 대괄호가 받는 인자 목록). lambda: SchemeStorage("aws", "s3")는 그런 함수를 이름 없이 한 줄로 만든 것이고, 이 함수 자체가 storage 필드에 담긴다. 중괄호에 값만 나열한 {a, b}는 집합이라 같은 값은 하나로 합쳐진다.

데모 [2]를 한 줄씩 풀면
  1. gcp_kit().storage — gcp_kit()이 GCP 묶음을 만들고, 거기서 storage 필드(GCP 저장소를 만드는 함수)만 꺼낸다. 끝에 ()가 없으므로 저장소를 만들지는 않고 함수만 꺼낸 것이다.
  2. aws_kit().queue — 같은 방식으로 AWS 큐를 만드는 함수를 꺼낸다.
  3. CloudKit("gcp", storage=…, queue=…) — 이름표는 "gcp"인데 큐는 AWS 것인 묶음을 만든다. 생성자가 필드를 채운 직후 __post_init__이 자동으로 불린다.
  4. __post_init__은 storage()와 queue()를 한 번씩 불러 각 제품이 밝힌 클라우드를 집합에 모은다. 결과는 {"gcp", "aws"}이고 이것은 {"gcp"}와 다르므로 ValueError를 낸다. 마지막 줄의 sorted(made)는 그 집합을 정렬해 ['aws', 'gcp']로 보여 준다.

데모 [2]가 핵심이다. 묶음은 데이터이므로 누구나 GCP 저장소와 AWS 큐를 섞어 새 묶음을 만들 수 있다. 클래스 계층에서는 GcpFactory라는 타입이 제품군 정의를 독점해 이런 일이 불가능했다. 묶음 방식은 그 보장을 실행 중 검사로 되찾아야 한다. 검사하려면 제품을 미리 만들어 봐야 하므로, 생성이 비싼 제품에는 쓰기 어렵다.

그래서 제품군이 두세 개이고 시작 지점에서만 조립된다면 묶음이 읽기 쉽다. 여러 팀이 제품군을 따로 추가하고 타입으로 일관성을 강제하고 싶거나, 제품을 만들 때 계측(실행 시간·호출 수 같은 지표를 재는 코드) 같은 공통 처리를 덧씌워야 한다면 클래스 계층이 낫다.

6. 트레이드오프와 관련 패턴

얻는 것.

  • 클라이언트가 구체 클래스를 모른다(DIP). 제품군 교체가 팩토리 하나를 바꾸는 일로 끝난다.
  • 제품군 안의 일관성이 구조로 보장된다. 이 패턴만의 이득이다.

치르는 것. 새 제품군은 수정 없이 추가되지만, 새 제품 종류는 모든 구체 팩토리를 고쳐야 한다. 이 패턴은 "제품 종류는 그대로고 제품군이 는다"는 예측에 거는 설계다.

이 패턴을 쓰지 말아야 할 때
  • 제품들 사이에 일관성 제약이 없을 때. 서로 섞여도 아무 문제가 없다면 각 제품을 따로 생성자 인자로 받게 하는 편이 단순하다. 같은 자격 증명(접근 권한을 증명하는 키·계정)이나 같은 리전(클라우드 데이터센터의 지역)을 공유해야 하는 것처럼 "같이 만들어져야" 할 이유가 있을 때만 묶는다.
  • 제품군이 하나뿐이고 테스트용 가짜만 필요할 때. 4절에서 본 생성자 주입으로 충분하다. 서비스가 필요한 저장소·큐를 생성자 인자로 받게 하고, 테스트에서는 메모리에 저장하는 가짜 객체를 넘기면 된다.
  • 제품 종류가 자주 바뀔 때. 3절 끝에서 본 비대칭 때문이다. 제품군(클라우드)을 늘리는 것은 기존 코드를 안 고쳐도 되지만, 제품 종류(저장소·큐·CDN 같은 것)를 하나 늘리면 CloudFactory와 구체 팩토리 전부에 새 메서드를 추가해야 한다. 종류가 늘 때마다 이 수정 비용을 매번 치른다.

헷갈리는 패턴과의 차이.

  • 팩토리 메서드(1장): 제품 하나의 생성을 하위 클래스에 미룬다. 추상 팩토리의 각 create_*는 팩토리 메서드이고, 그것들을 별도 객체로 떼어 클라이언트에 넘긴 것이 추상 팩토리다.
  • 빌더(3장): 추상 팩토리는 함께 쓰는 여러 객체를 즉시 만들고, 빌더는 하나의 복잡한 객체를 단계적으로 만든다.

7. 연습문제

개념 문제 1. CDN을 추가하면

배경. 이 장의 서비스는 사용자가 올린 이미지를 저장소에 보관하고, 다른 사용자가 그 이미지를 내려받아 본다. 사용자가 전 세계에 있으면 저장소가 한 곳(예: 서울)에만 있을 때 먼 나라 사용자는 이미지를 받는 데 오래 걸린다. 이 문제를 줄이려고 클라우드 업체들은 CDN(Content Delivery Network, 콘텐츠 전송 네트워크)이라는 서비스를 따로 판다. 원본 파일의 복사본을 세계 곳곳의 서버에 미리 놓아 두고, 사용자가 요청하면 가장 가까운 서버가 대신 보내 주는 서비스다. 저장소와 마찬가지로 AWS, GCP 같은 클라우드마다 이름과 사용법이 다른 또 하나의 제품 종류이고, 이름만 다를 뿐 하는 일은 같다. 이 문제는 이미 완성된 설계에 이 제품 종류를 새로 끼워 넣을 때 코드가 얼마나 바뀌는지를 묻는다. CDN의 동작 원리를 더 알 필요는 없다.

본문 패턴 코드의 설계에 제품 종류 "CDN"(create_cdn(), AWS는 CloudFront, GCP는 Cloud CDN, 로컬은 정적 파일 서버)을 추가하려 한다. (1) 새로 만들어야 하는 클래스와 수정해야 하는 기존 클래스를 각각 세라. (2) 비교를 위해 새 제품군 "Azure"를 추가할 때의 수를 같은 방식으로 세라. (3) 두 결과의 차이가 GoF가 말하는 이 패턴의 어떤 결과(consequence)인지 설명하라.

해설 보기

(1) CDN 추가: 새 클래스 4개(추상 제품 Cdn 1 + 구체 제품 CloudFrontCdn, CloudCdn, LocalStaticCdn 3). 수정할 기존 클래스 4개(CloudFactory에 추상 메서드 추가 + 구체 팩토리 3개 모두에 구현 추가). (2) Azure 추가: 새 클래스 4개(AzureFactory 1 + 구체 제품 3), 수정할 기존 클래스 0개. composition root의 분기 한 줄만 바뀐다.

(3) 만드는 클래스 수는 비슷하지만 수정의 수가 0 대 4로 갈린다. GoF는 이것을 "새로운 종류의 제품을 지원하기가 어렵다(Supporting new kinds of products is difficult)"는 결과로 명시한다. 추상 팩토리 인터페이스가 만들 수 있는 제품의 집합을 고정하기 때문이다. 즉 이 패턴은 제품군 축으로는 열려 있고 제품 종류 축으로는 닫혀 있다.

흔한 오답은 "클래스가 4개씩 생기니 비용이 같다"는 결론이다. 비용의 핵심은 새로 쓰는 코드량이 아니라 기존 코드를 건드리는 범위다. 수정은 다른 팀의 구체 팩토리(외부 저장소에 있을 수도 있다)까지 퍼지고, ABC를 썼다면 구현을 미처 추가하지 못한 구체 팩토리는 인스턴스화부터 실패한다. 이 실패는 사실 좋은 성질이다. 누락이 배포 후가 아니라 시작 시점에 드러나기 때문이다.

리팩터링 문제 2. 테마별 CLI 위젯

사내 배포 도구의 CLI(터미널에서 텍스트 명령으로 쓰는 프로그램)는 터미널 테마에 따라 버튼과 대화상자를 다르게 그린다. 아래 코드는 위젯을 만드는 곳마다 테마를 검사한다. 이것을 추상 팩토리로 리팩터링하고, 클라이언트 함수에 테마 분기가 하나도 남지 않게 하라.

def render_button(theme: str, label: str) -> str:
    # 문제: 테마 검사가 위젯 종류마다 복제된다
    if theme == "dark":
        return f"▐ {label} ▌"
    return f"[ {label} ]"

def render_dialog(theme: str, message: str, button_html: str) -> str:
    if theme == "dark":
        return f"┏ {message} ┓  {button_html}"
    return f"┌ {message} ┐  {button_html}"

def confirm_deploy(theme: str, target: str) -> str:
    # 문제: 대화상자와 버튼의 테마를 '같게' 넘기는 것은 호출자의 기억에 달려 있다
    button = render_button(theme, "확인")
    return render_dialog(theme, f"{target}에 배포할까요?", button)

def confirm_rollback(theme: str, target: str) -> str:
    # 실제로 났던 버그: 버튼에 하드코딩된 "light" — 다크 대화상자 안의 라이트 버튼
    button = render_button("light", "되돌리기")
    return render_dialog(theme, f"{target}을 되돌릴까요?", button)
해설 보기

"함께 쓰여야 하는 제품"은 버튼과 대화상자다. 대화상자가 버튼을 안에 담기 때문에 두 테마가 섞이면 화면에서 바로 드러나는, 본문 클라우드 예제와 똑같은 일관성 제약이다. WidgetFactory(추상 팩토리)에 create_button(label)과 create_dialog()를 두고, DarkWidgets/LightWidgets가 각 제품군을 만든다. 책임 배분에 주의하라. 버튼의 모양(테마)은 팩토리가 정하고, 버튼의 라벨("확인", "되돌리기")은 클라이언트가 정해 create_button()에 넘긴다. 대화상자는 받은 버튼의 render()만 부른다. 두 클라이언트 confirm_deploy()와 confirm_rollback()은 테마 문자열 대신 팩토리 하나만 받는다. 그래서 원래 confirm_rollback에서 났던 "버튼만 라이트로 하드코딩" 버그는 다시 쓸 방법이 없다. 버튼을 얻는 유일한 경로가 대화상자와 같은 팩토리이기 때문이다. 실행 결과에서 두 테마 × 두 클라이언트의 네 화면 모두 대화상자와 버튼의 테마가 일치한다. 테마 판단은 시작 시 THEMES 표 조회 한 번뿐이다.

흔한 오답 두 가지. 첫째, Button과 Dialog를 각각 클래스로 만들고 make_button(theme), make_dialog(theme) 두 팩토리 함수를 두는 것. 분기는 모였지만 호출자가 여전히 두 함수에 서로 다른 테마를 넘길 수 있어 일관성 문제가 남는다. 둘째, Dialog가 버튼을 직접 만들거나 버튼 라벨을 정하게 하는 것. 이 예에서는 동작하는 것처럼 보이지만 대화상자가 버튼의 구체 클래스나 라벨을 알게 되어, "확인" 말고 "되돌리기" 버튼이 필요한 confirm_rollback 같은 클라이언트를 만들 수 없게 된다. 리팩터링하면서 기능이 사라지는 것이다.

판단 문제 3. AWS 하나에 테스트용 가짜만

다른 팀은 앞으로도 AWS만 쓸 예정이고, 추상화가 필요한 이유는 단위 테스트에서 S3·SQS 대신 가짜 객체를 쓰기 위해서뿐이다. 이 팀에 추상 팩토리를 권하겠는가, 아니면 생성자 주입만으로 충분한가? 판단 근거를 쓰고, 어떤 조건이 생기면 추상 팩토리로 옮겨 갈지도 쓰라.

해설 보기

생성자 주입으로 충분하다. 서비스가 BlobStorage, MessageQueue를 (Protocol 타입으로) 생성자 인자로 받고, 운영 코드의 composition root에서 S3Storage와 SqsQueue를 만들어 넘기면 된다. 테스트는 인메모리 가짜를 넘긴다. 추상 팩토리가 주는 고유한 이득은 "제품군을 섞지 못하게 하는 것"인데, 운영 제품군이 하나뿐이면 섞을 대상이 없다. 테스트에서 가짜 저장소와 실제 큐를 섞어 쓰는 것은 오히려 원하는 유연성일 수 있다(통합 테스트, 곧 여러 구성 요소나 실제 외부 시스템을 함께 연결해 검증하는 테스트에서 일부만 실제로).

옮겨 갈 조건: (1) 두 번째 운영 제품군(다른 클라우드, 온프레미스, 곧 조직이 직접 보유·운영하는 서버 환경)이 생길 때, (2) 제품들이 같은 세션(여기서는 SDK가 자격 증명과 설정을 묶어 들고 있는 연결 단위)·자격 증명·리전을 공유해 "같이 만들어져야" 할 때, (3) 제품 생성 지점이 composition root 밖으로 퍼져 나갈 때(예: 요청마다 새 큐 클라이언트를 만들어야 하는 구조). 이 중 하나라도 생기면 생성 결정을 묶을 이유가 생긴다.

흔한 오답은 "테스트 가짜도 하나의 제품군이니 FakeFactory를 만들자"이다. 형식적으로는 맞지만, 테스트마다 일부 제품만 바꾸고 싶을 때 팩토리 전체를 새로 정의해야 하므로 테스트가 더 번거로워진다. 패턴이 "가능하다"는 것과 "이득이 있다"는 것은 다르다.
