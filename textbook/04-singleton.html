싱글턴 (Singleton)

'하나여야 한다'와 '어디서든 얻는다'를 떼어 놓기

학습 목표

  1. "인스턴스가 하나여야 한다"(유일성)와 "어디서든 얻을 수 있어야 한다"(전역 접근)를 나눠 보고, 싱글턴이 둘을 묶을 때 생기는 비용을 설명할 수 있다.
  2. 파이썬의 여러 구현(__new__, 메타클래스, 모듈 수준 객체)을 비교하고, __init__ 재호출 함정을 다룰 수 있다.
  3. 싱글턴을 composition root에서 하나만 만들어 주입하는 설계로 바꿀 수 있고, 싱글턴이 정당한 드문 경우를 판단할 수 있다.
핵심 한 줄 "하나면 충분하다"는 싱글턴의 이유가 아니다. "둘이면 틀린다"일 때만 유일성을 강제하고, 그때도 전역 접근은 따로 판단한다.

1. 상황

종합병원 개발자 태윤은 감사 로그를 맡았다. 감사 로그는 누가 언제 어떤 환자 기록을 열람·수정했는지 나중에 검증할 수 있게 빠짐없이 남기는 기록이다. 태윤은 각 기록이 직전 기록의 번호를 담게 해, 기록들이 한 줄의 체인으로 이어지게 했다. 중간 기록을 지우거나 고치면 체인이 끊겨 드러난다. 이 구조가 성립하려면 "마지막 기록 번호"를 쥔 기록기가 반드시 하나여야 한다.

처방·검사·원무 모듈이 각자 AuditLogger()를 만들자, 검증 도구가 수백 건을 "변조 의심"으로 내놓았다. 실제 변조는 없었다. 세 기록기가 각자의 "마지막 번호"를 들고 같은 파일에 번갈아 써서 체인이 세 갈래로 갈라진 것이다.

태윤은 싱글턴을 택했고 체인은 다시 하나가 되었다. 두 달 뒤 테스트 담당자가 모듈별 단위 테스트를 도입하자 새 문제가 났다. 혼자 돌리면 통과하는 테스트가 전체와 함께 돌리면 실패했다. 앞선 테스트의 기록이 같은 싱글턴에 쌓여 있었다. 싱글턴은 첫 고통을 풀었지만, 두 번째 고통은 싱글턴 자신이 만들었다.

2. 순진한 설계와 그 한계

싱글턴 도입 전, 모듈마다 기록기를 만들던 코드다. AuditLogger 자체는 결함이 없다. 문제는 _last라는 상태가 인스턴스마다 따로 있다는 점과, 세 모듈이 각자 인스턴스를 만든다는 점이 겹칠 때 생긴다. 데모 [2]의 prev를 위에서 아래로 따라가 보라.

  • 상태가 여러 벌이다. 기록기마다 "내가 마지막으로 쓴 번호"를 따로 들고 있어 #1, #2는 자기가 첫 기록이라 믿는다.
  • 각자는 정확하다. 기록기 하나만 쓰면 완벽하다. 파일 하나를 함께 쓰는 순간 서로를 모른다.

요구를 정확히 적으면 이렇다. "체인 파일 하나에 기록기 상태는 하나여야 한다." "어디서든 기록기를 얻을 수 있어야 한다"는 요구는 없다. 이 구분이 이 장의 결론을 정한다.

3. 패턴의 구조

GoF의 의도는 이렇다. "클래스의 인스턴스가 오직 하나임을 보장하고, 그 인스턴스에 대한 전역적인 접근점을 제공한다." 한 문장에 요구가 둘이다. (1) 유일성: 인스턴스가 하나다. (2) 전역 접근: 어디서든 그것을 얻는다. 싱글턴은 이 둘을 클래스 하나에 묶는다.

파이썬은 Cls()를 부르면 먼저 __new__로 객체를 할당해 얻고, 그다음 __init__으로 초기화한다. 싱글턴은 이 할당 단계에서 "이미 있으면 그것을 돌려준다"로 유일성을 통제한다.

요구싱글턴에서 맡는 곳대가
유일성클래스 자신(__new__, _instance)테스트에서도 하나뿐 → 테스트끼리 간섭, 리셋 뒷문
전역 접근어디서나 부르는 AuditLogger()의존성이 시그니처에 안 보이고, 구체 클래스에 묶인다(DIP 충돌)

4. 패턴 적용

태윤이 적용한 싱글턴이다. __new__의 잠금(threading.Lock)은 한 번에 한 스레드(한 프로그램 안에서 동시에 도는 실행 흐름)만 그 구간에 들어가게 하는 도구다. 잠금이 없으면 서버 재시작 직후 동시에 온 두 요청이 각자 "처음" 만들 수 있다. 앞부분에서는 __init__의 _initialized 가드가 무엇을 막는지, 뒷부분에서는 prescribe()의 시그니처와 두 테스트의 결과를 보라. pytest 같은 테스트 도구는 여러 테스트를 한 프로세스에서 차례로 돌리므로, 데모 [2]처럼 테스트들이 같은 싱글턴을 공유한다.

  • 데모 [1]: 몇 번을 부르든 같은 객체다. 첫 고통은 풀렸다.
  • __init__ 가드: 파이썬에서 AuditLogger()는 type.__call__(클래스 호출 Cls()를 실제로 처리하는 메서드)이 처리한다. 이것은 __new__가 기존 객체를 돌려줘도 __init__을 다시 부른다. 가드가 없으면 부를 때마다 기록이 지워진다.
  • 데모 [2]: 테스트 B가 A의 기록까지 본다. 결과가 실행 순서에 달려 있다. 단위 테스트가 가져서는 안 되는 성질이다.
  • 데모 [3]: 리셋 뒷문은 증상만 가린다. 운영 코드에 "유일한 인스턴스를 지우는" 문이 생겼다.

prescribe()의 생성자도 인자도 감사 로그를 말하지 않는다. 본문을 읽어야만 전역 상태에 쓴다는 것을 알고, 호출자는 그것을 바꿀 수 없다. 이것이 숨은 의존성이다. 진단을 정리하면, 첫 고통을 푸는 데 필요했던 것은 유일성뿐이었다. 두 번째 고통은 모두 전역 접근에서 나왔다.

5. 파이썬다운 변형

5.1 "하나"를 만드는 다른 방법

아래 구현 비교 코드는 두 방법을 나란히 놓는다. 메타클래스는 클래스를 만들어 내는 클래스(기본은 type)로, 클래스가 호출되는 방식 자체를 바꿀 수 있다. 각 방식에서 유일성을 보장하는 주체가 누구인지 보라.

데모 [1]의 메타클래스 방식에는 __init__ 재호출 함정이 없다. 인스턴스가 이미 있으면 원래의 생성 절차 자체를 건너뛰기 때문이다. 대신 상속 계층 전체에 퍼지고 다른 메타클래스와 섞기 어렵다.

데모 [2]가 더 중요하다. 모듈은 이미 싱글턴이다. 모듈은 첫 import 때 한 번만 실행되므로, 모듈 수준에 만든 audit_logger는 프로세스에 하나다. 클래스는 평범하고, 테스트는 언제든 새 객체를 만들 수 있다. 다만 함수 본문에서 그 변수를 가져다 쓰면 숨은 의존성은 그대로다.

5.2 두 요구를 떼어 놓기: composition root에서 주입

태윤의 최종 설계다. AuditLogger는 평범한 클래스로 돌아가고, 유일성은 조립 지점 build_app() 하나가 맡으며, 모듈들은 기록기를 생성자로 받는다. 데모 [3]이 보여 주는 대가도 놓치지 말라.

데모 [1]에서 운영 앱의 체인은 하나다. 데모 [2]에서 테스트는 각자 기록기를 넣고, 간섭도 리셋 뒷문도 없다. 이 차이를 만든 것은 PrescriptionModule.__init__(self, audit)이라는 시그니처 한 줄이다. 의존성이 드러나자 바꿀 수 있게 되었다. 대가는 데모 [3]이다. 이제 유일성은 "운영 코드에서 AuditLogger()를 부르는 곳은 build_app 하나"라는 규칙이고, 코드 리뷰로 지킨다.

6. 트레이드오프와 관련 패턴

얻는 것.

  • 유일성이 실행 중에 강제된다.
  • 조립 코드 없이 어디서든 쓸 수 있어 작은 스크립트에서는 편하다.

치르는 것. 숨은 의존성, 테스트 간섭과 리셋 뒷문, 구체 클래스에 대한 의존, 잠금 코드. 비용 대부분은 유일성이 아니라 전역 접근에서 나온다. 그리고 "하나"는 프로세스당 하나일 뿐이다.

이 패턴을 쓰지 말아야 할 때
  • "하나면 충분하다"일 뿐 "둘이면 틀린다"가 아닐 때. 설정 객체, 데이터베이스 커넥션 풀(비싼 연결을 미리 만들어 두고 재사용하는 연결 묶음), 2장의 구체 팩토리는 하나면 충분하지만 테스트에서 둘을 만드는 것은 문제가 없다. composition root에서 하나 만들어 주입하라.
  • "어디서든 쓸 수 있어 편하다"가 동기일 때. 그것은 전역 변수를 원한다는 뜻이다.
  • 클래스로 유일성을 강제하려 할 때. 정말 프로세스 전역 객체가 필요해도 모듈 수준 객체가 더 단순하다.

정당한 경우는 드물게 있다. 둘이면 논리적으로 틀리고, 상태가 없거나 그 상태를 테스트가 신경 쓰지 않을 때다. 파이썬의 None이 그렇다(is 비교가 뜻을 가지려면 하나여야 한다). 표준 라이브러리의 logging.getLogger(name)은 이름별로 로거를 하나만 두는 레지스트리다. 같은 이름에 로거가 둘이면 핸들러(로그를 실제로 어디에 어떻게 내보낼지 맡는 객체) 설정이 갈라지기 때문이다. 감사 로그 기록기는 상태가 있고 테스트가 그 상태를 검사하므로 해당하지 않는다.

헷갈리는 패턴과의 차이.

  • 추상 팩토리(2장): 구체 팩토리는 흔히 하나면 충분하다. 그래도 싱글턴으로 만들지 말고 composition root에서 나눠 준다.
  • 프록시(9장): "처음 쓸 때 만든다"가 싱글턴을 쓰는 이유라면, 프록시가 전역 접근 없이 같은 효과를 낸다.

연습문제 전에 알아 둘 말. EMR은 병원이 환자의 진료 기록을 전산으로 관리하는 시스템(전자의무기록)이다.

7. 연습문제

개념 문제 1. 인스턴스는 하나인데 기록이 사라진다

__new__를 재정의한 싱글턴에서 __init__이 self.entries = []로 상태를 초기화한다. 처방 모듈이 기록을 남긴 뒤 검사 모듈이 처음 AuditLogger()를 부르면 기록이 사라진다. 이 버그를 재현하는 코드를 쓰고, 파이썬의 객체 생성 절차로 원인을 설명하라. 해결책을 두 가지 제시하라.

해설 보기

원인: Cls() 호출은 type.__call__이 처리하며, 대략 "obj = Cls.__new__(Cls)를 부르고, obj가 Cls의 인스턴스이면 obj.__init__()을 부른다"로 동작한다. __new__가 새 객체 대신 기존 객체를 돌려줘도 그것은 여전히 Cls의 인스턴스이므로 __init__이 다시 실행된다. 유일성은 지켜졌지만 그 유일한 객체의 상태가 매번 덮어써진다.

해결 1: __init__ 첫 줄에서 _initialized 플래그를 검사해 두 번째 호출부터 즉시 반환한다(본문 패턴 코드의 방식). 해결 2: 상태 초기화를 __new__의 "처음 만들 때" 분기로 옮기고 __init__을 정의하지 않는다. 메타클래스 방식(본문 구현 비교 코드)은 type.__call__ 자체를 건너뛰므로 이 함정이 원천적으로 없다.

흔한 오답은 "__new__가 새 객체를 만들어서"다. 실험에서 cls() is cls()가 True이므로 객체는 하나다. 사라진 것은 객체가 아니라 상태다. 또 하나의 오답은 "__init__에서 if not hasattr(self, 'entries')로 검사한다"인데, 동작은 하지만 속성이 여러 개가 되면 검사도 늘어나고, 하위 클래스가 다른 속성을 추가하면 깨진다. 초기화 여부라는 하나의 사실은 하나의 플래그로 표현하는 편이 낫다.

리팩터링 문제 2. Config.instance()를 주입으로

EMR 병동 알림 기능의 세 모듈은 아래처럼 메서드 안에서 Config.instance()를 부른다. 이것을 생성자 주입으로 바꾸고, 테스트에서 "야간 시작 시각"만 바꾼 가짜 설정을 넣어 투약 알림 시각을 검증하는 예를 보여라.

class Config:
    """싱글턴 설정 — 프로세스 전체가 하나를 공유한다."""
    _instance = None

    @classmethod
    def instance(cls) -> "Config":
        if cls._instance is None:
            cls._instance = cls()
            cls._instance.values = {"beds_per_ward": 30, "med_alert_minutes": 15,
                                    "night_start_hour": 22}
        return cls._instance

class BedAssigner:
    def has_room(self, occupied: int) -> bool:
        # 숨은 의존성: 시그니처에 설정이 없다
        return occupied < Config.instance().values["beds_per_ward"]

class MedicationAlert:
    def alert_at(self, dose_minute: int) -> int:
        cfg = Config.instance().values
        lead = cfg["med_alert_minutes"]
        if dose_minute // 60 >= cfg["night_start_hour"]:
            lead *= 2   # 야간에는 두 배 일찍
        return dose_minute - lead

class NightCall:
    def is_night(self, hour: int) -> bool:
        return hour >= Config.instance().values["night_start_hour"]

# 테스트가 하던 일: 전역 설정을 바꿨다가 되돌린다 — 실패하면 되돌리지 못한다
# Config.instance().values["night_start_hour"] = 20
해설 보기

세 단계로 바꾼다. (1) 모듈이 실제로 쓰는 세 값만 담은 불변 값 객체 WardSettings를 정의한다. 전역 Config 전체를 주입하지 않는 이유는 모듈이 무엇에 의존하는지 타입이 정확히 말하게 하기 위해서다. (2) 각 모듈은 생성자에서 WardSettings를 받는다. (3) 설정 파일을 읽는 일은 composition root 한 곳에서 한다.

테스트는 dataclasses.replace(settings, night_start_hour=20)으로 하나만 바꾼 설정을 만들어 넣는다. 원래 설정은 불변이라 영향받지 않고, 되돌릴 것도 없으며, 병렬로 돌려도 안전하다.

흔한 오답 두 가지. 첫째, 모듈 생성자의 기본값을 settings=Config.instance()로 두는 것. 시그니처에 의존성이 드러나는 것은 좋지만, 기본값이 import 시점에 한 번 평가되어 싱글턴이 그대로 숨어 있고, 주입을 깜빡한 호출부는 조용히 전역을 쓴다. 둘째, Config에 set_instance(fake)를 추가해 테스트에서 바꿔 끼우는 것. 이것은 리셋 훅의 변형으로, 전역 상태를 테스트가 조작한다는 문제를 그대로 둔다.

판단 문제 3. 무엇을 하나로 만들까

다음 네 가지 각각에 대해 싱글턴 클래스, 모듈 수준 객체, composition root 주입 중 무엇이 적절한지 고르고 근거를 쓰라. (a) 로깅 설정(핸들러·포맷 구성), (b) DB 커넥션 풀, (c) 애플리케이션 설정, (d) 시뮬레이션용 난수 생성기.

해설 보기

(a) 로깅 설정 → 모듈 수준(표준 logging의 레지스트리 그대로). logging.getLogger(__name__)은 이미 이름별로 하나인 레지스트리이고, 로깅은 거의 모든 코드가 쓰는 횡단 관심사(로깅·인증·계측처럼 여러 모듈에 걸쳐 공통으로 필요해 한 모듈에 담기 어려운 관심사)라 주입하면 모든 시그니처가 오염된다. 테스트도 로그 내용을 거의 검증하지 않는다(필요하면 caplog 같은 도구로 핸들러를 붙인다). 상태가 있어도 테스트가 신경 쓰지 않는 경우의 전형이다. 설정 자체는 진입점에서 한 번 logging.basicConfig/dictConfig로 한다.

(b) DB 커넥션 풀 → composition root 주입. 운영에서는 하나여야 효율적이지만(연결 수 제한), 둘이 있다고 논리적으로 틀리지는 않는다. 그리고 테스트는 반드시 다른 풀(테스트 DB, 그리고 트랜잭션을 롤백하는 픽스처)을 써야 한다. 트랜잭션은 전부 반영되거나 전부 취소되어야 하는 작업 단위이고, 롤백은 진행한 변경을 취소해 이전 상태로 되돌리는 것이며, 픽스처는 테스트 전에 환경을 준비하고 끝난 뒤 정리하는 테스트 구성 요소다. 테스트마다 트랜잭션을 열었다가 롤백하면 운영 데이터에 흔적을 남기지 않는다. 숨은 전역 풀은 테스트가 운영 DB에 연결되는 사고의 원인이 된다.

(c) 애플리케이션 설정 → composition root에서 읽어 필요한 부분만 주입. 연습문제 2 그대로다. 설정이야말로 테스트가 경계값을 바꿔 가며 검증하고 싶은 대상이다.

(d) 난수 생성기 → 주입. 모듈 함수 random.random()은 숨은 전역 Random 인스턴스를 쓴다. 시뮬레이션의 재현성을 위해서는 random.Random(seed)를 만들어 주입해야 한다. 전역 시드(random.seed)는 다른 라이브러리가 같은 전역 생성기를 소비하면 재현성이 깨진다. "하나"가 오히려 해로운 경우다.

네 경우 모두 "싱글턴 클래스"는 답이 아니다. 흔한 오답은 (b)를 "자원이 비싸니 싱글턴"으로 고르는 것이다. 비싸다는 것은 "하나면 충분하다"의 근거이지 "하나만 존재할 수 있어야 한다"의 근거가 아니다.
