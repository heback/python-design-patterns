어댑터 (Adapter)

고칠 수 없는 남의 인터페이스를 우리 언어로 번역하기

학습 목표

  1. 고칠 수 없는 외부 인터페이스를 우리가 정한 인터페이스로 바꿔 주는 어댑터를 만들 수 있다.
  2. 객체 어댑터(합성)와 클래스 어댑터(상속)의 차이를 설명할 수 있다.
  3. 어댑터가 숨겨야 할 차이(이름, 단위, 실패 방식, 결과 전달 방식)를 찾아낼 수 있다.
핵심 한 줄 남의 코드는 못 고치고, 그 코드의 사정이 우리 코드 곳곳에 새고 있다면 어댑터를 떠올린다.
처음이라면 이 그림부터 외국 손님과 대화하는 자리에 통역사가 있다. 우리는 우리말로만 말하고, 통역사가 그것을 상대의 말로 바꿔 전하고, 상대의 대답도 우리말로 바꿔 돌려준다. 상대의 말투는 우리가 바꿀 수 없다. 새 외국어를 쓰는 손님이 오면 통역사만 새로 구하면 되고, 우리 말하기 방식은 그대로다. 어댑터가 이것이다. 우리가 정한 "우리 말"(Target)이 있고, 남의 코드마다 그 말로 바꿔 주는 통역사(어댑터)를 하나씩 둔다. 아래 결제 이야기는 이 그림을 코드로 옮긴 것이다.
이 장에서 무엇을 챙길까
  • 꼭 알아야 하는 것 ① 고칠 수 없는 남의 인터페이스를 우리가 정한 인터페이스로 번역하는 객체가 어댑터다. ② 번역할 차이는 이름·단위·실패를 알리는 방식·결과를 돌려주는 방식이고, 번역 규칙은 어댑터 한 곳에만 둔다. ③ 어댑터는 남의 객체를 상속하지 않고 필드로 들고 있다가 일을 넘긴다(합성).
  • 알면 좋은 것 5절처럼 상속 없이 모양만 맞추거나(Protocol), 함수 하나로 어댑터를 만들 수 있다. 메서드를 통째로 넘기는 __getattr__ 위임은 번역을 건너뛰게 하므로 조심한다.
  • 처음 읽을 때는 몰라도 되는 것 클래스 어댑터(다중 상속)와 MRO, Decimal의 세부, 연습문제의 인터페이스 오염. 연습문제를 풀 때 다시 찾아보면 된다.

1. 상황

캠핑용품 쇼핑몰 '솔숲상회'의 개발자 예린은 결제를 붙였다. 결제는 PG사(가맹점 대신 카드 결제 승인·취소를 처리해 주는 회사)가 맡는다. 처음 계약한 PG사 A의 SDK는 단순했고, 주문 서비스·환불 화면·밤마다 하루치 거래를 맞춰 보는 정산 배치가 모두 이 SDK를 직접 불렀다.

그 뒤 PG사 B와 간편결제 C가 추가되었다. B는 금액을 Decimal(오차 없는 10진수 타입)로 받고, 실패해도 예외 대신 status_code가 0이 아닌 응답을 준다. C는 금액을 센트처럼 100배 한 정수, 즉 최소 화폐 단위(minor unit)로 받아서 15,000원은 1500000이다. 결과도 콜백(미리 넘겨 둔 함수를 SDK가 나중에 불러 주는 방식)으로 온다. 예린은 PG마다 if 분기를 넣고 그 분기를 결제·환불 곳곳에 복사했다.

그러다 15,000원 환불 요청에 150원이 환불되었다. 환불 쪽에 복사한 C 분기에서 ×100을 빠뜨린 것이다. "C는 ×100"이라는 번역 규칙이 여기저기 흩어져 있었고, SDK는 남의 코드라 고칠 수도 없다.

2. 순진한 설계와 그 한계

사고 직전의 코드다. 차이가 큰 B와 C만 실었다. 앞쪽은 SDK 흉내이고, 뒤쪽 OrderService가 예린의 코드다. pay()와 refund()에 같은 분기가 두 번 있다는 점, 그리고 # ⚠ 문제: 주석을 보라.

실행하면 데모 [2]에서 실패를 알리는 방식이 PG마다 다르고, 데모 [3]에서 1500000이 아니라 15000 minor unit이 나간다.

  • 번역 규칙이 흩어져 있다. "B는 Decimal", "C는 ×100"이 pay()와 refund()에 따로 있다. 사본이 둘이면 언젠가 어긋난다.
  • 주문 서비스가 남의 말을 쓴다. status_code, 콜백 같은 SDK 사정이 주문 로직에 섞였다.
  • PG가 늘면 주문 서비스를 고친다. 고수준 코드가 특정 SDK에 직접 기대고 있다.

3. 패턴의 구조

GoF의 정의는 이렇다. "클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환한다." 여행용 플러그 어댑터와 같다. 전기는 그대로고 꽂는 모양만 바뀐다.

역할이 장의 클래스하는 일
ClientOrderServiceTarget으로만 결제를 요청한다.
TargetPaymentGateway우리가 정하는 인터페이스. 우리 말로 쓴다.
AdapteePgBClient, PgCClient쓸모는 있지만 모양이 안 맞는 남의 코드.
AdapterPgBAdapter, PgCAdapterTarget을 구현하고, 요청을 SDK의 말로 번역한다.

Target은 SDK들의 공통분모가 아니라 "주문 서비스가 결제에 대해 알고 싶은 최소한"으로 정한다.

어댑터를 만드는 방법은 두 가지다. 객체 어댑터는 SDK 객체를 필드(_client)로 갖고 일을 넘긴다(합성). 클래스 어댑터는 Target과 SDK를 둘 다 상속해 SDK 메서드를 물려받는다. 이 장은 객체 어댑터를 쓴다. 상속하면 SDK의 모든 메서드가 우리 인터페이스에 함께 딸려 오기 때문이다.

4. 패턴 적용

예린은 먼저 Target을 정했다. 금액은 원 단위 int, 결과는 거래번호 str, 실패는 우리 예외 PaymentDeclined 하나. 그다음 SDK마다 어댑터를 하나씩 두었다. SDK 흉내 부분은 순진한 코드와 같으니 건너뛰고 PaymentGateway부터 읽으면 된다. 코드에 처음 나오는 모양 몇 가지를 미리 읽어 두자. str | None은 "문자열이거나 None"이다. PaymentGateway(ABC)의 @abstractmethod는 "하위 클래스가 반드시 채워야 하는 메서드"라는 표시다. PgCAdapter._wait()는 처음 보면 가장 어렵다. C SDK는 결과를 반환값이 아니라 콜백(나중에 불러 달라고 넘겨 둔 함수)으로 주는데, 어댑터는 그것을 반환값으로 바꿔야 하기 때문이다. 코드 뒤의 풀이를 따라가 보라.

어디를 보면 되는가.

  • PgBAdapter._check(): 상태 코드 방식의 실패를 PaymentDeclined로 바꾼다. 이렇게 남의 실패 표현을 경계에서 우리 예외로 바꾸는 일을 예외 변환이라 한다.
  • PgCAdapter.MINOR_PER_KRW: 단위 규칙이 상수 하나에 있고 pay()와 refund()가 함께 쓴다. 데모 [1]에서 이번에는 1500000이 나간다.
  • PgCAdapter._wait(): 콜백으로 오는 결과를 반환값으로 바꾼다. 결과 전달 방식도 번역 대상이다.
  • OrderService: PG 이름도, Decimal도, status_code도 없다. 데모 [2]에서 두 실패가 같은 모양으로 보인다.
PgCAdapter.pay(15_000, "tok_ok")를 한 줄씩 풀면
  1. minor = 15000 * 100 — 원 단위를 C의 말(minor unit)로 바꿔 1500000을 만든다.
  2. lambda cb: self._client.submit(minor, card_token, cb) — lambda는 이름 없는 한 줄 함수다. "콜백 cb를 받으면 C의 submit을 부르는 함수"를 만들어 _wait에 넘길 뿐, 아직 부르지는 않는다.
  3. _wait 안에서 box = {}(빈 상자)를 만들고 start(...)를 부른다. 이때 콜백으로 "ok와 v를 상자에 적어 두는 함수"를 건넨다.
  4. C의 submit이 끝나며 콜백을 부르면 상자에 ok=True, v="C-1"이 적힌다. 함수가 바깥 변수에 값을 다시 대입할 수는 없지만 상자(dict) 안을 고치는 것은 되어서 상자를 쓴다.
  5. _wait가 상자를 읽어 성공이면 "C-1"을 return한다. 실패면 PaymentDeclined를 던진다. 호출한 쪽에서는 그냥 반환값을 받는 함수처럼 보인다.

어댑터의 두께는 SDK와의 차이만큼이다. 가치는 번역 코드 자체가 아니라 번역 규칙이 한 곳에 모이고, 그 바깥은 우리 말만 쓴다는 데 있다.

왜 어댑터 클래스를 따로 둘까? OrderService 안에 번역 함수를 두면 안 될까? 번역을 OrderService 안에 두면 주문 서비스가 PG 종류와 그 SDK의 사정을 알게 된다. 새 PG가 오면 주문 서비스를 또 고쳐야 하니 순진한 코드와 같다. 어댑터를 따로 두면 OrderService는 PaymentGateway만 알고, PG를 늘리는 일은 어댑터를 추가하는 일이 된다. 메서드가 pay·refund 둘이고 SDK 객체와 단위 규칙을 함께 들고 있어야 해서 클래스가 맞다. 메서드가 하나뿐이면 함수로 충분한데, 그것이 5절이다. 또 "구체 SDK 말고 추상(PaymentGateway)에 기대라"는 DIP는 지켜야 할 규칙이고, 어댑터는 외부 SDK를 상대로 그 규칙을 지키는 방법이다.

5. 파이썬다운 변형

팀 리드 도윤이 세 가지를 물었다. 어댑터가 꼭 Target을 상속해야 하나? 정산 배치처럼 함수 하나만 필요한 곳도 클래스로 만드나? SDK 메서드가 스무 개면 __getattr__ 한 줄로 넘기면 되지 않나?

4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 남의 SDK의 사정을 한 겹 안쪽에 가두고 바깥은 우리 말만 쓰게 하는 것이다. 4절은 Target을 ABC로 만들어 어댑터가 상속하게 하고 클래스로 묶는다. 5절은 같은 일을 모양만 맞으면 통과하는 Protocol, 또는 함수 하나로 줄인다. 대신 5절에서는 빠뜨린 메서드를 객체를 만들 때 알려 주지 않으므로 스스로 더 챙겨야 한다.

아래 코드가 데모 [1]~[3]으로 차례로 답한다. (1) Protocol로 정한 Target에 상속 없는 PgBAdapter가 들어간다. (2) b_charger()는 클로저로 만든 함수 어댑터다. (3) LeakyPgBAdapter는 일부러 나쁘게 만든 예다. 읽는 법을 미리 적는다. Charger = Callable[[int, str], str]은 "맨 끝이 돌려주는 값(str), 앞 대괄호가 받는 인자 목록(int, str)"이니 (금액, 토큰)을 받아 거래번호를 돌려주는 함수라는 뜻이다. b_charger()는 함수 안에서 함수 charge를 만들어 돌려주는데, charge는 바깥의 client를 계속 기억한다(클로저). __getattr__은 "보통의 속성 찾기가 실패했을 때만 불리는" 특수 메서드다. 데모 [3]에서 leaky.create_payment는 어댑터에 그 이름이 없으니 __getattr__이 불려 SDK의 메서드를 그대로 꺼내 준다. 번역을 거치지 않은 호출이 되는 이유다.

  • Protocol이면 모양만 맞으면 된다. 남이 만든 클래스도 메서드 모양이 같으면 어댑터 없이 끼울 수 있다. 대신 빠뜨린 메서드는 객체를 만들 때가 아니라 정적 검사기를 돌려야 잡힌다.
  • 메서드 하나짜리 Target은 Callable이다. 정산 배치가 원하는 Charger는 "(금액, 토큰) → 거래번호" 함수다. 그 모양으로 바꿔 주는 함수가 곧 어댑터다. 메서드가 여럿이고 상태를 나눠 쓰면 다시 클래스가 낫다.
  • __getattr__ 위임은 경계에 구멍을 낸다. 데모 [3]처럼 번역을 거치지 않은 create_payment가 새어 나와 호출자가 다시 status_code를 알게 된다. 넘길 메서드가 너무 많다면 Target이 너무 넓다는 신호다.

6. 트레이드오프와 관련 패턴

얻는 것

  • 번역 규칙이 SDK마다 한 곳에 모인다. 같은 실수가 두 번 생기지 않는다.
  • 주문 서비스가 우리 말만 쓴다. SDK를 바꿔도 주문 서비스는 그대로다.

쓰지 말아야 할 때

  • 외부 SDK가 하나뿐이고 바뀔 계획도 없을 때. Target과 어댑터는 읽을 거리만 늘린다. SDK 예외가 새는 것만 막고 싶다면 얇은 함수 하나면 된다.
  • 양쪽 다 우리 코드일 때. 어댑터를 두지 말고 이름을 고친다. 어댑터는 '고칠 수 없음'이 전제다.
  • 하는 일 자체가 다를 때. 어댑터는 같은 일을 다른 모양으로 하는 것만 맞춘다. 의미가 다른 것을 억지로 맞추면 어댑터 안에 업무 규칙이 자란다.

헷갈리는 패턴

  • 데코레이터(6장)는 인터페이스를 그대로 두고 기능을 더한다. 어댑터는 인터페이스를 바꾸고 기능은 더하지 않는다.
  • 프록시(9장)는 진짜 객체와 같은 인터페이스로 접근을 통제한다.
  • 퍼사드(8장)는 여러 객체 위에 새로운, 더 단순한 인터페이스를 만든다. 어댑터는 이미 정해진 Target에 맞춘다.

7. 연습문제

개념 문제 1. 클래스 어댑터를 권하지 않는 이유

동료가 이렇게 제안했다. "class PgBClassAdapter(PaymentGateway, PgBClient)로 다중 상속하면 _client 필드도 위임 코드도 필요 없다." 파이썬에서 이것은 문법적으로 가능하다. 그런데도 이 장이 객체 어댑터를 기본으로 하는 이유를 MRO와 인터페이스 오염 관점에서 설명하라. MRO(메서드 결정 순서)는 메서드를 찾을 때 클래스들을 훑는 순서이고, 인터페이스 오염은 의도하지 않은 메서드가 공개 인터페이스에 섞여 들어 경계가 흐려지는 것이다. B SDK가 refund(payment_id, amount)라는, Target과 같은 이름이지만 다른 시그니처의 메서드를 갖고 있다고 가정하라.

해설 보기

세 가지 문제가 있다. 아래 코드가 각각을 실행으로 보인다.

  1. 인터페이스 오염: 클래스 어댑터는 SDK의 모든 공개 메서드를 상속하므로 create_payment, refund_all이 Target에 그대로 노출된다. 또 isinstance(adapter, PgBClient)가 참이 되어 "이 객체는 SDK 클라이언트이기도 하다"는, 우리가 의도하지 않은 약속을 외부에 하게 된다. 어댑터의 존재 이유인 '경계'가 사라진다.
  2. 이름 충돌과 self 호출 납치: Target과 SDK가 같은 이름 refund를 쓰면 하나만 살아남는다. MRO가 PgBClassAdapter → PaymentGateway → ABC → PgBClient이므로 어댑터의 refund가 이긴다. 그 결과 SDK 내부의 refund_all()이 호출하는 self.refund(...)까지 동적 디스패치(호출할 메서드 구현을 실행 시점에 객체의 실제 타입으로 고르는 것)에 의해 우리 메서드로 넘어가, SDK가 기대한 PaymentResponse 대신 None을 받고 터진다. SDK 작성자가 전혀 예상하지 못한 방식으로 SDK를 깨뜨린 것이다.
  3. MRO 의존: 어댑터 안에서 SDK의 원본 refund를 부르려면 PgBClient.refund(self, ...)처럼 MRO를 우회해야 한다. 부모 순서를 바꾸면 동작이 바뀌는 코드는 SDK 버전 업그레이드에도 취약하다.

흔한 오답: "다중 상속은 다이아몬드 문제가 있어서 위험하다." 다이아몬드 문제란 두 부모가 같은 조상을 공유할 때 조상의 메서드가 어느 경로로, 몇 번 불리는지 모호해지는 것이다. 파이썬은 C3 선형화(다중 상속 계층을 부모 순서를 지키는 한 줄의 MRO로 펴는 알고리즘)로 이를 결정적으로 해결하므로 그것 자체는 문제가 아니다. 문제는 is-a 관계가 공개 표면과 동적 디스패치를 통해 Adaptee의 내부 가정까지 끌어들인다는 점이다. "상속보다 합성"의 전형적 사례다.

리팩터링 문제 2. 두 온도 센서

스마트 온실 컨트롤러가 구형 센서(LegacyThermo, 화씨, read_f())와 신형 센서(NewThermo, 섭씨, get_celsius())를 섞어 쓴다. 아래 코드를 어댑터로 리팩터링하라. 두 센서 라이브러리는 수정할 수 없다. Target 메서드 이름을 무엇으로 정할지도 근거와 함께 결정하라.

def average_celsius(sensors):
    # 센서 종류마다 분기한다 — 새 센서가 오면 이 함수를 또 연다
    values = []
    for s in sensors:
        if isinstance(s, LegacyThermo):
            # 구형은 화씨라 변환이 필요하다
            values.append((s.read_f() - 32) * 5 / 9)
        elif isinstance(s, NewThermo):
            values.append(s.get_celsius())
        else:
            raise TypeError(f"모르는 센서: {s!r}")
    return sum(values) / len(values)

def max_celsius(sensors):
    # 같은 분기가 여기에도 복제되어 있다
    return max((s.read_f() - 32) * 5 / 9 if isinstance(s, LegacyThermo)
               else s.get_celsius() for s in sensors)
해설 보기

Target을 CelsiusSource Protocol(get_celsius() -> float)로 정하고, 모양이 다른 구형 센서에만 LegacyThermoAdapter를 단다. 신형 센서는 Protocol 덕분에 어댑터 없이 그대로 Target이다. 단위(섭씨)를 인터페이스 계약에 포함시킨 것이 핵심이다. 원래 코드의 위험은 대부분 "이 숫자의 단위가 무엇이냐"에서 나왔다.

Target 이름에 대해서는 두 답이 모두 옳을 수 있다. 신형 센서의 이름을 따르면 어댑터가 하나로 줄어든다. 반면 temperature_c()처럼 중립적인 이름을 정하면 두 센서 모두 어댑터가 필요하지만 Target이 특정 벤더에 끌려가지 않는다. 벤더가 자주 바뀌는 환경이라면 후자가 낫다.

흔한 오답: LegacyThermo를 상속해 get_celsius()를 추가하는 것. 이는 클래스 어댑터이며, 센서 객체를 라이브러리가 생성해 돌려주는 경우(팩토리 함수 등)에는 아예 쓸 수 없다. 이미 만들어진 객체를 감쌀 수 있다는 것이 객체 어댑터의 실용적 장점이다.

해설 코드의 클라이언트 함수는 매개변수 타입을 Iterable로 적었다. 이터러블은 for 문으로 처음부터 순회할 수 있는 객체(리스트, 튜플 등)를 말하며, 센서를 리스트로만 받겠다고 못 박지 않으려는 선택이다.

판단 문제 3. 이름만 다를 때

새로 계약한 PG사 D의 SDK는 make_payment(amount_krw, token) -> str, cancel_payment(tid, amount_krw) -> None이다. 우리 PaymentGateway와 이름만 다르고 인자 순서·단위·반환·예외는 완전히 같다. (가) 클래스 어댑터, (나) __getattr__ 위임, (다) 명시적 얇은 어댑터 클래스 또는 함수 중 무엇을 택하겠는가? 정산 배치처럼 함수 하나만 필요한 클라이언트라면 답이 달라지는가?

해설 보기

(다)가 답이다. 위임할 메서드가 두 개뿐이라 (가)와 (나)가 아껴 주는 보일러플레이트(본질적 로직 없이 형식 때문에 반복해 쓰는 상투적 코드)는 거의 없는 반면, 공개 표면이 pay/refund로 정확히 고정되는 이점은 크다. 무엇보다 지금 "의미가 같다"는 것은 지금의 사실일 뿐이다. D가 다음 버전에서 예외 방식을 바꾸면 (다)에서는 두 메서드에 번역을 추가하면 되지만, (가)나 (나)로 시작했다면 구조를 갈아엎어야 한다.

(나)는 특히 이 상황에 맞지 않는다. 이름이 다르기 때문에 pay → make_payment 매핑은 어차피 손으로 써야 하고, __getattr__은 그 외의 SDK 속성(예: debug_dump)만 새게 만든다. (가)는 연습문제 1의 문제를 모두 갖는다.

함수 하나만 필요한 클라이언트라면 바운드 메서드 client.make_payment 자체가 어댑터다. 바운드 메서드는 인스턴스에 묶인 메서드 객체로, 호출하면 self가 자동으로 채워진다. Target이 Callable[[int, str], str]이고 모양이 이미 맞으므로 아무것도 만들 필요가 없다. 파이썬에서 "어댑터가 필요 없어지는" 가장 흔한 경우다.
