데코레이터 (Decorator)

같은 인터페이스를 유지한 채 책임을 겹겹이 덧입히기

학습 목표

  1. 같은 인터페이스를 유지하며 책임을 동적으로 덧붙이는 데코레이터를 구현하고, 서브클래스 폭발(조합 수만큼 클래스)을 피하는 원리를 설명할 수 있다.
  2. 데코레이터 체인의 순서가 의미를 바꾼다는 점(압축→암호화 vs 암호화→압축)을 분석할 수 있다.
  3. GoF 데코레이터 패턴과 파이썬 @decorator 문법의 관계(겹치는 부분과 다른 부분)를 정확히 구분할 수 있다.

1. 상황

스마트 농장 스타트업 '들빛팜'은 비닐하우스마다 토양 수분 센서를 꽂고, 하우스 한쪽에 있는 게이트웨이가 측정값을 모아 클라우드의 MQTT 브로커로 올린다. 게이트웨이는 현장 센서들의 값을 모아 클라우드로 중계하는 장치이고, MQTT는 IoT에서 많이 쓰는 가벼운 메시징 프로토콜이며, 브로커는 발행된 메시지를 받아 구독자에게 나눠 주는 서버다. 이렇게 원격 장치가 측정값을 자동으로 수집해 보내는 데이터를 텔레메트리라 한다. 임베디드 개발자 준호가 만든 첫 버전은 단순했다. MqttChannel.send(payload)가 JSON 한 줄을 받아 브로커에 publish한다(페이로드는 메시지에서 헤더 등을 뺀, 실제로 전달하는 데이터다).

석 달 뒤 청구서가 왔다. 게이트웨이는 LTE 모뎀으로 통신하는데, 측정값 한 건이 60바이트 남짓이어도 하우스 300동에서 10초마다 보내니 데이터 요금이 만만치 않았다. 영업팀은 "압축해 주세요"라고 했다. 같은 주에 대형 납품처 한 곳이 보안 감사를 이유로 "전송 데이터는 암호화돼야 한다"고 요구했다. 다른 농장들은 암호화가 필요 없었고, 저사양 게이트웨이는 암호화 연산이 부담스러웠다.

요구는 계속 쌓였다. 태양광으로 버티는 외곽 하우스는 모뎀을 켜는 횟수를 줄여야 해서 "10건씩 모아서 보내기"(배치)가 필요했고(배치는 여러 건을 모아 한 번에 보내는 것이다. 모아 두는 임시 공간을 버퍼, 버퍼에 남은 것을 모두 내보내는 연산을 flush라 한다), 현장 장애를 추적하던 운영팀은 "몇 바이트를 언제 보냈는지 로그를 남겨 달라"고 했다. 결정적으로 현장 설치 기사들이 "농장마다 조합을 설정 파일로 바꾸게 해 달라"고 요청했다. 어떤 농장은 배치+압축, 어떤 농장은 압축+암호화+로그, 어떤 농장은 로그만.

준호는 처음에 기능 조합마다 서브클래스를 만들다가, CompressedEncryptedBatchedMqttChannel이라는 이름을 쓰는 순간 손을 멈췄다. 기능이 넷이면 조합은 열여섯이다. 다음으로 하나의 send()에 플래그를 넣었는데, 이번에는 다른 문제가 생겼다. 테스트를 모두 통과한 리팩터링 이후 한 농장의 데이터 요금이 여섯 배로 뛰었다. 누군가 압축 블록과 암호화 블록의 줄 순서를 바꾼 것이다. "압축은 반드시 암호화보다 먼저"라는 규칙이 코드 어디에도 명시되어 있지 않았다.

2. 순진한 설계와 그 한계

준호가 거친 두 시도를 함께 재현한다. (A)는 기능 조합을 상속 계층으로, (B)는 플래그로 표현한다. 둘은 정반대 방향의 실패다. (A)는 클래스가 너무 많고, (B)는 한 클래스가 너무 많이 안다.

용어

아래 코드가 쓰는 도구들이다. zlib: DEFLATE 알고리즘으로 데이터를 압축·해제하는 파이썬 표준 모듈. json.dumps: 파이썬 객체를 JSON 문자열로 바꾸는 함수. 스트림 암호: 키로부터 만든 무작위처럼 보이는 바이트열(키스트림)을 평문과 XOR해 암호화하는 방식으로, 출력이 무작위처럼 보여 압축되지 않는다. 이 장의 toy_encrypt는 교육용이며, 실제 제품에서는 AES-GCM(AES 암호를 GCM 모드로 써서 암호화와 변조 검증을 함께 제공하는 표준 방식. 메시지마다 nonce라는 일회용 값과 인증 태그가 붙는다) 같은 검증된 방식을 쓴다.

CompressedEncryptedMqttChannel에서 순서를 맞추느라 부모를 건너뛰고 압축 로직을 복제하는 부분, 그리고 FlagMqttChannel.send()에서 순서 규칙이 '줄 순서'에만 숨어 있는 부분에 주목하라.

두 방식의 결함은 이렇게 정리된다.

  • 상속 방식은 '조합'을 '타입'으로 표현한다. 기능 n개의 모든 부분집합이 클래스가 되므로 2n개가 필요하고, 출력 [1]처럼 기능 넷이면 열여섯이다. 게다가 상속은 컴파일 시점에 고정되므로(컴파일은 소스를 실행 가능한 형태로 번역하는 단계이며, 파이썬에서는 클래스 정의문이 실행되는 시점이 이에 해당한다) "설정 파일로 조합을 바꾸자"는 요구를 근본적으로 충족할 수 없다. 순서를 바꾸고 싶으면 계층을 다시 짜야 한다.
  • 플래그 방식은 모든 기능이 한 메서드를 공유한다. 새 기능은 기존 메서드를 열어야 하고(OCP 위반), 배치·압축·암호화·로그라는 서로 무관한 이유로 같은 메서드가 바뀐다(SRP 위반). 무엇보다 처리 순서가 if 블록의 물리적 순서에 암묵적으로 들어 있다. 출력 [3]은 정상으로 보이지만, 두 블록을 맞바꿔도 기능 테스트는 통과하고 크기만 조용히 커진다.
  • 둘 다 위치를 바꿀 수 없다. "로그를 압축 전 크기로 찍고 싶다"는 요구가 오면 상속 방식은 새 클래스, 플래그 방식은 새 플래그가 필요하다.

필요한 것은 "기능 하나 = 부품 하나"이고, 부품을 런타임에, 원하는 순서로 꽂을 수 있는 구조다.

3. 패턴의 구조

GoF의 의도는 이렇다. "객체에 추가적인 책임을 동적으로 부여한다. 데코레이터는 기능 확장을 위해 서브클래스를 만드는 것에 대한 유연한 대안이다." '동적으로'와 '서브클래스의 대안'이 핵심이다. 조합을 클래스로 고정하는 대신, 같은 인터페이스를 가진 래퍼를 객체 수준에서 겹쳐 쌓는다.

역할이 장의 클래스책임
ComponentChannel실제 객체와 래퍼가 공유하는 인터페이스.
Concrete ComponentMqttChannel핵심 기능(실제 전송).
DecoratorChannelDecoratorComponent를 하나 감싸고, 기본으로 모든 요청을 위임한다.
Concrete DecoratorCompressingChannel 등위임 전후에 책임 하나를 덧붙인다.

그림에서 가장 중요한 것은 ChannelDecorator에서 나가는 두 화살표다. 위로 향하는 상속(빈 삼각형)은 타입을 맞추기 위한 것이다. 래퍼가 Channel이므로 다른 래퍼가 또 감쌀 수 있고, 클라이언트는 차이를 모른다. 오른쪽의 합성(_inner)은 기능을 재사용하기 위한 것이다. 상속 방식의 실패는 이 둘을 하나의 상속으로 해결하려 한 데서 왔다. 데코레이터는 둘을 분리한다.

객체 그래프로 보면 데코레이터 체인은 '자식이 하나뿐인 트리', 즉 연결 리스트다. 다음 장의 컴포지트가 자식을 여럿 가진 같은 구조라는 점을 기억해 두라.

4. 패턴 적용

준호는 기능 하나를 래퍼 클래스 하나로 만들고, 모든 래퍼가 같은 Channel 인터페이스를 지키도록 했다. 설계 중 하나의 결정이 따로 필요했다. 배치 래퍼는 내부에 데이터를 쥐고 있으므로, 게이트웨이가 종료될 때 "남은 것을 내보내라"는 신호가 체인 끝까지 전달되어야 한다. 그래서 flush()를 인터페이스에 올렸다.

먼저 Component, Concrete Component, 그리고 위임만 하는 Decorator 기반 클래스다. ChannelDecorator의 docstring이 설명하는 'is-a와 has-a의 동시 성립'과, flush() 위임을 빠뜨리면 생기는 일에 대한 주석을 읽어라.

ChannelDecorator는 아무 기능도 추가하지 않는다. 그 존재 이유는 "모든 메서드의 기본 위임"을 한 번만 쓰는 데 있다. 인터페이스 메서드가 둘뿐이라 이득이 작아 보이지만, 메서드가 다섯 개라면 구체 데코레이터마다 다섯 개의 위임 메서드를 반복해야 한다. 이 기반 클래스를 생략하는 것도 정당한 선택이지만, 그때는 위임 누락이 가장 흔한 버그가 된다.

이제 기능 넷이 각각 하나의 구체 데코레이터가 된다. 압축과 암호화는 데이터를 바꾸는 '전처리형', 로그는 관찰만 하는 '관찰형', 배치는 상태를 가진 '버퍼형'이다. BatchingChannel.flush()에서 자기 버퍼를 먼저 비우고 위임하는 순서가 왜 중요한지 docstring을 보라.

각 클래스는 자기 기능 하나만 안다. CompressingChannel은 zlib만, EncryptingChannel은 키와 암호화 함수만 안다. 새 기능(예: 전송 실패 시 재시도)이 필요해도 기존 클래스는 하나도 열지 않는다. 래퍼 클래스를 하나 추가하면 끝이다.

마지막으로 조립과 실행이다. farm_a를 조립하는 중첩 표현식을 바깥에서 안쪽으로 읽으면 그것이 곧 처리 순서다. 로그 래퍼가 두 위치에 꽂혀 '압축 전'과 '압축 후' 크기를 동시에 보여 준다는 점, 그리고 데모 [3]의 두 순서 비교에 주목하라.

출력 [1]에서 25건이 10+10+5로 나뉘어 나갔다. 마지막 5건은 collect() 끝의 flush()가 바깥 배치 래퍼에서 출발해 체인을 타고 내려간 결과다. 로그 두 줄은 같은 클래스의 두 인스턴스가 체인의 다른 위치에서 각각 629바이트(원본)와 104바이트(압축 후)를 관찰했음을 보여 준다. 플래그 방식으로는 할 수 없던 일이다.

출력 [3]이 이 장의 두 번째 학습 목표다. 같은 두 래퍼를 순서만 바꿔 감쌌더니 104바이트와 640바이트가 되었다. 원본(629바이트)보다도 커졌다. 암호화의 출력은 무작위처럼 보이므로 압축기가 찾을 반복 패턴이 없고, 압축 헤더만큼 오히려 늘어난다. 데코레이터들은 서로를 모르지만, 그것들이 함께 내는 결과는 순서에 의존한다. 이것은 패턴의 결함이 아니라 본질이다. 순서가 의미를 갖는다면 그 규칙은 어딘가에 명시되어야 한다. 조립 코드에 주석으로, 설정 검증 로직으로, 혹은 아예 "압축+암호화"를 하나의 데코레이터로 묶어서 말이다.

함정: 객체 정체성

데코레이터로 감싼 객체는 원래 객체와 다른 객체다. farm_a is mqtt는 거짓이고, 원래 객체의 참조를 들고 있던 코드는 래퍼를 우회해 직접 mqtt.send()를 부를 수 있다. 데코레이터가 보안 기능(암호화)을 담당한다면 "원본 참조가 새어 나가지 않는가"를 반드시 점검해야 한다. 이것이 9장의 프록시가 실제 객체의 생성까지 통제하려 하는 이유 중 하나다.

5. 파이썬다운 변형

펌웨어 팀 선배 미정이 준호의 코드를 보고 물었다. "send 하나짜리 인터페이스면 그냥 함수를 감싸면 되잖아. 파이썬엔 @ 데코레이터도 있고." 맞는 말이다. 그런데 이 질문에는 이 장에서 가장 자주 혼동되는 문제가 숨어 있다. 파이썬의 @decorator와 GoF의 데코레이터 패턴은 같은 것인가? (@ 데코레이터 문법은 함수·클래스 정의 위에 @이름을 붙여, 정의 직후 그것을 그 이름의 호출 가능 객체에 넘기고 반환값으로 원래 이름을 다시 묶는 파이썬 문법이다.)

함수 래퍼로 같은 의도를 구현하기

파일 03_pythonic.py의 첫 부분이다. Send = Callable[[bytes], None]이 Component 역할을 하고, compressed·encrypted·logged가 각각 Send를 받아 Send를 돌려준다. 설정이 필요한 래퍼(encrypted(key))가 왜 한 겹 더 감싸진 '팩토리'가 되는지 보라.

용어

문법 설탕: 새 기능을 더하지 않고 기존 표현을 짧고 읽기 좋게 쓰게 해 주는 문법. functools.wraps: 래퍼 함수가 원래 함수의 __name__·__doc__을 물려받고 __wrapped__로 원본에 닿게 해 주는 도구. functools.reduce: 두 값을 받는 함수를 목록에 왼쪽부터 차례로 적용해 하나의 값으로 접는 함수. @property: 메서드를 속성처럼 읽게(필요하면 대입하게) 만드는 표기. 투명성: 감싼 객체가 원래 객체와 똑같이 보여서, 쓰는 쪽이 차이를 알 수도 알 필요도 없는 성질.

함수 버전도 GoF의 의도를 그대로 만족한다. 래퍼는 감싼 것과 같은 시그니처(같은 '인터페이스')를 가지고, 책임 하나를 덧붙이며, 몇 겹이든 중첩된다. 클래스 버전의 생성자 인자(key)는 함수 버전에서 바깥 클로저로 옮겨간다. functools.wraps는 래퍼가 원래 함수의 __name__·__doc__을 물려받고 __wrapped__로 원본에 닿을 수 있게 해, 디버깅과 내성(introspection), 즉 실행 중에 객체의 이름·타입·문서 등을 조사하는 일에서 래퍼를 투명하게 만든다.

그러나 함수 버전은 BatchingChannel을 깔끔하게 표현하지 못한다. 배치는 send와 flush 두 연산이 하나의 버퍼를 공유해야 하는데, 함수는 호출 진입점이 하나뿐이다. 클로저에 버퍼를 숨기고 wrapper.flush = ... 같은 속성을 붙일 수는 있지만, 그때 우리는 클래스를 어설프게 다시 만드는 셈이다. 인터페이스가 메서드 하나면 함수, 둘 이상이거나 상태를 공유하면 클래스가 실용적 기준이다.

@ 문법: 정의 시점의 이름 재바인딩

다음 부분은 같은 래퍼를 @ 문법으로 적용한 경우와, @를 쓰지만 아무것도 감싸지 않는 register를 나란히 보여 준다.

@logged("debug")와 @compressed를 쌓은 정의는 정확히 send_to_debug_port = logged("debug")(compressed(send_to_debug_port))다. 아래쪽 데코레이터가 먼저 적용되어 안쪽이 되고, 호출 시에는 위에서 아래로 실행된다. 이 점에서 @ 체인과 객체 체인은 순서 규칙까지 같다.

하지만 register를 보라. 이것도 @로 쓰지만 함수를 감싸지 않는다. 레지스트리에 넣고 원본을 그대로 돌려줄 뿐이다. @property는 함수를 디스크립터 객체(__get__/__set__을 구현해 클래스 속성 접근을 가로채는 객체)로 바꾸고, @dataclass는 클래스에 메서드를 생성해 넣으며, Flask(파이썬 경량 웹 프레임워크)의 @app.route는 URL과 핸들러 함수를 등록한다. 이들 중 어느 것도 "같은 인터페이스로 책임을 덧붙인다"는 GoF 데코레이터가 아니다.

GoF 데코레이터와 @decorator: 같은 이름, 다른 범주

이제 관계를 정확히 말할 수 있다. GoF 데코레이터는 설계 의도(패턴)이고, 파이썬 @decorator는 언어 문법(메커니즘)이다. @는 "정의 직후 그 함수/클래스를 어떤 호출 가능 객체에 넘기고, 결과로 이름을 다시 묶는다"는 설탕일 뿐, 결과가 무엇이어야 하는지는 강제하지 않는다. 이 이름의 혼동은 파이썬 커뮤니티도 인지하고 있었다. @ 문법을 도입한 PEP 318(PEP는 파이썬 언어·표준 라이브러리 변경을 제안하고 기록하는 공식 문서다)은 'decorator'라는 이름이 GoF 책의 용법과 일치하지 않는다는 비판이 있었음을 스스로 기록하고 있다.

관점GoF 데코레이터 패턴파이썬 @decorator 문법
정체설계 의도: 같은 인터페이스로 책임을 동적으로 추가언어 메커니즘: f = deco(f)의 문법 설탕
적용 대상객체(인스턴스마다 다르게 감쌀 수 있음)함수/클래스 정의(그 이름 전체에 적용)
적용 시점런타임, 조립 코드가 원하는 때정의 시점(대개 모듈 임포트 시), 한 번
원본 접근원본 객체 참조는 그대로 남아 있다이름이 래퍼로 다시 묶여 원본은 __wrapped__로만 닿는다
인터페이스 보존필수(패턴의 정의)선택(@property, @register처럼 안 지켜도 됨)
겹치는 영역@wraps를 쓰고 시그니처를 유지하며 책임 하나를 덧붙이는 함수 데코레이터(@logged, 재시도, 계측 등)는 GoF 의도를 함수 수준에서 구현한 것이다.

표의 '적용 시점'이 실무에서 가장 큰 차이를 만든다. 들빛팜의 요구는 "설치 기사가 설정 파일로 조합을 바꾼다"였다. @는 소스 코드에 순서를 박아 넣으므로 이 요구를 충족하지 못한다. 그러나 @라는 문법을 버리고 데코레이터 '함수'만 취하면 런타임 조립이 가능하다.

설정 파일의 문자열 목록을 래퍼 함수로 매핑하고, functools.reduce로 접어 체인을 만드는 부분이다. 목록을 왜 reversed로 뒤집는지 docstring을 확인하라.

이것이 GoF 패턴의 '동적' 성질을 함수로 구현한 형태다. 문자열 → 래퍼 매핑(DECORATORS)이 일종의 플러그인 레지스트리 역할을 하므로, 새 기능은 함수 하나와 딕셔너리 항목 하나로 추가된다.

메서드가 많을 때: __getattr__ 위임의 함정

마지막 부분은 반대 방향의 문제다. 실제 MQTT 클라이언트처럼 메서드가 많은 객체를 감쌀 때, 가로챌 메서드만 정의하고 나머지는 __getattr__로 넘겨 겉으로는 원본과 같아 보이게 만든 투명 래퍼를 만들면 어떻게 되는지 본다.

출력 [4]가 핵심이다. w.connect() 같은 일반 메서드는 잘 위임되지만, len(w)와 with w:는 실패한다. 파이썬은 __len__, __enter__ 같은 특수 메서드를 인스턴스가 아니라 타입에서 직접 찾기 때문에 인스턴스 수준의 __getattr__을 거치지 않는다. 또 래퍼는 MqttClient를 상속하지 않으므로 isinstance 검사도 실패한다. "같은 인터페이스"를 약속하는 데코레이터에게 이것은 치명적이다. 감싼 객체를 with 문에 쓰던 코드가 래퍼를 끼우는 순간 깨진다. 해결책은 필요한 특수 메서드를 래퍼 클래스에 명시적으로 정의하거나, 인터페이스를 ABC/Protocol로 좁혀 위임 목록을 명확히 하는 것이다.

6. 트레이드오프와 관련 패턴

얻는 것과 치르는 것

  • 얻는 것: 기능 수에 선형인 클래스 수(2n → n), 런타임 조합, 기능별 단일 책임, 기존 코드 수정 없는 확장.
  • 치르는 것: 작은 객체가 많아지고 디버깅 시 호출 스택이 깊어진다. 스택 트레이스에 send가 다섯 번 찍히면 어느 층에서 문제가 났는지 찾기 어렵다. 순서 의존성이 조립 코드로 옮겨갈 뿐 사라지지 않는다. 그리고 래퍼는 원본과 다른 객체이므로 정체성(is) 비교나 구체 타입 검사가 깨진다.

쓰지 말아야 할 때

  • 조합이 고정되어 있을 때. 모든 농장이 항상 "압축+암호화"만 쓴다면 래퍼 둘을 조립하는 유연성은 쓸모가 없다. send() 안에서 두 줄로 끝내는 편이 읽기 쉽다.
  • 덧붙이는 책임이 감싼 객체의 내부 상태를 알아야 할 때. 데코레이터는 공개 인터페이스만 볼 수 있다. 내부에 손을 대야 한다면 그것은 '바깥에서 덧입히기'가 아니라 '속을 바꾸기'이므로, 전략 패턴(10장)으로 내부 알고리즘을 교체하는 편이 맞다. GoF의 표현을 빌리면 데코레이터는 객체의 '껍질'을, 전략은 '속'을 바꾼다.
  • 인터페이스가 넓을 때. 메서드가 스무 개인 인터페이스를 감싸면 모든 래퍼가 스무 개 메서드를 위임해야 한다. 위 함정처럼 __getattr__로 줄이면 투명성이 깨진다. 감쌀 인터페이스를 먼저 좁혀라.
  • 순서 조합 중 대부분이 무의미할 때. 압축과 암호화처럼 '맞는 순서가 하나뿐'인 조합이 많다면, 순서 자유도는 실수할 자유일 뿐이다. 하나의 데코레이터로 묶거나 조립 시점에 순서를 검증하라.

관련 패턴

패턴관계
프록시(9장)구조는 거의 같다(같은 인터페이스로 감싸고 위임). 차이는 의도다. 데코레이터는 책임을 추가하며 클라이언트가 조합을 정하고, 프록시는 접근을 통제하며 흔히 실제 객체의 생성·생명주기(객체가 만들어져 쓰이다가 해제되기까지의 전 과정)까지 관리한다.

7. 연습문제

개념 문제 1. 순서가 바뀐 체인

배치(10건)를 가장 바깥에 두고, 그 안에서 압축과 암호화를 (가) 압축→암호화, (나) 암호화→압축 순서로 감싼 두 체인에 측정값 100건을 보낸다. 각각의 총 전송 크기를 실행으로 확인하고, 차이가 나는 이유를 정보 이론적 관점에서 한두 문장으로 설명하라. 추가로, 배치를 압축 안쪽으로 옮기면(건별 압축 후 묶음) 어떻게 되는지도 예측하고 확인하라.

해설 보기

압축은 데이터 안의 반복(중복성), 즉 되풀이되는 부분을 찾아 짧은 참조로 바꾸는 일이다. 센서 JSON은 "sensor": "soil-07" 같은 반복이 많아 잘 압축된다. 반면 좋은 암호문은 무작위 바이트와 구별되지 않아야 하므로 중복성이 사라진다. 그래서 암호화 뒤에 압축하면 줄일 것이 없고, 압축 포맷의 헤더·체크섬(데이터 손상을 확인하려고 붙이는 짧은 검증 값)만큼 오히려 커진다(아래 출력에서 원본 대비 103%).

배치 위치도 같은 원리다. 압축기는 한 번에 보는 데이터가 클수록 반복을 많이 찾는다. 62바이트짜리 측정값 하나만 압축하면 반복이 거의 없어 헤더 비용만 붙지만, 10건을 묶은 뒤 압축하면 건 사이의 반복을 활용한다.

흔한 오답: "암호화가 데이터를 늘리기 때문"이라는 답. 이 예제의 스트림 암호는 길이를 바꾸지 않는다(실제 AES-GCM은 nonce·태그 몇십 바이트를 붙일 뿐이다). 차이의 원인은 길이가 아니라 압축 가능성이다.

리팩터링 문제 2. 플래그 인자 Notifier

들빛팜 관리 앱의 알림 모듈이다. 호출부마다 플래그 조합이 다르고, "로그를 재시도마다 찍을지 최종 결과만 찍을지"를 고를 수 없다. 데코레이터 체인으로 바꿔라. 원래 계약(send는 성공 여부를 bool로 반환)은 유지한다. 코드의 호출 제한은 일정 시간 안의 호출 횟수를 제한해 과도한 요청을 막는 기능이고, time.monotonic()은 시스템 시각 조정에 영향받지 않고 늘어나기만 하는 시계 값(초)을 돌려주어 경과 시간을 재는 데 쓴다.

class Notifier:
    def __init__(self, sms_api):
        self._sms_api = sms_api
        self._last = 0.0                     # 마지막 전송 시각(호출 제한용)

    def send(self, msg, *, with_retry=False, with_log=False, with_rate_limit=False):
        if with_rate_limit:                  # 1초에 한 번만
            now = time.monotonic()
            if now - self._last < 1.0:
                return False
            self._last = now
        if with_log:
            print("send:", msg)
        attempts = 3 if with_retry else 1    # 재시도 횟수가 하드코딩
        for i in range(attempts):
            try:
                self._sms_api.post(msg)
                return True
            except ConnectionError:
                if with_log:                 # 로그 플래그가 재시도 로직 안까지 침투
                    print("retry", i)
        return False
해설 보기

플래그 셋을 RetryingNotifier, LoggingNotifier, RateLimitingNotifier로 분리하고, SMS 호출은 SmsNotifier(Concrete Component)로 둔다. 원래 코드에서 '로그 플래그가 재시도 루프 안까지 침투'했던 문제는 LoggingNotifier를 체인의 어느 위치에 두느냐로 해결된다. 아래 데모처럼 재시도 바깥과 안쪽에 하나씩 두면 시도별 로그와 최종 결과 로그를 동시에 얻는다. 하드코딩된 재시도 횟수 3은 래퍼의 생성자 인자가 되었고, time.monotonic은 시계 함수 주입으로 바뀌어 테스트가 실제로 기다리지 않아도 된다.

순서에도 의미가 있다. 호출 제한을 재시도 바깥에 둬야 "사용자 요청 1회"를 기준으로 제한한다. 안쪽에 두면 재시도 자체가 제한에 걸려, 첫 실패 후 재시도가 모두 차단된다.

흔한 오답: LoggingNotifier가 ConnectionError를 잡아서 False를 반환하게 만드는 것. 그러면 안쪽에 놓인 로그 래퍼가 예외를 삼켜 바깥의 재시도 래퍼가 실패를 알아채지 못한다. 관찰형 데코레이터는 흐름을 바꾸지 말아야 하므로 기록 후 다시 던진다.

판단 문제 3. 인증을 어디에 붙일까

들빛팜 웹 콘솔에 인증 확인을 붙인다. 대부분의 화면은 로그인이 필요하고 /health는 공개다. 관수 밸브 리소스는 조회(GET)는 공개, 제어(POST)는 인증이 필요하다. (A) 핸들러 함수마다 @login_required, (B) 앱 전체에 미들웨어 리스트(미들웨어는 모든 요청이 핸들러에 닿기 전후로 거치도록 줄지어 놓은 처리 단계다), (C) GoF 데코레이터 객체 중 무엇이 적합한지, 각각이 GoF 데코레이터 의도와 어떤 관계인지 판단하라.

해설 보기

세 방법 모두 "같은 호출 모양을 유지한 채 책임(인증)을 덧붙인다"는 점에서 데코레이터 의도를 구현한다. 차이는 적용 범위를 어디서 결정하고, 기본값이 무엇이냐다.

  • 보안의 기본값이 중요한 '대부분 보호' 요구에는 (B) 미들웨어가 맞다. 새 엔드포인트(요청을 받는 개별 URL 경로와 그 처리기)가 자동으로 보호되고(secure by default: 명시적으로 예외를 두지 않는 한 기본값이 '보호됨'이 되게 하는 원칙), 예외는 화이트리스트로 한 곳에서 관리된다. (A)는 @를 깜빡하는 순간 공개되므로, 보안처럼 "빠뜨리면 사고"인 책임에는 위험하다. 미들웨어 리스트는 사실상 reduce로 조립한 데코레이터 체인이다.
  • (A) 함수 @decorator는 '일부만' 적용하는 책임(예: 특정 화면만 관리자 권한, 특정 API만 캐싱)에 좋다. 핸들러 정의 바로 위에서 정책이 보이는 지역성이 장점이다.
  • (C) 객체 데코레이터는 밸브 리소스처럼 인터페이스가 메서드 여러 개이고 메서드마다 정책이 다를 때 자연스럽다. 함수 하나를 감싸는 방식으로는 "GET은 통과, POST만 검사"를 표현하기 어색하다.

따라서 실무 답은 조합이다. 전체 인증은 (B), 밸브 제어는 (C), 화면별 추가 권한은 (A). 흔한 오답: "파이썬이니까 무조건 @". 문법의 편의가 아니라 '빠뜨렸을 때 무슨 일이 생기는가'로 판단해야 한다.

해설 코드의 Resource는 REST 리소스를 흉내 낸다. REST 방식 웹 API에서 URL로 식별되고 GET·POST 같은 HTTP 메서드로 조작되는 대상을 말한다.
