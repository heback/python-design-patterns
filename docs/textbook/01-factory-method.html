팩토리 메서드 (Factory Method)

'언제 만들지'는 프레임워크가, '무엇을 만들지'는 하위 클래스가

학습 목표

  1. 상위 클래스가 객체를 언제 만들지 정하고, 하위 클래스가 무엇을 만들지 정하는 역할 분담을 설명할 수 있다.
  2. 단순 팩토리(조건문으로 고르는 함수)와 팩토리 메서드(하위 클래스가 오버라이드하는 생성 메서드)를 구별하고, 새 종류를 추가할 때 누가 코드를 고치는지 비교할 수 있다.
  3. 파이썬의 생성 함수 넘기기, classmethod 대체 생성자, __init_subclass__ 자동 등록으로 같은 목적을 이루고, 각각이 GoF 원래 의도와 얼마나 다른지 판단할 수 있다.
핵심 한 줄 새 제품을 추가할 때 기존 클래스를 고쳐야 한다면 아직 패턴이 아니다. 하위 클래스를 추가하는 것만으로 끝나야 팩토리 메서드다.

1. 상황

화학과 박사과정생 서윤은 실험 자동화를 맡았다. 연구실의 UV-Vis 분광광도계(빛으로 시료를 재는 장비)가 측정을 마치면 결과 파일이 나온다. 서윤은 AcquisitionJob 클래스를 만들고 run() 하나에 "읽기 → 정규화 → 저장"을 넣었다. 정규화는 장비마다 다른 세기 단위를 비교하려고 최댓값을 1.0에 맞추는 일이다.

질량분석기(또 다른 분석 장비)가 들어왔고, 케이블 포트로 연결하는 신형 장비도 왔다. 장비마다 출력 형식이 다르다. 서윤은 run() 안에 if device == … 분기를 붙였다. 신형 장비에만 필요한 port 인자는 모든 작업의 생성자에 붙었다.

그다음 학과가 이 코드를 다섯 연구실의 공용 프레임워크로 삼았다. 프레임워크는 전체 흐름을 쥐고, 각 연구실의 코드를 정해진 자리에서 불러 주는 공용 골격이다. 옆 연구실이 새 장비를 붙이려 하자 공용 run()의 분기를 고쳐 달라고 요청해야 했다. 정규화 로직만 단위 테스트(작은 단위를 실제 장비 없이 따로 검증하는 테스트)하려던 학생은 가짜 리더를 끼울 자리를 찾지 못했다.

흐름은 모든 장비에 같다. 변하는 것은 "어떤 리더를 만드는가" 하나뿐인데, 그 결정이 흐름 한가운데 박혀 있다.

2. 순진한 설계와 그 한계

서윤이 분기를 붙인 직후의 코드다. 리더는 장비가 내보낸 글자를 읽어 숫자로 바꿔 주는 클래스다(이런 코드를 파서라고도 부른다). 리더들 자체는 멀쩡하다. 눈여겨볼 곳은 __init__의 port, run() 맨 앞의 if 목록, 그리고 데모 [3]이다. 데모 [3]은 테스트를 하려고 진짜 리더 이름 CsvSpectrumReader가 가짜 리더를 가리키도록 몰래 바꿔 놓았다가, 끝나면 원래대로 되돌린다. 이렇게 이름을 바꿔 끼우는 데 쓴 globals()는 이 파일에서 쓰는 이름표(클래스·함수 이름)와 그 대상을 모아 둔 목록을 돌려주는 함수라서, 여기에 다른 값을 넣으면 같은 이름표가 다른 클래스를 가리키게 된다. 파이썬 개발자들은 이렇게 실행 중에 이름이 가리키는 대상을 몰래 바꿔 끼우는 일을 몽키패치(monkeypatch)라고 부른다.

데모 [1]은 잘 돈다. 문제는 변경 때 드러난다.

  • 확장할 자리가 공용 코드 안에만 있다. 데모 [2]처럼 옆 연구실은 자기 장비인 X선 회절계(XRD)(결정 구조를 재는 장비)를 누구보다 잘 안다. 그런데 그 장비를 연결할 곳이 남이 관리하는 공용 run()의 if 목록뿐이다.
  • 장비마다 다른 설정이 모두에게 번진다. 신형 장비만 쓰는 port가 모든 작업에 따라붙는다.
  • 테스트용 가짜를 끼울 이음새가 없다. 이음새는 코드를 고치지 않고도 다른 것을 끼워 넣을 수 있는 자리다. 테스트 중에는 실제 장비 대신 가짜 리더를 쓰고 싶은데, run()이 CsvSpectrumReader라는 진짜 클래스의 이름을 직접 적어 두어서 가짜를 넣을 자리가 없다. 그래서 데모 [3]처럼 이름표를 몰래 바꿔 놓고 테스트가 끝나면 되돌려야 한다. 되돌리는 것을 잊으면 같은 이름을 쓰는 다른 코드도 가짜를 쓰게 된다.
흔한 첫 시도 분기를 make_reader(device) 함수로 빼면 run()은 깔끔해진다. 이것을 단순 팩토리(Simple Factory)라 한다. 그러나 새 장비를 넣으려면 여전히 그 함수를 고쳐야 한다. 생성 코드를 옮겼을 뿐, 고칠 권한은 여전히 공용 코드 주인에게 있다.

3. 패턴의 구조

GoF가 쓴 의도는 이렇다. "객체를 생성하기 위한 인터페이스를 정의하되, 어떤 클래스의 인스턴스를 만들지는 서브클래스가 결정하게 한다. 팩토리 메서드는 클래스의 인스턴스화를 서브클래스로 미룬다." 핵심은 미룬다이다. 생성은 여전히 상위 클래스의 흐름 안에서 일어난다. 상위 클래스는 만드는 시점을, 하위 클래스는 만들 대상을 안다.

역할이 장의 클래스하는 일
제품(Product)Reader흐름이 의존하는 추상 타입
구체 제품(Concrete Product)CsvSpectrumReader 등장비 하나의 형식을 읽는다
생성자(Creator)AcquisitionJob흐름 run()을 갖고, 그 안에서 create_reader()를 부른다
구체 생성자(Concrete Creator)UvVisJob 등create_reader()를 오버라이드해 무엇을 만들지 정한다

장비가 하나 늘면 작업 클래스와 리더 클래스가 하나씩 함께 는다. 두 계층이 나란히 자라는 이 모양을 평행 클래스 계층이라 부른다. 팩토리 메서드의 대표적인 결과이자 비용이다.

4. 패턴 적용

run()에서 "리더를 만든다"는 한 단계만 떼어 추상 메서드 create_reader()로 만들었다. 이 메서드가 팩토리 메서드다. 장비별 작업 클래스가 이것을 오버라이드한다. 아래쪽 "옆 연구실의 코드" 구획이 위쪽 공용 코드를 한 줄이라도 고치는지 확인하며 읽어라. 데모 [3]의 assert는 조건이 거짓이면 AssertionError를 내는 확인 문장이다. python -O로 실행하면 통째로 사라지므로 테스트 확인에만 쓰고 입력 검사에는 쓰지 않는다.

어디를 보면 되는가.

  • run() 본문에 구체 리더 이름이 하나도 없다. if 사슬은 "어떤 작업 클래스를 만드는가"라는 선택으로 바뀌었다. if 사슬은 닫힌 목록이지만 하위 클래스는 열린 목록이다.
  • port는 그것이 필요한 SerialJsonJob으로 옮겨 갔다. super().__init__()을 부른 뒤에 직접 보관한다.
  • 데모 [2]의 XrdJob은 추가만으로 생겼다. 확장할 지식을 가진 쪽이 자기 코드 안에서 확장을 끝낸다(OCP).
  • 데모 [3]의 FakeJob은 공식으로 열린 자리 create_reader()로 들어온다. 이음새가 설계의 일부가 되었다.

5. 파이썬다운 변형

패턴 코드의 UvVisJob은 create_reader() 한 줄만 한다. 파이썬에서는 클래스도 함수처럼 부를 수 있다. 그렇다면 하위 클래스 대신 "만드는 방법"을 값으로 넘기면 된다.

생성 함수 넘기기와 대체 생성자

아래 코드는 reader_factory 인자로 만드는 방법을 받는다. 두 가지 도구가 새로 나온다. functools.partial은 함수의 인자 일부를 미리 채운 새 함수를 만든다. 대체 생성자는 같은 클래스를 다른 입력(예: 설정 dict)에서 만드는 이름 붙은 생성 진입점이다. 파이썬에서는 보통 @classmethod로 만든다. 이 장식을 붙인 메서드는 인스턴스 대신 클래스 자체를 첫 인자 cls로 받는다. 데모 [3]에서 리더가 언제 만들어지는지 보라.

데모 [3]이 중요하다. 리더는 run()이 불릴 때 비로소 만들어진다. 인스턴스를 바로 넘겼다면 만드는 시점을 호출자가 정해 버렸을 것이다. 모양은 10장의 전략 패턴과 같다. 상속 대신 합성을 쓴 것이다.

데모 [4]의 from_config()는 흔히 "팩토리 메서드"라 불리지만 GoF의 팩토리 메서드가 아니다. 무엇을 만들지 정하는 것이 하위 클래스가 아니라 설정 데이터이고, 속은 표를 찾는 단순 팩토리다. 그래서 새 장비 "xrd"를 붙이려면 결국 DEVICES 표를 고쳐야 한다.

정의하는 순간 등록되는 레지스트리

레지스트리는 이름과 클래스를 짝지어 둔 등록부다. 호출자는 분기 대신 이 표를 찾는다. 표를 공용 코드가 쥐지 않게 하려면, 클래스가 스스로 등록하면 된다. 아래 코드는 __init_subclass__로 class XrdReader(Reader, device="xrd")가 정의되는 순간 등록되게 한다. 등록부에 오르는 것이 리더(제품)라는 점을 기억하라. 타입 힌트의 ClassVar는 그 속성이 인스턴스가 아니라 클래스 전체에 속한다는 표시이고, Any는 어떤 타입이든 허용한다는 표시다.

데모 [2]와 [3]을 비교하라. 공용 코드는 한 글자도 안 바뀌었는데 장비 목록이 늘었다. 대가는 데모 [4]다. 등록은 모듈을 import할 때 일어나는 부수 효과, 곧 값을 돌려주는 것 말고 바깥 상태를 바꾸는 일에 기댄다. 아무도 그 모듈을 import하지 않으면 코드가 있는데도 장비가 "없다".

6. 트레이드오프와 관련 패턴

얻는 것.

  • 흐름을 가진 코드가 구체 클래스를 모른다(DIP).
  • 새 제품은 하위 클래스 추가로 끝난다(OCP). 생성 인자도 그것을 아는 클래스로 모인다.
  • 테스트용 이음새가 설계의 일부로 생긴다.
이 패턴을 쓰지 말아야 할 때
  • 종류가 닫혀 있고 고치는 사람이 내부 팀뿐일 때. 장비가 둘뿐이고 늘 계획이 없다면 단순 팩토리 함수가 더 읽기 쉽다.
  • 변하는 것이 생성 하나뿐일 때. 메서드 한 줄을 위해 하위 클래스를 만든다면, 파이썬에서는 생성 함수를 넘기는 편이 싸다.
  • 흐름을 가진 상위 클래스가 없을 때. 그냥 객체를 만들어 주는 함수가 필요하다면 그것은 팩토리 함수다. 패턴 이름을 붙이려고 추상 클래스를 만들지 않는다.

헷갈리는 패턴과의 차이.

  • 추상 팩토리(2장): 팩토리 메서드는 제품 하나의 생성을 미루고, 추상 팩토리는 함께 쓰는 제품 여러 개의 생성을 한 객체에 묶는다.
  • 템플릿 메서드(14장): run()은 템플릿 메서드이고, 그 한 단계가 마침 "생성"인 경우가 팩토리 메서드다.

7. 연습문제

개념 문제 1. 표준 라이브러리의 "팩토리 메서드"

datetime.fromtimestamp()와 dict.fromkeys()는 문서와 블로그에서 흔히 팩토리 메서드라 불린다. GoF의 의도("어떤 클래스의 인스턴스를 만들지는 서브클래스가 결정한다")를 기준으로 이 둘이 GoF 팩토리 메서드인지 판별하라. 하위 클래스에서 이 메서드를 호출하면 무엇이 반환되는지 실험해 보고, 그 결과가 판별에 어떤 영향을 주는지도 논하라.

해설 보기

둘 다 GoF 팩토리 메서드가 아니라 대체 생성자다. 판별 근거는 두 가지다. 첫째, 만들 클래스는 호출자가 수신 클래스(Cls.method()에서 점 앞에 온 클래스, 곧 @classmethod의 cls로 전달되는 클래스)를 고르는 순간 정해진다. datetime.fromtimestamp(...)라고 쓴 코드는 이미 "datetime을 달라"고 말했다. 프레임워크의 흐름이 훅을 부르고 하위 클래스가 답하는 간접층이 없다. 둘째, 생성된 객체를 사용하는 Creator 쪽 연산(패턴 코드의 run())이 없다. 이 메서드들의 목적은 "같은 타입을 다른 입력 형식에서 만들기", 즉 생성자 오버로딩이 없는 파이썬에서 이름 붙은 생성자를 제공하는 것이다.

흔한 오답은 "하위 클래스에서 부르면 하위 클래스 인스턴스가 나오니 서브클래스가 결정한다"는 논리다. 아래 실험처럼 실제로 하위 클래스 인스턴스가 나온다. 그러나 그것은 cls를 통해 생성하는 classmethod의 일반적 성질일 뿐, 하위 클래스가 생성 결정을 오버라이드한 결과가 아니다. 결정은 여전히 호출자의 몫이다.

리팩터링 문제 2. 로그 수집기

연구실 서버 관리자가 쓴 다음 로그 수집기를 (1) GoF 팩토리 메서드로, (2) 이어서 __init_subclass__ 레지스트리로 리팩터링하라. 두 번째 단계에서는 "nginx"(널리 쓰이는 웹 서버로, 요청마다 접근 로그를 남긴다), "apache" 같은 설정 문자열로 수집기를 고를 수 있어야 하고, 새 형식은 프레임워크 수정 없이 클래스 정의만으로 추가되어야 한다. 코드의 re.match는 문자열 패턴을 기술하는 작은 언어인 정규식을 다루는 re 모듈 함수이고, 5xx는 웹에서 요청과 응답을 주고받는 프로토콜인 HTTP의 응답 상태 코드(결과를 나타내는 세 자리 숫자) 중 서버 오류(500번대)를 뜻한다.

import re

class LogCollector:
    """웹 서버 접근 로그에서 IP별 5xx 오류 수를 센다."""

    def __init__(self, fmt: str) -> None:
        self.fmt = fmt  # "nginx" 또는 "apache"

    def collect(self, lines: list[str]) -> dict[str, int]:
        errors: dict[str, int] = {}
        for line in lines:
            # 문제: 줄마다 형식 분기 — 흐름과 파싱 결정이 엉켜 있다
            if self.fmt == "nginx":
                m = re.match(r'^(\S+) .*?" (\d{3}) ', line)
                ip, status = m.group(1), int(m.group(2))
            elif self.fmt == "apache":
                status_s, ip, _ = line.split("|")
                status = int(status_s)
            else:
                raise ValueError(self.fmt)
            if status >= 500:
                errors[ip] = errors.get(ip, 0) + 1
        return errors
해설 보기

먼저 변하는 것(한 줄을 해석하는 방법)과 변하지 않는 것(줄을 돌며 5xx를 세는 흐름)을 가른다. 변하는 것을 LogParser 제품 계층으로 빼내고, collect()는 그 안에서 팩토리 메서드 create_parser()를 부른다. 원래 코드는 줄마다 분기했지만 이제 파서는 collect() 시작 시 한 번 만들어진다. 생성 시점이 흐름 안에 명확히 자리 잡은 것이다. 데모의 nginx 로그 줄에 보이는 GET·POST는 HTTP 요청의 동작 종류(GET은 조회, POST는 생성·변경)다.

2단계에서는 Product가 아니라 Concrete Creator를 등록했다. 본문 레지스트리 변형은 리더(Product)를 등록했다. 어느 쪽이든 된다. 판단 기준은 "설정 문자열이 고르는 단위가 무엇인가"다. 형식마다 수집 흐름의 다른 단계까지 바뀔 가능성이 있다면 Creator를 등록하는 편이 낫다.

흔한 오답은 create_parser() 안에 if self.fmt == ...를 그대로 옮기는 것이다. 메서드 이름은 팩토리 메서드지만 하위 클래스가 결정하지 않으므로 단순 팩토리를 메서드로 옮긴 것에 불과하다. 또 하나 따져 볼 변형은 __init__에서 self.parser = self.create_parser()로 파서를 미리 만들어 두는 것이다. 오버라이드는 그대로 동작하므로 하위 클래스로 바꿔 끼우는 데는 문제가 없다. 진짜 함정은 두 가지다. 첫째, 생성자에서 팩토리 메서드를 부르면 하위 클래스가 super().__init__() 뒤에 설정하는 상태가 아직 없다. 본문의 SerialJsonJob처럼 port를 super().__init__() 다음에 저장하는 하위 클래스라면 create_reader()가 AttributeError를 낸다. 둘째, 생성 시점이 "실행할 때"에서 "객체를 만들 때"로 당겨진다. 장비 연결처럼 생성이 비싸거나 부수 효과가 있으면, 실행되지 않을 작업까지 자원을 잡는다(본문 파이썬다운 변형 데모 [3]이 지킨 성질이다).

판단 문제 3. 장비가 두 종류뿐이라면

서윤의 연구실만 쓰는 프레임워크이고 장비는 UV-Vis와 질량분석기 두 종류뿐이다. 앞으로 늘릴 계획도 없다. 이때 단순 팩토리 함수(make_reader(device))와 팩토리 메서드 중 무엇을 고르겠는가? (a) 확장 주체가 내부 팀인가 외부 연구실인가, (b) 테스트 용이성, 두 관점에서 근거를 들어 논하라. 상황이 어떻게 바뀌면 결론이 뒤집히는지도 쓰라.

해설 보기

단순 팩토리 함수가 낫다. (a) 확장 주체가 내부 팀뿐이면 "공용 코드를 수정해야 한다"는 비용이 사실상 없다. 고치는 사람과 코드 소유자가 같기 때문이다. 팩토리 메서드의 평행 계층은 제3자가 프레임워크를 수정하지 않고 확장해야 할 때 비용을 회수하는데, 그 전제가 없다. 닫힌 두 갈래 분기는 한 화면에 다 보이는 편이 오히려 읽기 쉽다. (b) 테스트 용이성은 팩토리 메서드만의 장점이 아니다. AcquisitionJob이 생성 함수나 리더를 생성자 인자로 받게 하면(파이썬다운 변형의 방식) 단순 팩토리와 함께 써도 이음새가 생긴다. 즉 "테스트를 위해 팩토리 메서드가 필요하다"는 논리는 성립하지 않는다.

결론이 뒤집히는 조건: 다른 연구실이 같은 코드를 쓰기 시작해 확장 주체가 외부로 넘어갈 때, 또는 장비마다 정규화·저장 같은 다른 단계도 함께 달라져 "생성 + 다른 훅"을 한 단위로 묶어 바꿀 필요가 생길 때다. 앞의 경우는 레지스트리 변형도 후보이고, 뒤의 경우는 패턴 코드처럼 하위 클래스를 두는 방식이 가장 자연스럽다.

흔한 오답은 "나중에 늘 수도 있으니 미리 패턴을 적용한다"이다. 두 갈래 if를 팩토리 메서드로 바꾸는 데는 몇 분이면 충분하다. 바꾸는 비용이 낮은 결정을 미리 내려 두는 것은 YAGNI("You Aren't Gonna Need It": 실제로 필요해지기 전에는 기능이나 추상화를 미리 만들지 말라는 원칙) 위반이고, 그동안 모든 독자가 불필요한 간접층을 읽는 비용을 치른다.
