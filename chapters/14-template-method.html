학습 목표

  • 알고리즘의 골격을 상위 클래스에 고정하고 달라지는 단계만 하위 클래스에 맡길 수 있다. 추상 단계와 훅을 구분할 수 있다.
  • "골격이 단계를 부른다"는 할리우드 원칙이 이 패턴에서 어떻게 나타나는지 설명할 수 있다.
  • 상속(템플릿 메서드)과 단계 주입(전략) 가운데 무엇이 맞는지 판단할 수 있다.
핵심 한 줄 같은 절차가 여러 사본으로 복사되어 순서가 어긋나기 시작하면, 순서는 한 곳에 닫고 다른 단계만 연다.

1. 상황

코딩 교육 플랫폼 '코드랩'의 개발자 도윤은 파이썬 채점기를 만들었다. 제출된 코드를 샌드박스(다른 시스템과 격리된 실행 공간)에 넣고, 실행하고, 시간을 재고, 출력을 정답과 비교하고, 샌드박스를 치운다.

C++와 Java 과목이 열리자 도윤은 파이썬 채점기를 복사해 C++ 채점기를, 그것을 다시 복사해 Java 채점기를 만들었다. 그 뒤 "모든 언어에 정리 단계 추가" 같은 요구가 올 때마다 세 곳을 고쳤고, 두 군데가 어긋났다. Java 채점기는 정리를 빠뜨려 서버 디스크를 채웠다. C++ 채점기는 누군가 비교와 시간 검사의 순서를 바꿔 놓았다. 그래서 같은 '느린 오답'이 파이썬에서는 TLE(Time Limit Exceeded, 시간 초과), C++에서는 WA(Wrong Answer, 오답)가 되었다. 학생들이 항의했다.

2. 순진한 설계와 그 한계

세 채점기가 함께 있던 시점의 코드다. 실제 채점기는 time.perf_counter(짧은 구간의 경과 시간을 재는 정밀한 시계)로 시간을 재지만, 여기서는 실행과 시간을 흉내만 낸다. 판정 문자열에는 TLE·WA 말고도 AC(Accepted, 통과)와 CE(Compile Error, 컴파일 실패, 곧 소스 코드를 실행할 수 있는 형태로 옮기는 데 실패함)가 있다. 세 judge()를 나란히 놓고 어디가 같고 어디가 미묘하게 다른지 찾아보라.


  
실행하면 데모 [1]에서 같은 제출물이 언어에 따라 TLE와 WA로 갈리고, 데모 [2]에서 Java 샌드박스가 남는다.

  
    
    
  • 절차와 단계가 한 덩어리로 복사되었다. 정말 다른 부분은 컴파일·클래스 이름 검사 정도인데, 나머지까지 모두 사본이다.
    • 
    
  • 공통 요구 하나가 수정 세 번이 된다. 하나라도 빠뜨리지 않는다는 보장이 없다.
    • 
    
  • 순서는 지켜야 할 규칙인데 아무도 지키지 않는다. "시간 검사 → 비교"가 각 사본의 선택처럼 보여서 누구든 바꿀 수 있다.
    • 
  






  
3. 패턴의 구조

  
GoF의 의도는 이렇다. "연산 안에 알고리즘의 골격을 정의하고, 일부 단계를 하위 클래스로 미룬다." 요리법 카드와 같다. 순서는 카드에 인쇄되어 있고, "양념: 취향대로" 칸만 비어 있다. 순서는 닫고 단계는 연다.

  
  

    
역할이 장의 요소하는 일

    
      
템플릿 메서드Judge.judge()단계의 순서와 공통 단계(정리, 시간 검사, 판정)를 가진다.

      
추상 단계run언어마다 반드시 다르다. 하위 클래스가 꼭 구현한다.

      
훅(hook)validate, compile, outputs_match기본 동작이 있고, 필요한 하위 클래스만 재정의한다.

      
구체 클래스PythonJudge, CppJudge, JavaJudge다른 부분만 쓴다.

    
  

  
추상 단계와 훅을 가르는 기준은 "합리적인 기본값이 있는가"다. compile의 기본값은 no-op, 곧 아무 일도 하지 않는 구현이다. 컴파일이 없는 인터프리터 언어(파이썬처럼 소스를 읽어 가며 바로 실행하는 언어)에 딱 맞는다. 기본값이 분명한 단계를 추상으로 만들면 하위 클래스마다 뜻 없는 같은 코드, 곧 보일러플레이트가 생긴다. 반대로 기본값이 없는 단계를 훅으로 만들면, 빠뜨린 하위 클래스가 조용히 틀리게 동작한다.

  
흐름의 주인은 골격이다. 하위 클래스는 골격을 부르지 않고, 골격이 하위 클래스를 부른다. 이를 할리우드 원칙("우리에게 전화하지 마라, 우리가 전화하겠다")이라 한다.






  
4. 패턴 적용

  
도윤은 세 사본의 공통 절차를 Judge.judge()로 끌어올렸다. 골격에 붙은 @final은 "재정의하지 말라"고 타입 검사기에 알리는 표시다. 제출물이 실행 중 예외를 내면 골격이 RE(Runtime Error) 판정으로 바꾼다.

  

  
    
    
  • judge()의 반복문: 시간 검사가 비교보다 먼저다. 하위 클래스는 단계의 내용만 바꾸고 순서는 못 바꾼다. 데모 [1]에서 느린 오답은 모든 언어에서 TLE다.
    • 
    
  • finally: 정리는 골격이 보장한다. 데모 [3]에서 남은 샌드박스가 없다.
    • 
    
  • CompileError: 훅은 예외를 던지기만 하고, CE로 바꾸는 일은 골격이 한다(데모 [2]).
    • 
    
  • GoJudge: run을 빠뜨리면 객체를 만들 때 바로 거부된다(데모 [4]). @final은 실행 중에는 아무것도 막지 않으니, 지켜야 할 것은 abstractmethod로 지킨다.
    • 
  

  
그런데 부동소수 문제에 '오차 허용 비교'가 필요해지면 어떻게 될까? 오차 허용은 언어가 아니라 문제의 속성이다. 상속으로 하면 FloatTolerantCppJudge, FloatTolerantJavaJudge…처럼 클래스가 언어 수 × 비교 방식 수로 곱해진다.






  
5. 파이썬다운 변형

  
서로 따로 바뀌는 요구의 방향을 변경 축이라 한다. 여기서는 "언어"와 "비교 방식"이 두 축이다. 파이썬에서는 단계가 그냥 함수일 수 있으므로, 축마다 단계를 골라 주입하면 된다. 10장의 전략 패턴이다.

  
아래 코드에서 언어 축은 단계 묶음 Toolchain(한 언어의 컴파일·실행 도구 묶음)이, 비교 축은 함수 하나인 Checker(실제 출력과 정답을 받아 일치 여부를 돌려주는 함수)가 맡는다. judge()의 순서가 패턴 코드와 같다는 점을 보라.

  

  
    
    
  • 얻는 것: 데모 [1]처럼 클래스를 더하지 않고 언어 × 비교 방식을 조합한다. 문제마다 실행 중에 체커를 고를 수도 있다.
    • 
    
  • 잃는 것: None을 허용한 단계는 빠뜨림이 조용히 기본값이 된다. 데모 [2]에서 compile을 깜빡한 C++가 빈 소스를 통과시킨다. 상속이라면 단계끼리 self로 나누던 값도 인자로 넘겨야 한다.
    •

7. 연습문제


  

    
개념 문제 1. 추상 단계, 훅, 그리고 훅이 너무 많을 때

    
(a) 패턴 코드의 Judge에서 run()은 추상 단계이고 compile()은 훅이다. 둘을 바꾸면, 곧 run()을 기본 no-op 훅으로 하고 compile()을 추상으로 하면 각각 어떤 문제가 생기는가? (b) 팀원이 before_compile, after_compile, before_each_test, after_each_test, on_tle, on_wa, should_skip_test 같은 훅 일곱 개를 추가하자고 제안한다. 무엇이 걱정되는가?

    

      해설 보기
      
(a) run()을 no-op 훅으로 만들면, 구현을 빠뜨린 채점기가 빈 출력을 내고 모든 제출물을 WA로 판정한다. 실패가 조용히, 잘못된 결과로 드러난다. 기본값이 의미 없는 단계는 추상이어야 하며, 그래야 인스턴스화 시점에 크게 실패한다. 반대로 compile()을 추상으로 만들면, 인터프리터 언어 채점기마다 def compile(...): pass라는 보일러플레이트가 생긴다. 기본값이 분명한 단계는 훅이어야 한다.

      
(b) 훅 하나하나는 골격이 하위 클래스에게 하는 약속이다. "이 시점에, 이런 상태로, 한 번 부르겠다"는 약속이다. 훅이 일곱 개가 되면 하위 클래스 작성자는 after_each_test가 TLE일 때도 불리는지, should_skip_test가 True면 before_each_test는 불리는지 같은 질문에 답하려고 골격 코드를 읽어야 한다. 골격의 내부 순서가 사실상 공개 API가 되어 버리고, 이후 골격을 리팩터링할 자유도 사라진다. 흔한 오답은 "훅이 많을수록 확장성이 좋다"이다. 확장 지점은 많을수록 골격이 굳는다. 대안은 제안된 훅이 실제로 해결하려는 요구를 묻는 것이다. 대개는 로깅이나 지표 수집이며, 이런 요구는 옵저버(11장)로 골격 밖에 두거나 골격을 더 작은 템플릿 둘로 쪼개는 편이 낫다.

    

  


  

    
리팩터링 문제 2. 리포트 생성기 세 개

    
코드랩 운영팀은 주간 채점 통계를 CSV, JSON, XML(태그로 구조를 표현하는 텍스트 데이터 형식)로 내려받는다. 아래 코드를 템플릿 메서드로 바꿔라. 원래 코드에 숨어 있는 형식 간 불일치 하나를 찾고, 리팩터링이 그것을 어떻게 구조적으로 막는지 설명하라.

    
class CsvReport:
    def generate(self):
        rows = [r for r in db.rows() if not r["deleted"]]   # 조회(삭제 문제 제외)
        lines = ["problem,submissions,ac_rate"]              # 머리말
        lines += [f"{r['problem']},{r['submissions']},{r['ac_rate']}" for r in rows]
        return storage.save("\n".join(lines))                # 저장

class JsonReport:
    def generate(self):
        rows = db.rows()                                     # 조회 — 필터가 빠졌다?
        body = ",\n".join(f'  {{"problem": "{r["problem"]}"}}' for r in rows)
        return storage.save("[\n" + body + "\n]")            # 머리말·꼬리말·저장

class XmlReport:
    def generate(self):
        rows = [r for r in db.rows() if not r["deleted"]]
        lines = ["<report>"]                                 # 머리말
        lines += [f'  <row problem="{r["problem"]}"/>' for r in rows]
        lines.append("</report>")                            # 꼬리말
        return storage.save("\n".join(lines))

    

      해설 보기
      
불일치는 JsonReport의 조회 단계에 삭제 필터가 없다는 점이다. 같은 주간 통계인데 JSON에만 테스트용 문제가 섞인다. 리팩터링한 뒤에는 조회(fetch)와 저장(save)이 @final 공통 단계가 된다. 하위 클래스는 필터를 쓸 기회 자체가 없으므로, 빠뜨릴 수도 없다.

      
단계는 이렇게 분류했다. 행 서식은 모든 형식에 필요하고 기본값이 없으므로 추상 단계다. 머리말과 꼬리말은 CSV에 꼬리말이 없듯 없을 수도 있으므로 빈 문자열을 기본값으로 하는 훅이다. 행 구분자는 메서드가 아니라 클래스 속성(separator)으로 열었다. 값 하나를 바꾸려고 메서드를 재정의하게 하는 것은 과하기 때문이다. 흔한 오답은 generate() 전체를 추상으로 두고 "공통 헬퍼"만 상위 클래스에 두는 것이다. 그러면 순서와 필터 적용 여부가 다시 하위 클래스의 선택이 되어, 원래 문제가 그대로 남는다.

      

    

  


  

    
판단 문제 3. 상속인가, 주입인가

    
코드랩이 다음 학기에 Go, Rust, Kotlin을 추가하고, 문제 출제자가 웹 화면에서 "출력 비교 방식"(정확 일치/오차 허용/순서 무관/출제자 체커 스크립트)을 고르게 하려 한다. 패턴 코드(템플릿 메서드)와 전략 버전(단계 주입) 가운데 어느 것을 기반으로 삼겠는가? 선택한 쪽에서 잃는 것을 어떻게 보완하겠는가?

    

      해설 보기
      
전략 버전(단계 주입)을 택한다. 결정적인 근거는 두 가지다. 첫째, 비교 방식은 출제자가 실행 중에 고르는 값이다. 클래스 정의 시점에 고정되는 상속으로는 표현할 수 없다. 둘째, 언어 6개 × 비교 방식 4개를 상속으로 표현하면 클래스가 24개 필요하다. 합성이라면 Toolchain 6개와 체커 함수 4개로 충분하다.

      
다만 언어 축 안에서는 템플릿 메서드가 여전히 유효할 수 있다. 컴파일 언어들(C++, Go, Rust, Kotlin)은 "컴파일 → 산출물 확인 → 실행"이라는 하위 골격을 공유한다. 그래서 Toolchain을 추상 클래스로 만들고 CompiledToolchain이 그 하위 골격을 템플릿 메서드로 가지는 혼합형이 현실적이다. 이렇게 하면 기본 구현을 상속하고, 컴파일 단계를 클래스 단위로 강제할 수 있다. 전략 버전의 None 훅에서는 컴파일 단계를 빠뜨려도 조용히 넘어갔다. 시그니처 오류는 어느 쪽이든 타입 검사로 잡는다. 흔한 오답은 둘 중 하나만 고르는 것이다. 축마다 따로 판단하라. 실행 중에 고르는 축은 합성으로, 정적이고 단계를 많이 공유하는 축은 상속으로 다룬다.

    

  


  

    
확장 문제 4. 모든 언어에 메모리 제한 추가

    
"리스트에 10만 개를 쌓는 풀이가 채점 서버를 죽였다." 모든 언어에 메모리 제한(MLE, Memory Limit Exceeded 판정)을 추가하라. 판정 규칙(한도를 넘으면 MLE, 비교보다 먼저)은 모든 언어에서 같아야 하지만, 측정 방법은 언어 런타임마다 다를 수 있다. 무엇을 골격에 넣고 무엇을 훅으로 열겠는가?

    

      해설 보기
      
판정은 골격에, 측정은 훅에 둔다. 테스트 루프에 "실행 → 시간 검사 → 메모리 검사 → 출력 비교"를 고정하고, 측정은 기본 구현(파이썬 메모리 할당을 추적해 최대 사용량을 재는 표준 라이브러리 tracemalloc)이 있는 measure() 훅으로 연다. PythonJudge는 아무것도 고치지 않고 메모리 제한을 얻는다. JavaJudge는 측정 방식만 재정의하며, MLE 판정 규칙에는 손댈 수 없다. 순진한 코드의 복붙 구조였다면 세 파일을 고쳐야 했고 순서가 또 어긋났을 것이다.

      
흔한 오답은 측정과 판정을 함께 훅(check_memory()가 판정 문자열을 반환)으로 여는 것이다. 그러면 언어마다 한도 비교 방식이 달라질 수 있고(이상인가 초과인가), 시간 검사와의 순서도 하위 클래스가 정하게 된다. 공정성 규칙은 골격 밖으로 내보내지 않는다.

      
해설 코드 주석의 용어 몇 가지: 실제 채점기는 cgroup이나 setrlimit(운영체제가 프로세스의 메모리·CPU 사용량을 제한하는 수단)로 메모리를 막는다. JVM(Java Virtual Machine)은 자바 바이트코드를 실행하는 가상 머신이고, 힙은 실행 중 동적으로 할당되는 객체가 놓이는 메모리 영역이다. JVM은 힙을 미리 잡아 두므로 측정 방식이 파이썬과 달라진다.
