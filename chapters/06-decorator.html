학습 목표

  1. 같은 인터페이스를 지키며 기능을 하나씩 덧붙이는 데코레이터를 만들고, 조합마다 서브클래스가 늘어나는 문제를 어떻게 피하는지 설명할 수 있다.
  2. 감싸는 순서가 결과를 바꾼다는 점(압축→암호화 vs 암호화→압축)을 설명할 수 있다.
  3. GoF 데코레이터 패턴과 파이썬 @decorator 문법이 어디서 겹치고 어디서 다른지 구분할 수 있다.
핵심 한 줄 기능을 켜고 끄는 조합이 많고, 그 조합을 실행 중에 바꿔야 한다면 기능 하나를 래퍼 하나로 만들어 겹쳐 쌓는다.
처음이라면 이 그림부터 선물을 포장한다고 하자. 선물을 비닐로 싸고, 상자에 넣고, 리본을 묶는다. 어느 단계에서든 겉모습이 어떻든 그것은 여전히 "건넬 수 있는 선물"이다. 겹마다 하는 일은 하나뿐이고, 상자 없이 리본만 묶을 수도 있다. 다만 순서가 있다. 리본을 먼저 묶고 상자에 넣으면 리본이 눌려 버린다. 데코레이터가 이것이다. 같은 모양을 유지한 채, 겹 하나가 기능 하나를 맡아 필요한 만큼 순서대로 쌓는다. 아래 농장 이야기는 이 그림을 코드로 옮긴 것이다.

1. 상황

스마트 농장 '들빛팜'은 비닐하우스마다 토양 수분 센서를 꽂고, 측정값을 인터넷 너머 서버로 올린다. 받는 쪽은 MQTT 브로커다. MQTT는 작은 기기들이 많이 쓰는 가벼운 메시지 전송 규약이고, 브로커는 받은 메시지를 필요한 곳에 나눠 주는 서버다. 개발자 준호의 첫 버전은 MqttChannel.send(payload) 하나였다. 페이로드는 실제로 보내는 데이터 부분이다.

요구가 쌓였다. 통신 요금 때문에 압축, 보안 감사 때문에 암호화, 배터리 때문에 배치(묶어 보내기), 장애 추적 때문에 전송 로그. 배치는 10건을 모아 한 번에 보내는 것이고, 모아 둔 것을 모두 내보내는 연산을 flush라 한다. 농장마다 필요한 조합도 달라서, 설치 기사는 조합을 설정 파일로 바꾸고 싶어 했다.

준호는 조합마다 서브클래스를 만들다가 CompressedEncryptedBatchedMqttChannel이라는 이름에서 멈췄다. 기능이 넷이면 조합은 열여섯이다. 다음엔 send()에 플래그를 넣었다. 그런데 어느 날 한 농장의 통신 요금이 여섯 배로 뛰었다. 누군가 압축 줄과 암호화 줄의 순서를 바꾼 것이다. "압축은 암호화보다 먼저"라는 규칙이 코드 어디에도 드러나 있지 않았다.

4. 패턴 적용


기능 넷이 각각 구체 데코레이터 하나가 된다. 압축·암호화는 데이터를 바꾸고, 로그는 보기만 하는 '관찰형'이며, 배치는 버퍼를 가진다. 맨 아래 조립 부분의 중첩을 바깥에서 안쪽으로 읽으면 그것이 처리 순서다. 코드에 처음 나오는 모양을 미리 읽어 두자. self._size, self._buffer = size, []는 두 변수에 한 줄로 대입하는 것이다(_size = size, _buffer = []). super().__init__(inner)는 부모(ChannelDecorator)의 생성자를 불러 _inner를 채운다. 데모 [2]의 outer(inner(sink))는 클래스도 변수에 담아 함수처럼 부를 수 있다는 점을 쓴다. 괄호가 겹친 조립 코드는 만들어지는 순서는 안쪽부터, 데이터가 지나는 순서는 바깥부터다.

쓰는 쪽은 자기가 받은 것이 맨 채널인지 다섯 겹 감싼 채널인지 모른다. 이렇게 감싼 객체가 원래 객체와 똑같이 보여 쓰는 쪽이 차이를 알 필요가 없는 성질을 투명성이라 한다. 래퍼들은 서로를 모르지만 함께 내는 결과는 순서에 달려 있다. 순서가 중요하면 그 규칙을 조립 코드의 주석이나 설정 검사로 드러내야 한다. 또 감싼 객체는 원래 객체와 다른 객체라서, 원래 mqtt를 들고 있는 코드는 래퍼를 건너뛸 수 있다.


왜 래퍼를 겹칠까? 플래그나 서브클래스면 안 될까? 플래그는 기능이 늘 때마다 send() 한 메서드를 고치게 하고, 순서가 줄 순서에 숨는다. 서브클래스는 조합마다 클래스가 필요해 기능이 넷이면 열여섯이 된다(2절). 래퍼는 기능마다 클래스 하나이고 조합은 끼우는 순서로 정해 클래스가 늘지 않는다. 한편 ChannelDecorator가 Channel을 상속하면서 Channel을 또 하나 갖는 것이 헷갈릴 수 있다. 상속은 "나도 Channel이다"(그래서 다른 래퍼가 나를 감쌀 수 있다), 필드는 "안쪽에 Channel이 하나 있다"(그래서 일을 넘긴다)로 역할이 다르다.







5. 파이썬다운 변형


선배 미정이 물었다. "send 하나짜리면 함수를 감싸면 되잖아. 파이썬엔 @도 있고."


4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 기능 하나를 겹 하나로 만들어 순서대로 쌓는 것이다. 4절은 클래스로 한다. send와 flush 두 메서드가 있고, 배치처럼 상태(버퍼)를 가진 래퍼도 된다. 5절은 함수로 한다. 함수를 받아 함수를 돌려주므로 메서드 하나짜리에만 맞고, 상태가 필요하면 클래스로 돌아간다. 또 @는 "정의 순간에 한 번 감싸 고정하는" 문법이라 실행 중에 조합을 바꾸는 4절의 장점과는 다르다.


아래 코드는 (1) Send 함수 타입을 Component로 삼은 함수 래퍼, (2) @ 문법, (3) 설정 목록으로 실행 중에 체인을 만드는 build_chain()을 차례로 보여 준다. @ 문법은 함수 정의 위에 @이름을 붙이면 정의 직후 그 함수를 넘겨 받은 결과로 이름을 다시 묶는 파이썬 문법이다. functools.reduce는 두 값을 받는 함수를 목록에 차례로 적용해 하나로 접는 함수다. 타입 힌트부터 읽는 법을 적는다. Send = Callable[[bytes], None]은 "맨 끝이 돌려주는 값(None), 앞 대괄호가 받는 인자 목록(bytes 하나)"이니 바이트를 받아 아무것도 돌려주지 않는 함수다. compressed(send: Send) -> Send는 그런 함수를 받아 같은 모양의 함수를 돌려주므로 몇 겹이든 겹칠 수 있다. logged("debug")처럼 설정이 필요하면 logged가 "래퍼를 만드는 함수"를 돌려주는 한 겹 더 깊은 모양이 된다. @logged("debug") 아래에 @compressed가 있으면 가까운 것부터(압축 먼저, 로그가 바깥) 감싼다.




    
  
  • 함수 래퍼도 GoF의 의도를 그대로 따른다. 같은 모양(Send)을 받아 같은 모양을 돌려주고, 기능 하나를 덧붙이며, 몇 겹이든 겹친다. 다만 배치처럼 send와 flush가 버퍼를 함께 써야 하면 클래스가 낫다. 실무에서는 안쪽 wrapper에 functools.wraps(래퍼가 원래 함수의 이름과 docstring을 물려받게 하는 도구)를 붙인다.
    • 
  
  • @ 문법은 패턴이 아니라 문법이다. 데모 [2]의 debug_send는 정의되는 순간 감싸지고 조합이 소스 코드에 박혀, "설정 파일로 조합을 바꾼다"는 요구에 맞지 않는다. 그럴 때는 데모 [3]처럼 래퍼 함수만 가져와 실행 중에 조립한다. 또 함수를 감싸지 않고 등록만 하는 @도 흔하니, @가 곧 GoF 데코레이터는 아니다.
    •

  1. 시작값은 sink(= mqtt_send)다. 뒤집은 목록은 ["compress", "log"].
    2. 
    
  2. "compress": compressed(mqtt_send)를 만든다.
    3. 
    
  3. "log": logged("config")(위 결과)를 만든다. 최종 체인은 "로그 → 압축 → 전송"이다.
    4. 
    
  4. 이 함수에 데이터를 넣으면 로그가 원본 크기(390바이트)를 찍고, 압축 후 MQTT에 51바이트가 도착한다.

  • 어댑터(5장)는 인터페이스를 바꾸고, 데코레이터는 그대로 둔다. 그래서 데코레이터는 여러 겹 겹친다.
    • 
  
  • 프록시(9장)는 모양이 거의 같지만 목적이 접근 통제다. 데코레이터의 목적은 기능 덧붙이기다.
    • 
  
  • 컴포지트(7장)는 자식을 여럿 가진다. 데코레이터는 자식이 하나뿐인 컴포지트처럼 보인다.
    • 


  
연습문제 전에 알아 둘 말. field(default_factory=…)는 데이터클래스 필드의 기본값을 인스턴스마다 새로 만들게 하는 설정이다. 선언적이란 "어떻게"보다 "무엇을 원하는지"를 적는 방식이다. 헬스 체크는 서비스가 살아 있는지 보려고 주기적으로 보내는 점검 요청이다. 화이트리스트는 허용할 것만 적어 두고 나머지는 모두 거부하는 방식이다.

개념 문제 1. 순서가 바뀐 체인

  
배치(10건)를 가장 바깥에 두고, 그 안에서 압축과 암호화를 (가) 압축→암호화, (나) 암호화→압축 순서로 감싼 두 체인에 측정값 100건을 보낸다. 각각의 총 전송 크기를 실행으로 확인하고, 차이가 나는 이유를 정보 이론적 관점에서 한두 문장으로 설명하라. 추가로, 배치를 압축 안쪽으로 옮기면(건별 압축 후 묶음) 어떻게 되는지도 예측하고 확인하라.

  

    해설 보기
    
압축은 데이터 안의 반복(중복성), 즉 되풀이되는 부분을 찾아 짧은 참조로 바꾸는 일이다. 센서 JSON은 "sensor": "soil-07" 같은 반복이 많아 잘 압축된다. 반면 좋은 암호문은 무작위 바이트와 구별되지 않아야 하므로 중복성이 사라진다. 그래서 암호화 뒤에 압축하면 줄일 것이 없고, 압축 포맷의 헤더·체크섬(데이터 손상을 확인하려고 붙이는 짧은 검증 값)만큼 오히려 커진다(아래 출력에서 원본 대비 103%).

    
배치 위치도 같은 원리다. 압축기는 한 번에 보는 데이터가 클수록 반복을 많이 찾는다. 62바이트짜리 측정값 하나만 압축하면 반복이 거의 없어 헤더 비용만 붙지만, 10건을 묶은 뒤 압축하면 건 사이의 반복을 활용한다.

    
흔한 오답: "암호화가 데이터를 늘리기 때문"이라는 답. 이 예제의 스트림 암호는 길이를 바꾸지 않는다(실제 AES-GCM은 nonce·태그 몇십 바이트를 붙일 뿐이다). 차이의 원인은 길이가 아니라 압축 가능성이다.

    

  






  
리팩터링 문제 2. 플래그 인자 Notifier

  
들빛팜 관리 앱의 알림 모듈이다. 호출부마다 플래그 조합이 다르고, "로그를 재시도마다 찍을지 최종 결과만 찍을지"를 고를 수 없다. 데코레이터 체인으로 바꿔라. 원래 계약(send는 성공 여부를 bool로 반환)은 유지한다. 코드의 호출 제한은 일정 시간 안의 호출 횟수를 제한해 과도한 요청을 막는 기능이고, time.monotonic()은 시스템 시각 조정에 영향받지 않고 늘어나기만 하는 시계 값(초)을 돌려주어 경과 시간을 재는 데 쓴다.


class Notifier:
    def __init__(self, sms_api):
        self._sms_api = sms_api
        self._last = 0.0                     # 마지막 전송 시각(호출 제한용)

    def send(self, msg, *, with_retry=False, with_log=False, with_rate_limit=False):
        if with_rate_limit:                  # 1초에 한 번만
            now = time.monotonic()
            if now - self._last < 1.0:
                return False
            self._last = now
        if with_log:
            print("send:", msg)
        attempts = 3 if with_retry else 1    # 재시도 횟수가 하드코딩
        for i in range(attempts):
            try:
                self._sms_api.post(msg)
                return True
            except ConnectionError:
                if with_log:                 # 로그 플래그가 재시도 로직 안까지 침투
                    print("retry", i)
        return False


  

    해설 보기
    
플래그 셋을 RetryingNotifier, LoggingNotifier, RateLimitingNotifier로 분리하고, SMS 호출은 SmsNotifier(Concrete Component)로 둔다. 원래 코드에서 '로그 플래그가 재시도 루프 안까지 침투'했던 문제는 LoggingNotifier를 체인의 어느 위치에 두느냐로 해결된다. 아래 데모처럼 재시도 바깥과 안쪽에 하나씩 두면 시도별 로그와 최종 결과 로그를 동시에 얻는다. 하드코딩된 재시도 횟수 3은 래퍼의 생성자 인자가 되었고, time.monotonic은 시계 함수 주입으로 바뀌어 테스트가 실제로 기다리지 않아도 된다.

    
순서에도 의미가 있다. 호출 제한을 재시도 바깥에 둬야 "사용자 요청 1회"를 기준으로 제한한다. 안쪽에 두면 재시도 자체가 제한에 걸려, 첫 실패 후 재시도가 모두 차단된다.

    
흔한 오답: LoggingNotifier가 ConnectionError를 잡아서 False를 반환하게 만드는 것. 그러면 안쪽에 놓인 로그 래퍼가 예외를 삼켜 바깥의 재시도 래퍼가 실패를 알아채지 못한다. 관찰형 데코레이터는 흐름을 바꾸지 말아야 하므로 기록 후 다시 던진다.

    

  






  
판단 문제 3. 인증을 어디에 붙일까

  
들빛팜 웹 콘솔에 인증 확인을 붙인다. 대부분의 화면은 로그인이 필요하고 /health는 공개다. 관수 밸브 리소스는 조회(GET)는 공개, 제어(POST)는 인증이 필요하다. (A) 핸들러 함수마다 @login_required, (B) 앱 전체에 미들웨어 리스트(미들웨어는 모든 요청이 핸들러에 닿기 전후로 거치도록 줄지어 놓은 처리 단계다), (C) GoF 데코레이터 객체 중 무엇이 적합한지, 각각이 GoF 데코레이터 의도와 어떤 관계인지 판단하라.

  

    해설 보기
    
세 방법 모두 "같은 호출 모양을 유지한 채 책임(인증)을 덧붙인다"는 점에서 데코레이터 의도를 구현한다. 차이는 적용 범위를 어디서 결정하고, 기본값이 무엇이냐다.

    
    
      
  • 보안의 기본값이 중요한 '대부분 보호' 요구에는 (B) 미들웨어가 맞다. 새 엔드포인트(요청을 받는 개별 URL 경로와 그 처리기)가 자동으로 보호되고(secure by default: 명시적으로 예외를 두지 않는 한 기본값이 '보호됨'이 되게 하는 원칙), 예외는 화이트리스트로 한 곳에서 관리된다. (A)는 @를 깜빡하는 순간 공개되므로, 보안처럼 "빠뜨리면 사고"인 책임에는 위험하다. 미들웨어 리스트는 사실상 reduce로 조립한 데코레이터 체인이다.
    • 
      
  • (A) 함수 @decorator는 '일부만' 적용하는 책임(예: 특정 화면만 관리자 권한, 특정 API만 캐싱)에 좋다. 핸들러 정의 바로 위에서 정책이 보이는 지역성이 장점이다.
    • 
      
  • (C) 객체 데코레이터는 밸브 리소스처럼 인터페이스가 메서드 여러 개이고 메서드마다 정책이 다를 때 자연스럽다. 함수 하나를 감싸는 방식으로는 "GET은 통과, POST만 검사"를 표현하기 어색하다.
    • 
    

    
따라서 실무 답은 조합이다. 전체 인증은 (B), 밸브 제어는 (C), 화면별 추가 권한은 (A). 흔한 오답: "파이썬이니까 무조건 @". 문법의 편의가 아니라 '빠뜨렸을 때 무슨 일이 생기는가'로 판단해야 한다.

    
해설 코드의 Resource는 REST 리소스를 흉내 낸다. REST 방식 웹 API에서 URL로 식별되고 GET·POST 같은 HTTP 메서드로 조작되는 대상을 말한다.
