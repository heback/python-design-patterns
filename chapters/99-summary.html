학습 목표

  1. 모양이 비슷한 패턴들을 "누가 무엇을 결정하는가"로 구별할 수 있다.
  2. 한 시스템에서 변경 축을 세고, 축마다 가장 가벼운 해법을 고르며, 넣지 않은 패턴과 그 이유를 말할 수 있다.
  3. 냄새에서 후보 패턴을 떠올리되 과잉 적용을 걸러 낼 수 있다.
핵심 한 줄 패턴의 수는 설계의 품질이 아니다. 실제로 바뀌는 곳에만, 가장 가벼운 형태로 넣는다.

1. 닮은 패턴 구별하기

전략과 상태, 데코레이터와 프록시는 다이어그램이 거의 같다. 가르는 것은 의도이고, 의도는 질문 하나로 드러난다. 누가 무엇을 결정하는가?

두 쌍을 같은 모양으로 짠 코드다. 로봇의 속도 규칙을 전략과 상태로, 드라이버를 데코레이터와 프록시로 감쌌다. 다음 규칙을 고르는 코드가 어디에 있는지, 진짜 드라이버를 누가 만드는지 보라.



    
  
  • 데모 [1]·[2]: 전략은 바깥(관제 시스템)이 r.rule = careful로 갈아 끼우고, 로봇은 바뀐 줄도 모른다. 상태는 Normal.after_trip()이 배터리를 보고 PowerSave를 돌려준다.
    • 
  
  • 데모 [3]·[4]: 데코레이터는 만든 드라이버를 받는다. 프록시는 진짜 드라이버를 스스로 만들어 연결 시점을 통제하고, 클라이언트는 진짜를 한 번도 갖지 않는다.
    • 



판별 질문 모음



  
닮은 패턴가르는 질문

  
    
전략 / 상태교체를 바깥이 정하나, 상태 객체 스스로 정하나?

    
데코레이터 / 프록시책임을 더하나(조합은 바깥이), 접근을 통제하나(진짜 객체를 흔히 프록시가 만든다)?

    
어댑터 / 데코레이터·프록시인터페이스를 바꾸나, 그대로 두나?

    
퍼사드 / 어댑터여러 객체 위에 새 단순한 인터페이스를 만드나, 이미 정해진 인터페이스에 맞추나?

    
커맨드 / 전략무엇을 할지(요청 자체)인가, 어떻게 할지(같은 일의 다른 방법)인가?

    
템플릿 메서드 / 전략단계를 상속으로 바꾸나, 합성으로 바꾸나? 실행 중에 바꾸거나 축이 둘 이상이면 합성.

    
팩토리 메서드 / 추상 팩토리제품 하나인가, 함께 쓰는 제품 묶음인가?

  








2. 사례 연구: 로봇 창고


2.1 상황


물류 기업 한빛로지스는 창고에 피킹(주문 상품을 칸에서 꺼내 모으는 일) 로봇을 들였다. 개발자 도윤의 WMS(창고 관리 시스템) 프로토타입이 성공하자 여섯 요구가 한꺼번에 왔다.


    
  
  1. 구매팀: 제조사가 둘이 되었다. Acme는 mm 좌표·정수 % 배터리, RoboKo는 칸 이름·0~1 배터리다.
    2. 
  
  2. 운영팀: 유리 구역은 "가까운 칸 먼저" 대신 "구역 순서대로 쓸기" 경로로.
    3. 
  
  3. 고객센터: 출고 전이면 주문을 취소할 수 있게.
    4. 
  
  4. 관제실: 대시보드에 로봇 상태를 실시간으로, 곧 모바일 알림도.
    5. 
  
  5. 재무팀: 재고를 구역·랙(선반 틀)·선반·칸으로 집계. 신축 동은 한 단계 더 깊다.
    6. 
  
  6. 관제실: 배터리가 떨어지면 진행 중인 주문과 엉키지 않게 충전을.
    7. 



요구를 하나씩 WMS 클래스에 분기로 넣다가 사고가 났다. 배터리가 떨어진 로봇이 주문 도중 "충전 시작"으로 기록되고도 피킹을 계속하다 멈췄다. 신입 다온은 열다섯 패턴을 모두 넣은 설계안을 들고 왔다. 도윤은 물었다. "실제로 바뀌는 것이 몇 가지예요?"


2.2 순진한 프로토타입


아픈 곳은 요구마다 하나씩이다. 제조사별 if가 업무 로직 한가운데 있고, 경로도 if 분기다. 주문은 즉시 실행되어 취소할 수 없다. 대시보드를 직접 호출한다. 재고 계층이 4중 반복문에 박혀 있다. 배터리 대응이 진행 중인 주문과 엉킨다. 한 클래스가 바뀔 이유가 여섯이다.


2.3 변경 축을 세고, 축마다 하나씩


서로 다른 이유로 바뀌는 부분을 변경 축이라 하자. 원칙은 "축마다 가장 가벼운 해법 하나, 축이 아닌 곳에는 넣지 않는다"다.



  
변경 축(누가 바꾸나)패턴가장 가벼운 형태

  
    
① 제조사 SDK(구매팀)어댑터Target은 Protocol, 어댑터는 메서드 몇 개짜리 클래스

    
② 경로 알고리즘(운영팀)전략상태 없는 함수 + 이름표 dict

    
③ 주문 대기·취소(고객센터)커맨드되돌리기가 필요 없으니 execute 하나짜리 객체 + 대기열

    
④ 알림 채널(관제실)옵저버듣는 쪽은 그냥 함수로 구독

    
⑤ 재고 계층 깊이(재무팀)컴포지트 + 반복자Group 클래스 하나 + yield from 제너레이터

    
⑥ 배터리 대응(관제실)새 패턴 없음옵저버 + 커맨드 조합: 배터리 사실만 알리고, 듣는 쪽이 충전 명령을 대기열에 넣는다

  



운영 콘솔이 "주문 접수 → 대기열 실행"을 한 번에 부르고 싶다는 별도 요구에는 퍼사드를 두었다. 한 줄씩 넘기기만 하는 통과용 메서드뿐이라면 퍼사드의 가치는 없다.


2.4 조합된 코드


완성된 WMS다. 구획마다 패턴 하나다. 상품을 구별하는 재고 코드 SKU는 코드에서 sku 필드다. 세 곳만 보라. 사실만 알리는 PickOrder.execute(), "왜 바로 충전하지 않는가"를 적은 BatteryGuard, 모든 조립이 모인 build().




    
  
  • 데모 [1]: 깊이가 다른 계층도 walk() 위의 sum 한 줄이다. 단계 추가는 데이터 한 겹이다.
    • 
  
  • 데모 [2]: 주문이 대기열에서 데이터로 기다리므로 취소된다.
    • 
  
  • 데모 [3]: 배터리 사실이 이벤트로 나가고, BatteryGuard가 충전 명령을 대기열 맨 앞에 넣는다. 순서는 "주문 → 충전 → 주문"이 되어 사고가 사라졌다.
    • 
  
  • 데모 [4]: 경로 교체는 조립 때 이름 하나다.
    • 



2.5 넣지 않은 패턴과 그 이유



  
넣지 않은 패턴이 시스템의 사실

  
    
상태상태별로 다른 것이 "작업을 받나" 하나뿐이다. Enum이면 된다.

    
추상 팩토리시뮬레이션과 실환경의 차이는 드라이버 하나, 묶음이 아니다.

    
싱글턴EventHub·TaskQueue는 하나면 충분할 뿐이다. 전역 이벤트 버스(알리는 쪽과 듣는 쪽을 잇는 공용 통로)로 두면 테스트 사이에 구독이 남는다.

    
템플릿 메서드두 명령의 execute()에 공유할 골격이 없다.

    
빌더재고 트리는 build() 안의 리터럴이다. ERP(기업의 재고·회계를 통합 관리하는 시스템)에서 읽어 검증해야 할 때가 빌더의 차례다.

    
데코레이터·프록시덧붙일 책임이나 막을 접근이 아직 요구되지 않았다.

  



평가 기준은 패턴의 수가 아니라 "변경 요구 하나가 몇 곳을 건드리는가"다. 새 제조사는 어댑터 하나, 새 경로는 함수 하나, 새 알림은 구독 한 줄, 새 계층 단계는 데이터 한 겹이다.







3. 자주 쓰이는 조합


3.1 옵저버 + 커맨드: 이벤트가 명령을 만든다


BatteryGuard처럼 듣는 쪽이 일을 직접 하지 않고 명령을 만들어 넘기면 세 가지를 얻는다. 통지가 언제 와도 일은 명령 사이로 미뤄진다. 이벤트가 만든 일도 같은 대기열·기록을 탄다. "30% 미만이면 충전"이라는 정책을 알리는 쪽이 몰라도 된다.


3.2 그 밖의 조합


컴포지트 + 반복자(순회를 제너레이터에), 커맨드 + 컴포지트(명령 묶음), 전략 + 이름표 dict(선택을 한 곳에).







4. 원칙으로 되짚기



  
원칙대표 패턴

  
    
OCP(추가로 확장)팩토리 메서드, 데코레이터, 전략, 옵저버, 커맨드, 상태

    
DIP(추상에 의존)추상 팩토리, 어댑터, 옵저버

    
SRP(바뀔 이유 하나)빌더, 프록시, 퍼사드, 상태

    
합성 우선데코레이터, 전략, 컴포지트, 프록시

  



부딪히는 곳도 있었다. 싱글턴은 클라이언트를 구체 클래스에 묶어 DIP와, 템플릿 메서드는 상속을 데려와 합성 우선과 충돌한다.







5. 파이썬이 흡수한 패턴들



  
흡수 정도패턴 → 파이썬의 수단

  
    
언어의 일부반복자 → for, 제너레이터

    
대부분 함수로전략 → 함수, 옵저버 → 함수 구독

    
다른 수단이 대신싱글턴 → 모듈 객체·조립 지점에서 넘겨주기, 퍼사드 → 모듈 함수, 어댑터 → Protocol

    
일부만 함수로커맨드, 데코레이터, 템플릿 메서드, 팩토리 메서드

    
여전히 클래스 구조상태, 컴포지트

  



흡수되어도 의도는 남는다. 클래스가 다시 필요한 때는 늘 같았다. 행동이 둘 이상이거나, 설정을 바깥에서 보거나 저장해야 하거나, 구현 누락 검사 같은 보장이 필요할 때다.







6. 냄새에서 후보 패턴으로


냄새를 맡으면 패턴을 후보로 떠올리고, 오른쪽 질문으로 먼저 거른다.



  
냄새후보먼저 물을 것

  
    
알고리즘을 고르는 if가 계속 는다전략함수 하나면 되지 않나?

    
같은 상태 분기가 여러 메서드에 반복된다상태다른 것이 데이터뿐인가 → Enum

    
외부 SDK의 어휘가 우리 코드에 샌다어댑터대상이 하나뿐인가 → 얇은 함수

    
알려야 할 곳이 늘어 알리는 쪽 코드가 바뀐다옵저버듣는 쪽이 하나뿐인가 → 콜백 인자

    
요청을 취소·되돌리기·기록해야 한다커맨드셋 다 없는가 → dict[str, 함수]

    
"하나뿐이어야 한다"며 어디서나 꺼내 쓴다(싱글턴 대신) 넘겨주기둘이면 틀리나, 하나면 충분할 뿐인가?

  








7. 패턴 과잉 체크리스트


지금 문제에 필요한 것보다 많은 구조를 미리 넣는 것이 패턴 과잉이다. 패턴을 넣자는 제안이 나오면 차례로 묻는다.


    
  
  1. 변경이 실제로 일어났는가? "나중에 바뀔지도"는 추측이다.
    2. 
  
  2. 구현이 하나뿐인 인터페이스인가? 파이썬에서는 나중에 Protocol을 붙여도 된다.
    3. 
  
  3. 추상화 비용이 변경 비용보다 큰가?
    4. 
  
  4. 언어가 이미 자리를 주는가? key=, 모듈, 제너레이터.
    5. 
  
  5. 이름을 붙이려고 구조를 만들고 있지 않은가?
    6. 
  
  6. 그 패턴이 맡을 변경 축을 한 문장으로 말할 수 있는가? "제조사가 바뀐다 → 어댑터"처럼.
    7. 



반대 실수도 있다. 프로토타입처럼 이미 같은 곳이 서로 다른 이유로 거듭 깨지고 있다면 "아직 이르다"가 아니라 "이미 늦었다"다. 기준은 미래의 추측이 아니라 지금까지의 변경 이력이다.

  
연습문제 전에 알아 둘 말. 취약한 기반 클래스 문제는 상위 클래스의 내부를 조금 바꾸면 그에 기대던 하위 클래스가 깨지는 문제이고, 요요 문제는 상속이 깊어 동작을 이해하려고 위아래 클래스를 계속 오가야 하는 문제다.






  
8. 연습문제


  

    
개념 문제 1. 같은 그림, 네 개의 패턴

    
다음 네 설계는 클래스 다이어그램이 모두 같다. "X는 인터페이스 I를 가진 객체 하나를 필드로 갖고, 자기 연산을 그 객체에 위임한다." 설명만 다르다. 각각이 전략·상태·데코레이터·프록시 중 무엇인지 판별하고, 근거를 "누가 무엇을 결정하는가"로 쓰라.

    
    
      
  1. Conveyor는 Motor를 갖는다. 운영자가 야간에는 QuietMotor, 주간에는 FastMotor를 끼운다. Conveyor는 무엇이 끼워졌는지 모른다.
    2. 
      
  2. Door는 DoorMode를 갖는다. Locked.open()은 거부하고, Unlocked.lock()은 Door의 모드를 Locked로 바꾼다.
    3. 
      
  3. ScannerClient는 Scanner 인터페이스를 구현하고 내부에 Scanner를 갖는다. 생성자는 장치 주소만 받고, 첫 scan() 때 실제 장치 드라이버를 만들어 연결한다. 관리자 계정이 아니면 calibrate()를 거부한다.
    4. 
      
  4. RetryingScanner는 Scanner를 구현하고 생성자로 Scanner를 받는다. 실패하면 세 번까지 다시 부른다. 설정 파일에 따라 LoggingScanner로 한 번 더 감싸기도 한다.
    5. 
    

    

      해설 보기
      
(a) 전략. 교체를 바깥(운영자)이 결정하고, 컨텍스트는 교체 시점도 이유도 모른다. 모터들은 서로를 모른다.

      
(b) 상태. 교체를 상태 객체 자신이 결정한다(Unlocked.lock()이 다음 모드를 정한다). 상태 객체가 컨텍스트에 전이를 요청하는 역방향 의존과, 구체 상태끼리 서로를 아는 관계가 있다. "거부"라는 상태별 행동 차이도 상태 패턴의 신호다.

      
(c) 프록시. 가상 프록시(첫 사용 때 생성)와 보호 프록시(권한 검사)를 겸한다. 결정적 근거는 실제 객체를 스스로 만든다는 것이다. 클라이언트는 실제 드라이버의 참조를 갖지 않고, 프록시가 그 생명주기를 소유한다. 목적은 책임 추가가 아니라 접근 통제다.

      
(d) 데코레이터. 감쌀 객체를 받고, 같은 인터페이스로 책임(재시도, 로그)을 덧붙이며, 조합을 바깥(설정)이 정하고, 몇 겹이든 쌓인다.

      
흔한 오답은 (d)를 프록시로 보는 것이다. "재시도"를 접근 통제로 볼 수도 있기 때문이다. 판별 기준은 생성과 조합의 주도권이다. 실제 객체를 받아서 감싸고 클라이언트가 조합을 정하면 데코레이터다. 또 (a)를 상태로 보는 오답도 흔한데, "야간/주간"이라는 말이 상태처럼 들리기 때문이다. 그러나 그 전환을 모터 객체가 결정하지 않는다. 이름이 아니라 결정의 위치를 보라.

    

  


  

    
리팩터링 문제 2. 스마트 주차장

    
한빛로지스 물류센터의 주차장 시스템이다. 변경 이력을 보면 이 코드가 바뀐 이유는 세 가지였다. 변경 축 셋을 찾고, 축마다 가장 가벼운 패턴을 적용하라. 축이 아닌 곳에는 패턴을 넣지 마라.

    
class ParkingLot:
    """출차 처리. 요금·차단기·알림이 한 메서드에."""

    def __init__(self, lot_type: str, gate_vendor: str) -> None:
        self.lot_type, self.gate_vendor = lot_type, gate_vendor

    def leave(self, plate: str, car: str, minutes: int) -> str:
        # 변경 이력 1: 요금 규칙 — 직원 주차장 무료, 경차 할인이 차례로 추가됨
        if self.lot_type == "staff":
            fee = 0
        else:
            fee = -(-minutes // 30) * 1000
            if car == "compact":
                fee //= 2
        # 변경 이력 2: 차단기 교체 — 신형은 SDK 모양이 다르다
        if self.gate_vendor == "gateco":
            opened = f"GateCo #2 열림"            # sdk.open_bar(2)
        else:
            opened = f"BarrierX BX-7 5000ms 열림"  # sdk.lift("BX-7", 5000)
        # 변경 이력 3: 알림 대상 추가 — 전광판, 문자, 이번 달엔 정산 시스템
        print(f"전광판: {plate} {fee}원")
        print(f"문자: {plate}님 {fee}원 결제")
        return opened

    

      해설 보기
      
변경 이력이 곧 변경 축이다. (1) 요금 규칙 → 전략. 메서드 하나에 상태가 없으므로 함수와 이름표 dict로 충분하다. 경차 할인은 요금 규칙 내부의 사정이므로 별도 축이 아니라 standard 함수 안에 둔다. (2) 차단기 제조사 → 어댑터. 우리가 고칠 수 없는 SDK 두 개를 Gate.open() 하나로 번역한다. 게이트 번호나 유지 시간 같은 SDK 고유 인자는 어댑터 필드가 된다. (3) 알림 대상 → 옵저버. 콜러블 구독 목록이면 정산 시스템 추가는 구독 한 줄이다.

      
넣지 않은 것도 답의 일부다. 차량의 입차/출차 상태는 bool 하나라 상태 패턴이 필요 없고, 주차장이 하나라고 싱글턴을 만들 이유도 없다. 출차 흐름 하나뿐인데 퍼사드를 씌우면 통과용 메서드만 생긴다.

      
흔한 오답 두 가지. 첫째, 요금 규칙마다 FeePolicy ABC를 상속한 클래스를 만드는 것. 틀리지는 않지만 메서드 하나·상태 없음인 전략에 클래스 계층은 소음이다(10장 표). 둘째, 알림을 데코레이터로 푸는 것(NotifyingParkingLot(lot)). 알림 대상이 늘 때마다 래퍼가 한 겹씩 늘고, 순서를 조립 코드가 관리해야 한다. "반응하는 쪽이 늘어난다"는 축에는 옵저버가 맞다. 해설 코드의 -(-minutes // 30)은 올림 나눗셈 관용구다. 내림 나눗셈 //을 부호를 뒤집어 적용해 나눗셈 결과를 올림한다(31분은 2구간).

      

    

  


  

    
판단 문제 3. 동료의 세 가지 제안

    
2절의 WMS 설계 리뷰에서 다온이 세 가지를 제안했다. 각각에 찬성 또는 반대 의견을 쓰라. 근거는 "그 패턴이 해결할 변경 축이 이 시스템에 존재하는가"여야 한다. 반대한다면 어떤 변화가 생기면 찬성으로 바뀌는지도 쓰라.

    
    
      
  1. "EventHub와 TaskQueue는 시스템에 하나뿐이니 싱글턴으로 만들죠."
    2. 
      
  2. "PickOrder와 ChargeRobot에 공통 기반 클래스 BaseCommand를 두고, execute()를 '검증 → 수행 → 이벤트 발행' 템플릿 메서드로 고정하죠."
    3. 
      
  3. "재고 트리를 build() 안에 리터럴로 쓰지 말고 InventoryBuilder로 만들죠."
    4. 
    

    

      해설 보기
      
(a) 반대. "하나뿐이다"는 "하나면 충분하다"이지 "둘이면 틀린다"가 아니다(4장). 이미 build()가 각각 하나씩 만들어 필요한 곳에 나눠 준다. 싱글턴으로 바꾸면 테스트마다 구독자와 대기 명령이 누적되고(11장도 전역 이벤트 버스를 싱글턴의 유혹으로 경고했다), PickOrder가 전역에서 허브를 꺼내 쓰는 숨은 의존이 생긴다. 찬성으로 바뀌는 조건: 사실상 없다. 프로세스 사이에서 대기열이 하나여야 한다면 그것은 싱글턴이 아니라 외부 브로커의 일이다.

      
(b) 지금은 반대. 변경 축이 없다. 명령은 둘뿐이고, "검증"은 아직 어느 명령에도 없으며, 이벤트 발행 내용도 명령마다 다르다. 기반 클래스를 미리 깔면 취약한 기반 클래스 문제와 요요 문제(14장)만 들여온다. 찬성으로 바뀌는 조건: 명령이 늘고 모든 명령에 같은 골격(예: 실행 전 로봇 가용성 검사 → 실행 → 감사 로그)이 반복될 때. 그때도 먼저 고려할 곳은 상속이 아니라 호출자 TaskQueue.run_next()다. 골격을 호출자가 소유하면 명령 클래스는 상속 없이 그대로다.

      
(c) 지금은 반대, 곧 찬성. 현재 트리는 코드 안의 리터럴이고 조립하는 곳이 한 곳뿐이라 빌더가 해결할 문제가 없다. dataclass 생성자 호출로 충분하다(3장 5절). 그러나 실제 운영에서는 재고 배치가 ERP나 창고 설계 DB에서 오고, 칸 코드 중복, 빈 선반, 좌표 범위 같은 구조 제약을 조립이 끝난 시점에 검사해야 한다. 그때가 빌더의 시점이다. 7장도 "ERP 데이터에서 BOM을 만드는 코드"를 빌더의 좋은 후보로 꼽았다. 조건부·누적적 조립과 완성 시점 교차 검증이 함께 나타나기 때문이다.

      
세 답의 공통 구조를 보라. 패턴의 장점을 나열하는 것이 아니라 "이 시스템에서 무엇이 바뀌는가"를 먼저 물었다. 흔한 오답은 각 패턴의 일반적 장점("싱글턴은 메모리를 아낀다", "템플릿 메서드는 중복을 없앤다")으로 찬성하는 것이다. 장점은 해결할 문제가 있을 때만 장점이다.
