학습 목표

  1. 바뀌는 계산 규칙을 전략 객체로 빼고, 컨텍스트가 그것을 갖고 실행 중에 바꿔 끼우게 만들 수 있다.
  2. 전략을 클래스로 둘 때와 함수로 둘 때를 구분할 수 있다.
  3. "어느 전략을 쓸지" 고르는 코드를 컨텍스트 바깥 한 곳에 둘 수 있다.
핵심 한 줄 같은 일을 하는 방법이 여러 개이고, 그 방법이 따로따로 자주 바뀐다면 전략을 떠올린다.
처음이라면 이 그림부터 길 안내(내비게이션) 앱을 떠올려 보자. 앱은 출발지와 목적지를 받고 "경로를 알려 줘"라는 일을 한다. 그런데 경로를 어떻게 찾을지(가장 빠른 길, 무료 도로만, 환승 적은 길)는 설정에서 고른다. 앱은 지금 어떤 방식이 골라졌는지 따지지 않고 그냥 "경로 줘"라고 부를 뿐이다. 방식을 바꿔도 앱 자체는 그대로이고, 새 방식이 생기면 방식 목록에 하나 더하면 된다. 전략 패턴이 이것이다. 앱(컨텍스트)은 일의 틀을 쥐고, 계산 방법(전략)은 갈아 끼울 수 있는 부품으로 갖고만 있는다.
이 장에서 무엇을 챙길까
  • 꼭 알아야 하는 것 ① 자주 바뀌는 계산 규칙(요금표)을 따로 빼 두고, 서비스는 "계산해 줘"만 부른다. ② 서비스는 정책을 상속하지 않고 갖고 있어서 대입 한 번으로 바꿔 끼울 수 있다. ③ "어느 규칙을 쓸지" 고르는 if는 없어지지 않고, 서비스 바깥 한 곳(설정과 build_policy())으로 모인다.
  • 알면 좋은 것 메서드가 하나뿐인 전략은 파이썬에서 그냥 함수로 써도 된다(5절). 클래스·함수 중 무엇을 고를지는 5절 표가 기준이다.
  • 처음 읽을 때는 몰라도 되는 것 @dataclass(frozen=True)의 frozen, __call__, 정책을 등록하는 데코레이터 @register의 안쪽 동작, sorted(key=...). 5절 코드를 한 번 따라 읽은 뒤에 다시 보면 된다.

1. 상황

배달 앱 '한끼배달'의 민재는 배달비를 "기본 3,000원 + km당 500원"으로 정했다. 메서드 하나면 됐다. 그 뒤로 비 오는 날 할증, 밤 할증, 구독 회원 무료, 가게가 대신 내 주는 할인이 차례로 붙었다. 민재는 그때마다 if를 하나씩 더했다.

이번에는 운영팀이 부산에서 구간제를 시험하겠다고 한다. 구간제는 거리를 몇 구간으로 나눠 구간마다 정해진 요금을 받는 방식이다. 제주는 이번 주만 1,900원 정액이다. 민재는 서울 코드를 복사해 부산 분기를 만들었다. 몇 주 뒤 "새벽 5시 주문인데 서울은 밤 할증이 붙고 부산은 안 붙는다"는 문의가 왔다. 복사하면서 한쪽 기준만 바뀐 것이다.

4. 패턴 적용


민재는 줄마다 "운영팀이 바꾸고 싶어 하는가?"를 물었다. 요금표와 할증은 바뀌므로 정책으로 뺐고, 구독 무료와 가게 할인은 서비스에 남겼다. Order 대신 FeeInput이 넘어간다는 점을 보라. 코드에서 처음 만나는 문법 두 가지를 먼저 읽어 두자. @dataclass(frozen=True)는 __init__을 자동으로 만들어 주고, frozen은 만든 뒤 값을 바꾸지 못하게 막는다. FeePolicy(ABC)의 @abstractmethod는 "하위 클래스가 반드시 채워야 하는 메서드"라는 표시다. 마지막 build_policy()의 **가 어렵다면 바로 아래 callout을 보라.




어디를 보면 되는가.


    
  
  • FeeInput과 Order.fee_input(): 정책이 Order의 속을 모른다. 데모 [1]처럼 한 줄로 정책을 시험할 수 있다.
    • 
  
  • is_night(): 밤 기준이 한 곳에 모였다. 데모 [2]에서 두 지역 모두 할증이 붙는다.
    • 
  
  • DeliveryFeeService.quote(): 정책 종류를 묻는 if가 없다. 데모 [3]은 대입 한 번으로 정책을 바꾼다.
    • 
  
  • build_policy(): 지역 분기는 사라지지 않고 서비스 바깥의 설정과 이 함수로 옮겨졌다.
    • 



전략 패턴은 if를 없애는 패턴이 아니다. 고르는 일을 한 곳으로, 가능하면 데이터로 옮기는 패턴이다.


build_policy()의 마지막 줄을 한 줄씩 풀면 설정이 {"type": "flat", "fee": 1900}일 때
  
    
    
  1. spec["type"]은 "flat"이다. kinds["flat"]은 클래스 FlatPolicy 자체를 꺼낸다(아직 만든 것은 아니다).
    2. 
    
  2. 중괄호 안 {k: v for k, v in spec.items() if k != "type"}은 "type"만 빼고 나머지를 모은 새 dict라서 {"fee": 1900}이 된다.
    3. 
    
  3. **{"fee": 1900}은 dict를 풀어 fee=1900이라는 이름 붙은 인자로 바꿔 넘긴다. 그래서 FlatPolicy(fee=1900)을 부른 것과 같다.
    4. 
  

  {"type": "distance"}이면 남는 것이 없어 DistancePolicy()가 만들어진다. 이름 하나로 클래스를 고르는 이 표가 "고르기"를 서비스 밖으로 뺀 자리다.



왜 정책으로 따로 뺄까? 지역마다 함수를 나눠 if로 부르면 안 될까? 함수를 seoul_fee()·busan_fee()로 쪼개는 것만으로도 계산은 분리된다. 그런데 서비스가 if region == "seoul"로 어느 함수를 부를지 직접 고르면, 새 지역이 생길 때마다 서비스 안의 그 if를 또 고쳐야 한다. 전략 패턴은 고르는 일까지 서비스 밖으로 내보내서, 서비스는 "정책아, 계산해 줘" 한 줄만 남게 한다. 또 정책이 받는 입력을 FeeInput으로 좁혀 두었기 때문에 주문·고객·가게를 만들지 않고도 요금표 하나만 시험할 수 있다.







5. 파이썬다운 변형


정책 클래스의 본질은 calculate() 하나다. 파이썬은 함수를 변수에 담아 넘길 수 있으니 "FeeInput을 받아 int를 주는 함수"면 전략이 된다.


4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 요금 계산 방법을 서비스 밖에 두고 바꿔 끼우는 것이다. 다른 점은 전략의 모양이다. 4절은 클래스다. FeePolicy를 상속한 클래스를 만들고 calculate()를 채운다. 5절은 함수다. "FeeInput을 받아 int를 준다"는 호출 모양만 맞으면 함수든 람다든 전략이 되어, 상속도 추상 클래스도 필요 없다.


아래 코드에서 정책은 함수·람다·__call__이 있는 dataclass다. 새 문법을 먼저 읽어 두자. Callable[[FeeInput], int]는 "FeeInput 하나를 받아 int를 돌려주는 호출 가능한 것"이다(맨 끝이 돌려주는 값, 앞 대괄호가 받는 인자 목록). __call__이 있는 객체는 policy(q)처럼 함수 부르듯 부를 수 있다. 그리고 @register("flat")는 바로 아래 함수를 POLICY_FACTORIES["flat"]이라는 표에 올려 두는 장식이다. 데모 [2]에서 로그에 무엇이 찍히는지 비교하라.




@register("flat")를 한 줄씩 풀면
  
    
    
  1. register("flat")이 먼저 불려 deco라는 안쪽 함수를 돌려준다. 이때 "flat"이 kind로 기억된다.
    2. 
    
  2. 파이썬이 바로 아래 _flat 함수를 deco(_flat)에 넣어 부른다.
    3. 
    
  3. deco는 POLICY_FACTORIES["flat"] = _flat으로 표에 적고, _flat을 그대로 돌려준다.
    4. 
    
  4. 그래서 build_policy({"type": "flat", "fee": 1900})는 표에서 _flat을 찾아 _flat(fee=1900)을 부르고, 그 결과로 "무엇이든 1900을 돌려주는 람다"를 얻는다. 이 람다가 정책이다.
    5. 
  




람다는 이름만 찍히고, dataclass는 설정값까지 찍힌다. 그래서 형태는 이렇게 고른다.



  
전략의 성격권하는 형태

  
    
매개변수 없음, 순수 계산(같은 입력에 늘 같은 결과, 바깥을 바꾸지 않음)그냥 함수 (standard_distance)

    
설정값이 있고 로그에 남겨야 함frozen dataclass + __call__

    
메서드가 둘 이상(calculate + describe)ABC 클래스

  



데모 [3]처럼 sorted(key=...)도 전략 자리다. 파이썬은 이미 곳곳에서 함수를 받아 전략으로 쓴다.

7. 연습문제




  
판단 문제 1. 전략이 너무 많이 알 때

  
동료가 새 정책 LoyaltyPolicy.calculate(self, order: Order)를 만들었다. 안에서 order.customer.order_count, order.store.category, order.items를 읽고, 계산 후 order.applied_policy = "loyalty"를 기록한다. 이 설계에서 무엇이 잘못된 신호인지, 그리고 인자 설계로 어떻게 고칠지 설명하라.

  

    해설 보기
    
잘못된 신호는 두 가지다. 첫째, 전략이 Order의 내부 구조 경로(order.customer.order_count)를 알고 있다. 이제 Customer의 필드 이름을 바꾸면 요금 정책이 깨지고, 이 정책을 테스트하려면 고객·가게·메뉴를 갖춘 Order가 필요하다. 이는 순진한 설계의 결합을 클래스 경계 너머로 옮겨 놓았을 뿐이다. 둘째, 전략이 컨텍스트 쪽 객체에 쓰기를 한다. 전략은 "입력 → 결과"인 계산이어야 교체·병렬 실행·재시도가 안전하다. 기록은 결과를 받은 컨텍스트가 할 일이다.

    
고치는 방법은 FeeInput을 넓히는 것이다. 필요한 사실(order_count, store_category)만 필드로 추가하고, Order.fee_input()이 그것을 추출한다. 결합 지점이 fee_input() 한 메서드로 모이므로 Order 구조가 바뀌어도 그 한 곳만 고친다. 정책 이름 기록은 DeliveryFeeService.quote()가 self.policy.describe()로 한다.

    
흔한 오답은 "Order 대신 **kwargs로 다 넘기면 된다"이다. 결합은 줄어든 것처럼 보이지만 계약이 타입에서 사라져 어떤 키가 필요한지 아무도 모르게 된다. 좁은 입력은 명시적인 값 객체여야 한다. 반대로 "FeeInput이 계속 넓어지면 어떡하나"라는 걱정은 타당하다. 필드가 10개를 넘고 대부분의 정책이 그중 둘만 쓴다면 정책 군을 나눠야 한다는 신호다.

  






  
리팩터링 문제 2. 이미지 리사이즈 방식 고르기

  
사진 편집 서비스의 리사이즈 함수다(이해를 쉽게 하려고 이미지를 회색조 — 색 없이 밝기 하나로 픽셀을 나타내는 형식 — 픽셀 한 줄로 줄였다). 리사이즈는 원본 픽셀 사이의 값을 추정해 채우는 보간 계산이고, 그 추정 방법이 여럿이다. 새 보간 방식이 추가될 때마다 이 함수를 고쳐야 한다. 함수 전략 + 등록부로 바꾸되, resize(row, size, mode="linear")라는 공개 API는 유지하라.


# 보간 방식이 늘 때마다 이 함수에 elif가 추가된다.
def resize(row: list[int], size: int, mode: str = "linear") -> list[int]:
    out = []
    for i in range(size):
        x = i * (len(row) - 1) / max(1, size - 1)  # 원본 위 실수 좌표
        if mode == "nearest":
            out.append(row[round(x)])
        elif mode == "linear":
            lo = int(x); hi = min(lo + 1, len(row) - 1); t = x - lo
            out.append(round(row[lo] * (1 - t) + row[hi] * t))
        elif mode == "box":
            # 구간 평균 — 위 두 방식과 계산 단위(구간)가 달라 루프 안에서 어색하다
            step = len(row) / size
            seg = row[int(i * step):max(int(i * step) + 1, int((i + 1) * step))]
            out.append(round(sum(seg) / len(seg)))
        else:
            raise ValueError(mode)
    return out


  

    해설 보기
    
보간 방식은 설정 상태가 없는 순수 계산이므로 클래스가 아니라 함수가 알맞다. 다섯 번째 절의 표에서 "매개변수 없음, 순수 계산" 행에 해당한다. 각 방식을 (row, size) -> row 함수로 분리하고, @interpolator("이름") 데코레이터로 등록부에 올린다. resize()는 등록부 조회 후 위임만 하므로 분기가 사라진다.

    
용어
해설 코드의 세 방식은 다음과 같다. 최근접 이웃 보간은 목표 위치에 가장 가까운 원본 픽셀 값을 그대로 쓴다. 가장 빠르지만 확대하면 경계가 계단처럼 각지는 계단 현상이 생긴다. 선형 보간은 이웃 두 픽셀을 거리 비율로 섞는다. 구간 평균(box)은 축소할 때 여러 픽셀을 평균하므로, 픽셀을 듬성듬성 뽑아 원래 없던 무늬·톱니가 생기는 앨리어싱이 적다.

    
원래 코드에서 box가 어색했던 이유도 드러난다. 원래 함수는 "픽셀 하나씩 루프를 돌며 그 안에서 분기"하는 구조를 강요했는데, 구간 평균은 계산 단위가 다르다. 전략으로 분리하면 각 알고리즘이 자기에게 맞는 반복 구조를 가질 수 있다 — 조건문 안에 알고리즘을 두면 알고리즘들이 하나의 골격을 공유하도록 억지로 맞춰진다.

    

    
흔한 오답은 Interpolator ABC와 구체 클래스 셋을 만드는 것이다. 틀렸다기보다 과하다. 각 클래스에는 상태도, 두 번째 메서드도 없으므로 클래스가 주는 이점(repr, 필드, 여러 메서드의 계약)이 하나도 쓰이지 않는다. 또 하나의 오답은 공개 API를 resize(row, size, algo=linear)로 바꿔 버리는 것이다. 문자열 mode는 HTTP 요청 파라미터처럼 바깥에서 들어오는 값이므로 이름 → 함수 매핑이 어딘가에는 필요하고, 기존 호출자를 깨지 않는 편이 낫다.

  






  
판단 문제 3. 정렬 기준 두 가지

  
가맹점 월간 리포트는 "매출순"과 "가게명순" 두 가지 정렬만 지원한다. 신입 개발자가 SortStrategy ABC와 RevenueSort, NameSort 클래스를 만들자고 제안했다. 전략 패턴을 쓸 것인가, sorted(key=...)로 충분한가? 판단 근거를 쓰고 코드로 보여라.

  

    해설 보기
    
sorted(key=...)로 충분하다. 이유는 패턴을 쓰지 말자는 것이 아니라 이미 쓰고 있기 때문이다. sorted()는 정렬 알고리즘(Timsort)이라는 컨텍스트이고, key는 비교 기준이라는 전략을 주입받는 자리다. 우리가 할 일은 key 함수 두 개에 이름을 붙이는 것뿐이고, operator.attrgetter(지정한 속성을 꺼내는 함수를 만들어 주는 도구)가 그것마저 한 줄로 만들어 준다. 리포트 한 줄은 NamedTuple로 표현했다 — 필드 이름으로 접근할 수 있는 불변 튜플을 만드는 클래스라, attrgetter("revenue")를 바로 key로 쓸 수 있다.

    

    
판단 근거를 일반화하면 세 가지다. (1) 변형의 수와 증가 가능성: 두 개이고 리포트 화면의 드롭다운이 갑자기 열 개로 늘 일은 드물다. (2) 변형의 복잡도: 각 기준이 속성 하나 읽기다. (3) 언어가 제공하는 자리: key가 있다. 클래스 계층이 정당화되는 경우는 정렬 기준마다 "화면 표시 이름, 기본 방향, 권한 검사" 같은 여러 속성이 붙을 때다. 그때도 먼저 SORT_OPTIONS의 값을 작은 NamedTuple로 키우는 것을 고려하라.

    
흔한 오답은 "나중에 늘어날 수 있으니 미리 패턴을 적용한다"이다. 늘어날 때 SORT_OPTIONS에 한 줄을 추가하면 된다. 이 구조도 이미 OCP를 만족한다.

  






  
확장 문제 4. 할증을 따로 실험하기

  
운영팀이 새 요청을 했다. "요금표(A안 거리 비례 / B안 구간제)와 우천 할증(정액 1,000원 / km당 200원)을 독립적으로 조합해 2×2 실험을 하고 싶어요." 본문 패턴 코드처럼 할증이 각 요금표 클래스 안에 있으면 어떤 문제가 생기는지 설명하고, 조합을 클래스 정의 없이 조립만으로 표현하는 구조를 만들어라.

  

    해설 보기
    
할증이 요금표 클래스 안에 있으면 조합 하나가 클래스 하나다. 2×2면 4개, 요금표 3개와 할증 3개면 9개로 곱이 된다. 이것은 변하는 축이 둘인데 전략 슬롯이 하나뿐이라서 생기는 문제다. 축마다 슬롯을 하나씩 두면 클래스 수는 합(N+M)이 되고 조합은 생성 시점의 조립으로 표현된다.

    

    
할증 슬롯을 리스트로 둔 것은 할증끼리 서로 더해지는 독립적 관계이기 때문이다. 만약 할증이 "기본 요금에 1.2배" 같은 변형이라면 순서가 중요해지고, 그때는 기본 요금 전략을 감싸는 06장의 데코레이터 구조가 더 자연스럽다. 흔한 오답은 DistancePolicy를 상속해 DistancePerKmRainPolicy를 만드는 것인데, 이는 정확히 전략 패턴이 피하려 한 "상속으로 인한 클래스 폭발"을 되살린다. 클래스 폭발이란 서로 독립적으로 바뀌는 차원(여기서는 요금표와 할증) 여러 개를 상속으로 조합할 때, 클래스 수가 각 차원의 종류 수를 곱한 만큼 늘어나는 현상이다.
