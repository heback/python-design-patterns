학습 목표

  1. 복잡한 서브시스템 묶음에 대해 클라이언트용 단순한 진입점을 제공하는 퍼사드를 설계하고, 서브시스템 직접 접근을 막지 않는다는 점을 설명할 수 있다.
  2. 퍼사드가 "모든 것을 아는 신 객체(God object)"로 변질되는 징후를 식별하고 경계를 정할 수 있다.
  3. 디미터 법칙과 결합도 감소 관점에서 퍼사드의 효과를 측정(클라이언트가 의존하는 모듈 수)할 수 있다.

1. 상황

'푸른날개항공'은 인천공항 출국장에 셀프 체크인 키오스크 마흔 대를 설치했다. 키오스크 개발팀의 지호가 만든 화면 코드는 다섯 개의 사내 서비스를 차례로 불렀다. 예약 시스템에서 예약을 찾고, 여권 판독기로 승객을 확인하고, 좌석 서비스에서 좌석을 받고, 수하물 서비스에서 초과 요금을 계산하고, 탑승권 발급기로 출력한다. 각 서비스는 담당 팀이 따로 있고, 각자는 잘 만들어져 있었다.

이듬해 같은 체크인을 모바일 앱과 카운터 직원용 웹에서도 제공하기로 했다. 두 팀은 가장 빠른 길을 택했다. 지호의 화면 코드를 열어 호출 순서를 보고 자기 코드에 옮겨 적었다. 세 클라이언트가 다섯 서비스를 각자 직접 부르게 되었다.

그 뒤 두 가지 변경이 겹쳤다. 첫째, 미국 노선에 사전 승객정보(APIS) 전송 의무가 생겼다. 발권 전에 승객 정보를 미국 당국에 보내지 않으면 항공사가 승객당 벌금을 문다. 둘째, 좌석 서비스 팀이 API를 v2로 바꿨다. 키오스크 팀은 두 변경을 모두 반영했다. 모바일 팀은 좌석 API만 고치고 APIS를 놓쳤다. 감사에서 드러난 것은 그것만이 아니었다. 모바일 앱은 복제 과정에서 "여권 판독 전에는 좌석을 배정하지 않는다"는 출입국 규정을 어기고 순서를 뒤바꿔 놓았다.

문제의 핵심은 어느 서비스의 품질도 아니었다. "체크인이란 이 다섯(여섯) 서비스를 이 순서와 이 조건으로 부르는 것"이라는 지식이 UI 세 곳에 흩어져 있었다. 서비스가 바뀔 때마다 세 UI가 흔들리고, 규칙이 바뀔 때마다 세 곳 중 하나가 빠진다.

2. 순진한 설계와 그 한계

감사 직전의 코드를 재현한다. 예약·여권 판독·좌석·수하물·탑승권처럼 큰 기능을 이루면서 각자 독립적으로 관리되는 하위 구성 요소들을 서브시스템이라 부르자. 서브시스템은 각자 단순하다. 문제는 아래쪽의 두 클라이언트에 있다.

두 클라이언트의 생성자에서 서브시스템 객체를 몇 개씩 만드는지 세어 보고, MobileApp.check_in()이 KioskScreen.on_check_in()과 어디서 달라졌는지 찾아보라. 데모 [2]와 [3]이 그 차이의 결과다. 코드의 pnr은 항공 예약 기록 번호(PNR, 예약 번호)이고, mrz는 여권 하단의 기계 판독 영역(MRZ)에 정해진 형식으로 인쇄된 문자열이다.



출력 [2]에는 APIS 전송 로그가 없다. [3]은 더 심각하다. 여권 MRZ의 성(PARK)이 예약자(Lee)와 다른데도 탑승권이 나왔다. 모바일 앱은 판독 결과를 확인하지 않고 진행했다. 정리하면 다음과 같다.


    
  
  • 흐름 지식의 복제. 호출 순서, 실패 조건, 노선별 단계가 클라이언트마다 따로 존재한다. 복제본은 시간이 지나면 반드시 어긋난다.
    • 
  
  • 과도한 결합. 각 UI 클래스가 서브시스템 다섯~여섯 개에 직접 의존한다. 좌석 API v2 변경은 UI 세 개를 모두 고치게 만든다. 클라이언트의 의존 수를 세는 것이 이 장의 측정 지표다.
    • 
  
  • 디미터 법칙 위반. 디미터 법칙(최소 지식 원칙)은 객체가 직접 협력하는 객체에게만 말을 걸고, 받은 결과의 내부 구조를 따라 들어가 판단하지 말라는 원칙이다. UI가 booking.passport_verified, booking.destination 같은 서브시스템 결과의 내부를 직접 들여다보고 판단한다. UI가 알아야 할 것은 "체크인이 됐는가, 탑승권은 무엇인가"뿐이다.
    • 
  
  • 책임의 오배치. 출입국 규정 준수는 UI의 책임이 아니다. 그러나 지금은 UI 코드의 줄 순서가 규정 준수를 결정한다.
    • 








3. 패턴의 구조


GoF의 의도: "서브시스템의 인터페이스 집합에 대해 하나의 통합된 인터페이스를 제공한다. 퍼사드는 서브시스템을 더 쉽게 사용할 수 있게 해 주는 상위 수준의 인터페이스를 정의한다." 두 가지를 짚어 둔다. 대상은 객체 하나가 아니라 서브시스템(여러 객체)이고, 퍼사드는 기존 인터페이스를 맞추는 게 아니라 새로운 상위 수준 인터페이스를 정의한다. 5장의 어댑터와 구별되는 지점이다.




  
역할이 장의 클래스책임

  
    
FacadeCheckInFacade어떤 서브시스템을 어떤 순서·조건으로 부를지 안다. 요청을 적절한 서브시스템에 위임한다.

    
Subsystem classesReservationSystem, PassportReader, SeatServiceV2, BaggageService, ApisGateway, BoardingPassPrinter실제 업무 기능을 구현한다. 퍼사드의 존재를 모른다(퍼사드 쪽으로 의존하지 않는다).

    
ClientKioskScreen, MobileApp퍼사드를 통해 체크인한다.

  



구조에서 놓치기 쉬운 두 가지 성질이 있다. 첫째, 의존은 한 방향이다. 서브시스템은 퍼사드를 모른다. 그래서 퍼사드가 여럿이어도(승객용, 직원용) 서브시스템은 영향을 받지 않는다. 둘째, 퍼사드는 서브시스템을 캡슐화하지 않는다. 그림의 점선처럼 카운터 직원 웹은 좌석 수동 지정을 위해 SeatServiceV2를 직접 부른다. 퍼사드는 흔한 일을 쉽게 만드는 정문이지, 다른 출입구를 봉쇄하는 벽이 아니다. 접근을 실제로 막아야 한다면 그것은 9장 프록시(보호 프록시: 호출자의 권한에 따라 실제 객체로의 접근을 허용하거나 거부하는 대리 객체)의 일이다.







4. 패턴 적용


지호는 퍼사드를 설계하며 한 가지 원칙을 세웠다. 퍼사드의 책임은 '조율'뿐이다. 좌석을 어떻게 고르는지, 수하물 요금을 어떻게 계산하는지는 여전히 각 서비스의 일이다. 퍼사드가 아는 것은 "누구를, 어떤 순서로, 어떤 조건에서 부르는가"다.


서브시스템 부분은 01과 거의 같고, 좌석 서비스만 v2(allocate, 그리고 직원 전용 override)로 바뀌었다(전체 파일 앞부분). 여기서는 퍼사드 부분을 보자. check_in()의 주석이 '규칙 1', '규칙 2'로 표시한 곳이 01에서 UI 세 곳에 흩어져 있던 지식이다. docstring이 경계하는 두 개념도 미리 밝혀 둔다. 업무 로직은 요금 계산·좌석 배정처럼 도메인 규칙 자체를 구현한 코드로, 화면 표시·통신·조율 같은 기술적 코드와 구별된다. 신 객체(God object)는 너무 많은 책임과 지식을 떠안아 시스템 대부분이 의존하게 된 거대한 클래스다.




세 가지 설계 결정을 짚는다.


    
  
  • 반환은 CheckInResult, 실패는 CheckInError. Booking 객체를 그대로 돌려주면 클라이언트가 다시 booking.destination 같은 내부를 들여다보게 된다. 클라이언트에 필요한 것만 담은 결과 값을 정의해 디미터 법칙을 지킨다.
    • 
  
  • 서브시스템을 생성자로 주입. 퍼사드가 서브시스템을 직접 생성하면 테스트에서 가짜 판독기를 넣을 수 없고, 카운터 웹과 같은 좌석 서비스 인스턴스를 공유할 수도 없다.
    • 
  
  • 좌석 API v2 변경은 두 줄로 흡수. seat_pref → zone 변환과 allocate() 호출만 바뀌었다. 클라이언트 쪽 인터페이스(seat_pref="window")는 그대로다.
    • 



이제 클라이언트와 데모다. 두 클라이언트의 생성자 인자가 퍼사드 하나뿐이라는 점, 그리고 [3]에서 카운터 웹이 퍼사드와 서브시스템을 함께 쓰는 장면에 주목하라.




출력 [1]에서 키오스크와 모바일 모두 APIS를 전송했다. 모바일 팀이 APIS를 '기억해서'가 아니라, 기억할 필요가 없어졌기 때문이다. [2]에서 여권 불일치는 두 클라이언트 모두 좌석 배정 전에 멈췄고, 각자 자기 형식(화면 문구, JSON)으로 보여 준다. 공통 흐름은 공유하고 표현은 각자 한다. [3]의 직원 수동 변경은 퍼사드를 거치지 않았다. 이것이 학습 목표 1의 "직접 접근을 막지 않는다"이다.


학습 목표 3의 측정을 해 보자. 클라이언트가 직접 의존하는 서브시스템 모듈 수다.

전체 의존 간선이 17개에서 4개(+ 퍼사드 → 서브시스템 6개)로 줄었다. 의존의 총량은 크게 줄지 않은 것처럼 보일 수 있지만, 중요한 것은 변경 영향의 경로다. 서브시스템 변경이 퍼사드에서 멈추므로, 변경 비용이 클라이언트 수에 비례하지 않게 된다.



  함정: 신 객체로 가는 길
  
퍼사드는 "어디에 둘지 모르는 코드"가 모이기 쉬운 곳이다. 다음 징후가 보이면 경계를 다시 그어야 한다. ① 퍼사드 안에서 계산·검증 같은 업무 로직이 자란다(조율이 아니라 일을 한다). ② 서로 다른 클라이언트군(승객, 직원, 운영)이 쓰는 메서드가 한 클래스에 섞인다. ③ 퍼사드 메서드 하나를 바꾸면 무관한 클라이언트의 테스트가 깨진다. ④ 서브시스템 팀이 기능을 추가할 때마다 퍼사드에 통과용(pass-through) 메서드, 즉 받은 호출을 가공 없이 서브시스템의 같은 메서드로 넘기기만 하는 메서드가 하나씩 는다. 연습문제 3에서 이 상황을 다룬다.









5. 파이썬다운 변형


CheckInFacade는 상태가 없다. 서브시스템 참조를 들고 있을 뿐, 호출 사이에 기억하는 것이 없다. 동료 서윤이 물었다. "그럼 클래스일 이유가 있어?" 파이썬에서 퍼사드는 클래스 말고도 여러 모양을 가질 수 있다.


아래 파일은 (1) 모듈 수준 함수 하나로 된 퍼사드와 __all__(from 모듈 import *로 내보낼 이름 목록. 공개 API를 선언하는 관례로도 쓰인다)로 공개 표면을 좁히는 방식, (2) 키오스크 하드웨어의 열기·닫기 순서를 감싸는 contextmanager 퍼사드, (3) 표준 라이브러리의 대표적 퍼사드인 subprocess.run을 보여 준다(subprocess는 자식 프로세스를 실행하고, 그 프로세스의 표준 입출력을 파이프(한 프로세스의 출력을 다른 프로세스의 입력으로 잇는 운영체제 통로)로 연결해 데이터를 주고받으며, 종료 코드를 다루는 모듈이다). 데모 [2]에서 예외가 나도 장치가 역순으로 닫힌다는 점을 확인하라.


용어
__init__.py: 디렉터리를 파이썬 패키지로 만드는 파일. 패키지를 import할 때 실행되며 공개할 이름을 모아 내보낼 수 있다. 이름 앞 밑줄(_name): '내부용, 공개 API 아님'을 뜻하는 관례. 접근을 실제로 막지는 않는다. 스트리밍: 결과를 한꺼번에 모으지 않고 생기는 대로 조금씩 받아 처리하는 것.





모듈이 곧 퍼사드다


파이썬 패키지의 __init__.py는 그 자체로 퍼사드 역할을 한다. 패키지 내부에 모듈이 스무 개 있어도 __init__.py가 from ._checkin import check_in과 __all__ = ["check_in"]만 노출하면, 사용자에게 패키지는 함수 하나짜리 단순한 정문이 된다. 그러면서도 pkg._seats 같은 내부 모듈은 여전히 import 가능하다. 밑줄 접두사는 "공개 API가 아니다"라는 관례적 표시일 뿐 접근을 막지 않으므로, "퍼사드는 서브시스템을 숨기지 않는다"는 원칙과 정확히 맞는다. 상태가 없는 퍼사드라면 함수가 가장 단순한 형태다. 단, 서브시스템을 모듈 전역 기본값으로 숨기면 테스트에서 교체하기 어려운 전역 상태가 생기므로(4장 싱글턴의 함정), 위 코드처럼 키워드 인자로 주입받게 했다.


contextmanager 퍼사드: 순서 규칙 + 정리 보장


키오스크 장치는 열고 닫아야 하는 자원이다. "판독기를 먼저 열고, 프린터를 열고, 끝나면 역순으로 닫되, 예외가 나도 반드시 닫는다"는 규칙은 체크인 흐름만큼 복제되기 쉬운 지식이다. @contextmanager는 이 규칙을 with kiosk_session() as ...: 한 줄 뒤에 숨긴다. 이는 '순서 있는 여러 호출을 단순한 하나로'라는 퍼사드 의도의 파이썬다운 형태다. 데모에서는 이 세션 퍼사드와 함수 퍼사드 check_in()을 조합했기 때문에 클라이언트가 reader/printer를 받아 다시 넘긴다. 즉 "클라이언트는 장치의 열기·닫기를 모른다"까지만 성립한다. 장치의 존재까지 숨기려면 세션이 functools.partial(check_in, reader=reader, printer=printer)를 만들어 그 함수 하나만 yield하면 된다.


표준 라이브러리에서 퍼사드 읽기


subprocess.run()은 Popen 생성, 파이프 연결, communicate(), 대기, 종료 코드 확인(check=True)을 한 번의 호출로 묶는다. 그런데도 Popen은 그대로 공개되어 있어, 출력을 줄 단위로 스트리밍해야 하는 사람은 직접 쓴다(데모 [3]의 두 번째 줄). shutil.copytree()(shutil은 디렉터리 복사·삭제 같은 고수준 파일 작업 모듈이다. copytree()는 os·stat 호출을 묶는다), urllib.request.urlopen()(URL을 열어 응답을 돌려주는 함수. 연결·요청·리다이렉트 처리를 묶는다. 리다이렉트는 서버가 다른 URL로 다시 요청하라고 안내하는 응답이다)도 같은 구조다. 표준 라이브러리는 "쉬운 길을 주되 다른 길을 막지 않는다"는 퍼사드의 원칙을 일관되게 보여 준다.







6. 트레이드오프와 관련 패턴


얻는 것과 치르는 것


    
  
  • 얻는 것: 클라이언트의 결합도 감소, 흐름 규칙의 단일 출처, 서브시스템 변경의 국소화, 서브시스템의 계층화(퍼사드를 계층 간 진입점으로 삼기).
    • 
  
  • 치르는 것: 퍼사드는 '평균적인' 사용을 위한 것이므로 특수한 요구는 결국 서브시스템을 직접 쓰게 된다. 그러면 같은 일을 하는 길이 둘이 되고, 어떤 클라이언트가 어느 길을 쓰는지 추적해야 한다. 그리고 퍼사드는 신 객체로 비대해지는 경향이 있다.
    • 



쓰지 말아야 할 때


    
  
  • 클라이언트가 하나뿐이고 흐름이 단순할 때. 서브시스템 두 개를 한 곳에서만 부른다면 퍼사드는 간접 층만 더한다.
    • 
  
  • 클라이언트마다 흐름이 정말로 다를 때. 공통 흐름이 없다면 퍼사드는 클라이언트별 메서드의 잡동사니가 된다. 퍼사드의 가치는 '공유되는 흐름'에서 나온다.
    • 
  
  • 통과용 메서드만 있을 때. facade.get_seat_map()이 seats.get_seat_map()을 그대로 부르기만 한다면, 그 메서드는 단순화가 아니라 중복이다. 클라이언트가 서브시스템을 직접 쓰게 두라.
    • 
  
  • 접근 통제가 목적일 때. "직원만 좌석을 수동 변경해야 한다"는 요구는 퍼사드로 충족되지 않는다. 퍼사드는 다른 길을 막지 않기 때문이다. 권한 검사는 서브시스템 자체나 보호 프록시(9장)에 두어야 한다.
    • 



관련 패턴



  
패턴관계

  
    
어댑터(5장)둘 다 감싸지만, 어댑터는 이미 정해진 인터페이스로 변환하고 보통 객체 하나를 감싼다. 퍼사드는 새로운, 더 단순한 인터페이스를 정의하고 여러 객체를 감싼다.

    
추상 팩토리(2장)퍼사드가 플랫폼별 서브시스템 객체들을 생성해야 할 때, 그 생성을 추상 팩토리로 숨길 수 있다.

    
싱글턴(4장)퍼사드는 보통 하나면 충분하지만 그것을 강제할 이유는 없다. 조립 지점에서 하나 만들어 주입하면 된다.

    
중재자(범위 밖)중재자도 여러 객체를 조율하지만, 동료 객체들이 중재자를 알고 서로 소통을 맡긴다(양방향). 퍼사드의 서브시스템은 퍼사드를 모른다(단방향).

  








7. 연습문제




  
개념 문제 1. 퍼사드와 어댑터

  
퍼사드와 어댑터는 둘 다 "다른 객체를 감싸서 클라이언트에게 다른 인터페이스를 보여 준다." 그렇다면 둘을 어떻게 구분하는가? 감싸는 대상의 수, 인터페이스를 누가 정하는가, 의도의 세 축으로 설명하라. 그리고 이 장의 CheckInFacade.check_in() 안에서 좌석 v2 API를 다루는 두 줄은 둘 중 무엇의 성격을 띠는지 말하라.

  

    해설 보기
    

      
축어댑터퍼사드

      
        
감싸는 대상대개 객체 하나(Adaptee)서브시스템, 즉 객체 여럿

        
인터페이스Target이 이미 존재하며 거기에 맞춘다퍼사드가 새로 정의한다

        
의도변환: 호환되지 않던 것을 함께 쓰게단순화: 복잡한 것을 쉽게 쓰게

        
메서드 수Target의 메서드 수와 같다보통 서브시스템 전체보다 훨씬 적다

      
    

    
판별 질문 하나로 줄이면 이렇다. "클라이언트가 기대하는 인터페이스가 퍼사드/어댑터보다 먼저 존재했는가?" 그렇다면 어댑터, 감싸는 쪽이 인터페이스를 새로 만들었다면 퍼사드다.

    
check_in() 안의 좌석 v2 두 줄(seat_pref → zone, allocate 호출)은 어댑터적 성격이다. 퍼사드가 이미 정해 둔 자기 인터페이스(seat_pref="window")에 맞춰 바뀐 서브시스템 API를 번역하고 있기 때문이다. 실무에서 두 패턴은 이처럼 한 클래스 안에 섞여 나타나는 일이 흔하다. 번역이 커지면 SeatServiceAdapter로 분리해 퍼사드는 조율에만 집중하게 하는 것이 좋다.

    
흔한 오답: "퍼사드는 메서드를 줄이고 어댑터는 이름을 바꾼다." 현상의 일부만 본 답이다. 메서드 하나짜리 퍼사드도, 이름이 같은 어댑터(단위만 변환)도 있다. 구분 기준은 의도와 인터페이스의 출처다.

판단 문제 3. 메서드 30개짜리 퍼사드

  
2년 뒤 CheckInFacade의 메서드가 30개가 되었다. 승객용(체크인, 좌석 변경, 수하물 추가), 직원용(수동 좌석 지정, 오버부킹 처리, 탑승 마감. 오버부킹은 좌석 수보다 예약을 더 받는 항공사 관행이다), 운영용(통계, 장비 상태)이 섞여 있다. (가) 퍼사드를 쪼갠다, (나) 서브시스템을 재설계한다, (다) 그대로 둔다 중 무엇을 택할지 정할 판단 기준을 제시하라.

  

    해설 보기
    
메서드 수 30은 그 자체로 문제가 아니다. 기준은 "누가, 왜 바뀌는가"다.

    
    
      
  • (가) 쪼갠다: 메서드들이 서로 다른 클라이언트군에 쓰이고, 서로 다른 이유로 바뀐다면(승객 UX 개편 vs 운영 절차 개정) SRP·ISP 관점에서 쪼갠다. 기준은 클라이언트 역할이다. 이 사례는 여기에 해당한다. 쪼갠 퍼사드들은 서브시스템 인스턴스를 공유하므로 상태가 갈라지지 않는다. 덤으로 승객용 퍼사드에는 직원 전용 기능이 없으므로 승객 퍼사드를 통해서는 그것을 부를 길이 없다(아래 실행 [3]). 다만 퍼사드는 접근을 막지 않으므로 서브시스템을 직접 쓰는 것까지 차단하려면 보호 프록시나 서브시스템의 권한 검사가 필요하다(9장).
    • 
      
  • (나) 서브시스템 재설계: 퍼사드 메서드 다수가 여러 서브시스템을 복잡하게 엮어 '업무 로직'을 수행하고 있다면, 퍼사드가 서브시스템의 설계 결함을 메우고 있는 것이다. 예를 들어 오버부킹 처리가 퍼사드에서 좌석·예약·보상 서비스를 열 번 오가며 계산한다면, 그 로직은 오버부킹 전용 서비스(새 서브시스템)로 내려가야 한다.
    • 
      
  • (다) 그대로 둔다: 30개가 모두 한 클라이언트군의 한 흐름(예: 체크인의 세부 단계들)이고, 각 메서드가 얇은 조율만 한다면 둘 수 있다. 쪼갬 자체가 목적이 되면 안 된다.
    • 
    

    
실무 신호: "이 메서드를 바꾸면 어느 팀의 테스트가 깨지는가"를 메서드별로 적어 보라. 결과가 두 개 이상의 군집으로 나뉜다면 (가), 대부분의 메서드가 서브시스템 셋 이상을 엮어 계산한다면 (나)다.

    
흔한 오답: "메서드가 많으니 서브시스템별로 퍼사드를 하나씩 만든다(SeatFacade, BaggageFacade…)." 이는 퍼사드의 존재 이유인 '여러 서브시스템을 엮는 흐름'을 다시 클라이언트로 돌려보내는 것이다. 나누는 축은 서브시스템이 아니라 클라이언트다.
