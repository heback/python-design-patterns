학습 목표

  1. 점층적 생성자와 반쯤 만들어진 객체가 만드는 문제를 진단하고, 단계적 조립과 최종 검증을 나누는 빌더를 적용할 수 있다.
  2. GoF 빌더(Director로 같은 절차에서 다른 표현 만들기)와 유창한 빌더가 이름만 같고 목적이 다르다는 점을 설명할 수 있다.
  3. 파이썬의 키워드 인자·dataclass·dataclasses.replace가 빌더를 얼마나 대신하는지, 그래도 빌더가 필요한 때가 언제인지 판단할 수 있다.
핵심 한 줄 조각이 여러 곳에서 조건에 따라 쌓이거나 같은 절차로 여러 표현을 내야 할 때 빌더를 쓴다. 값이 한자리에서 다 정해지면 키워드로 부르는 생성자로 충분하다.
처음이라면 이 그림부터 국수집의 맞춤 주문서를 떠올려 보자. 손님은 주문서에 면·국물·토핑을 아무 순서로나 적는다. 적는 동안에는 빈칸이 있어도 괜찮다. 그러다 "제출"하면 접수 창구가 한 번에 검사한다(국물 없이 토핑만 주문하면 돌려보낸다). 접수된 주문은 더 고치지 못한다. 이 주문서가 빌더이고, 접수된 주문이 완성품이다. 한편 같은 접수 순서를 읽어 주는 담당자에게 주방을 연결하면 음식이 나오고, 안내 데스크를 연결하면 안내문이 나온다. 절차는 하나인데 결과의 모양이 다른 이 방식이 원래의 빌더(GoF 빌더)다. 아래 쿼리 이야기는 이 그림을 코드로 옮긴 것이다.
이 장에서 무엇을 챙길까
  • 꼭 알아야 하는 것 ① 조립 중의 불완전한 상태는 빌더가, 검증을 통과한 완성품은 따로 맡는다. 그래서 틀린 완성품은 아예 존재하지 않는다. ② "빌더"라는 이름이 두 가지다. 점으로 이어 쓰는 유창한 빌더(.a().b().build())와, 같은 절차로 여러 결과를 내는 GoF 빌더는 푸는 문제가 다르다. ③ 파이썬에서는 키워드 인자와 dataclass가 많은 경우 빌더를 대신한다. 조각이 여러 곳에서 조건에 따라 쌓일 때만 빌더가 필요하다.
  • 알면 좋은 것 dataclasses.replace로 불변 객체에서 조금 바꾼 객체를 만드는 법, GoF 빌더에서 Director와 렌더러의 역할 분담.
  • 처음 읽을 때는 몰라도 되는 것 typing.Self, # type: ignore, kw_only의 세부. 연습문제를 풀 때 다시 찾아보면 된다.

1. 상황

쇼핑몰 회사의 데이터 분석가 하은은 사내 BI(회사 데이터를 모아 차트로 보여 주는 분석 체계) 대시보드에 "기간별 매출" 차트를 만들었다. 데이터베이스에 묻는 언어인 SQL 문장 한 줄이면 충분했고, 이것을 SalesQuery 클래스로 감쌌다.

차트가 스무 개로 늘었다. 지역 필터, 회원 등급 필터가 붙고, 어떤 차트는 월별로 묶어 일정 금액 이상만 보여 준다. SQL에서 묶는 기준은 GROUP BY, 묶은 뒤에 거는 조건은 HAVING이다. 하은은 요구가 올 때마다 생성자에 선택 인자를 하나씩 더했다.

사고가 이어졌다. 기간 없이 지역만 걸자 문법 오류가 났다. 누군가 GROUP BY 없이 HAVING만 붙였다. 팀은 "HAVING을 쓰려면 GROUP BY도 있어야 한다"는 규칙을 정했지만 검사할 자리가 없었다. 팀장이 차트마다 한국어 요약을 띄워 달라고 하자, 하은은 to_sql()을 복사해 to_summary()를 만들었다. 한 달 뒤 VIP 매출 요약에 회원 등급 조건이 빠져 있었다.

2. 순진한 설계와 그 한계

하은의 SalesQuery다. 선택 인자가 늘 때마다 매개변수를 덧붙여, 호출부가 위치로만 구분되는 긴 인자 목록을 쓰게 되는 모양을 점층적 생성자(telescoping constructor)라 한다. 생성자와 데모 [1]의 호출부를 비교하고, to_summary()가 to_sql()을 따라 하다 무엇을 놓쳤는지 보라. 표기 두 가지: str | None = None은 "문자열이거나 None이고, 안 주면 None"이라는 뜻이고, if self.start:는 값이 None(또는 빈 문자열)이면 거짓이라 그 줄을 건너뛴다.


  
    
    
  • None 행렬. 데모 [1]의 None, "VIP", None, None은 위치로만 의미가 정해진다.
    • 
    
  • 검사할 시점이 없다. 생성자 한 번에 다 만들어야 하니, 데모 [2]의 WHERE 없는 AND나 데모 [3]의 단독 HAVING이 그대로 데이터베이스로 간다.
    • 
    
  • 조립 절차가 두 벌이다. 데모 [4]처럼 "어떤 조건이 있으면 무엇을 덧붙인다"는 절차를 두 메서드가 따로 들고 있으니 언젠가 어긋난다.
    • 
  

  
파이썬이라면 키워드로 부르기만 해도 첫 문제는 사라진다. 나머지 두 문제는 그렇지 않다.






  
3. 패턴의 구조

  
GoF의 의도는 이렇다. "복잡한 객체의 생성 과정과 표현 방법을 분리하여, 동일한 생성 절차에서 서로 다른 표현 결과를 만들 수 있게 한다." 핵심은 같은 절차와 다른 표현이다. 하은의 경우 절차는 "필터 → 묶기"이고, 표현은 SQL과 요약이다.

  
그런데 요즘 "빌더"라고 하면 대개 Builder().a(1).b(2).build() 같은 유창한 인터페이스를 떠올린다. 메서드가 자기 자신을 돌려주어 호출을 점으로 이어 쓰게 만든 API(다른 코드가 쓰라고 내놓은 함수·메서드의 약속) 설계 방식이다. 이 유창한 빌더에는 Director도 다중 표현도 없다. 목적은 "선택 사항이 많은 객체 하나를 읽히게, 검증된 불변 상태로 만들기"다. 불변은 만든 뒤 상태를 바꿀 수 없다는 뜻이다. 이름은 같지만 푸는 문제가 다르다. 이 장은 둘 다 다룬다.

  
  

    
역할이 장의 클래스하는 일

    
      
감독(Director)QueryDirector어떤 단계를, 어떤 순서로, 언제 건너뛸지 정한다

      
빌더(Builder)QueryRenderer단계별 조립 인터페이스. 순서는 모른다

      
구체 빌더(Concrete Builder)SqlRenderer, SummaryRenderer단계를 자기 표현으로 쌓고 result()로 내준다

      
유창한 빌더QueryBuilder → Query단계적으로 모으고 build()에서 검증한 뒤 불변 완성품을 낸다

    
  






  
4. 패턴 적용

  
4.1 유창한 빌더: 조립과 완성을 나눈다

  
먼저 현업에서 더 흔한 유창한 빌더로 앞의 두 문제를 푼다. 메서드가 return self로 자신을 돌려주어 호출을 점으로 이어 붙이는 기법을 메서드 체이닝이라 한다. 반환 타입 Self(typing.Self)는 "이 메서드가 불린 객체의 실제 클래스"를 뜻하는 타입 힌트다. 가변 리스트가 어디에만 있는지, 그리고 교차 검증, 곧 필드 하나가 아니라 여러 필드의 조합에 걸린 규칙(HAVING이면 GROUP BY도)을 검사하는 일이 왜 build()에 모여 있는지 보라. 코드에서 처음 나오는 표기도 읽어 두자. tuple[str, ...]은 "문자열이 몇 개든 담는 튜플"(...이 개수는 자유라는 뜻)이고, @dataclass(frozen=True)는 필드 목록만 적으면 생성자를 자동으로 만들고 만든 뒤 필드를 다시 대입하지 못하게 한다. " AND ".join(조각들)은 조각 사이에 " AND "를 끼워 한 문자열로 잇는다.

  

  
데모 [2]와 [4]를 한 줄씩 풀면
    
    
      
  1. 데모 [2]: toggles는 화면에서 사용자가 고른 값이다. start는 고르지 않았으니 None이다. b = QueryBuilder()는 세 리스트가 모두 빈 상태로 시작한다.
    2. 
      
  2. if toggles["start"]:는 None이 거짓이라 건너뛴다. region은 "서울"이라 b.where("region = '서울'")가 불린다. 이 호출이 돌려주는 self는 받지 않고 버려도 된다. 조건은 이미 b 안의 리스트에 쌓였기 때문이다. 점으로 잇는 것은 편의일 뿐이다.
    3. 
      
  3. b.build().to_sql()의 결과에 WHERE region = '서울'만 나온다. 첫 조건이 지역이어도 WHERE AND가 되지 않는 것은 조건을 모아 두었다가 한 번에 붙이기 때문이다.
    4. 
      
  4. 데모 [4]는 [2]의 같은 b를 이어 쓴다. first = b.build()가 그 시점의 조건(지역 하나)을 튜플로 복사해 first 안에 넣는다.
    5. 
      
  5. b.where("tier = 'VIP'")는 b의 리스트에만 VIP를 더한다. first가 든 튜플은 별개의 복사본이라 그대로다. 그래서 first.to_sql()에는 VIP가 없다. b.build()를 다시 부르면 그때는 VIP가 든 새 Query가 나온다.
    6. 
    

  

  
    
    
  • 데모 [1]의 호출부는 그 자체로 쿼리를 설명한다. 단계마다 이름이 있어 None 행렬이 생길 수 없다.
    • 
    
  • 데모 [2]에서 WHERE AND가 사라진 것은 조건을 리스트에 모았다가 " AND ".join()으로 한 번에 붙이기 때문이다.
    • 
    
  • 데모 [3]: 조립 순서는 자유롭지만 완성 조건은 엄격하다. 검증을 통과하지 못하면 Query는 아예 존재하지 않는다. "조립 중에는 관대하게, 완성 시에는 엄격하게"가 빌더의 약속이다.
    • 
    
  • 데모 [4]: Query는 frozen=True이고 필드가 튜플이라, 빌더를 계속 바꿔도 이미 만든 완성품은 그대로다.
    • 
  

  
4.2 GoF 빌더: 같은 절차, 다른 표현

  
이제 SQL과 요약이 절차를 복제하다 어긋난 문제를 원래의 빌더로 푼다. QueryDirector.construct()가 절차의 유일한 주인이라는 점, 두 렌더러는 단계를 표현만 한다는 점을 보라. ABC·@abstractmethod는 2장과 같다. QueryRenderer는 "이 두 단계를 구현하라"는 약속만 적은 클래스다.

  

  
데모 [1]을 한 줄씩 풀면
    
    
      
  1. q는 조건 두 개와 묶는 열 하나(month)를 가진 Query다. sql = SqlRenderer()는 parts에 시작 조각 "SELECT SUM(amount) FROM orders" 하나만 든 상태다.
    2. 
      
  2. director.construct(q, sql)은 q.where가 있으니 sql.add_filters(...)를, q.group_by가 있으니 sql.add_grouping(...)를 이 순서로 부른다. 단계마다 parts에 조각이 하나씩 붙는다.
    3. 
      
  3. construct() 자신은 아무것도 돌려주지 않는다. 결과는 렌더러에서 sql.result()로 꺼내며, 이때 조각들을 공백으로 이어 붙인다.
    4. 
      
  4. 데모 [2]는 렌더러만 SummaryRenderer()로 바꿔 같은 construct()를 부른다. 같은 순서로 같은 두 단계가 불리고, 렌더러가 자기 방식(조건: …, month별)으로 쌓을 뿐이다.
    5. 
    

  

  
데모 [1]과 [2]는 같은 Query를 같은 construct()에 넣었다. 다른 것은 건네준 렌더러뿐이다. 요약에서 등급 조건이 더 빠지지 않는 것은 렌더러가 꼼꼼해서가 아니라, 조건을 종류별로 다루는 분기 자체가 없어졌기 때문이다. 새 표현을 더해도 절차는 다시 쓰지 않는다.

  
왜 이렇게 나눌까? 더 단순한 방법이면 안 될까? ① 왜 where()마다 검사하지 않고 build()에서 한꺼번에 검사할까? having()을 group_by()보다 먼저 부르는 것도 정당한 순서인데, 단계마다 검사하면 그 순서를 막아 버린다. 조립 중에는 관대하게, 완성할 때 엄격하게 본다. ② 왜 Query와 QueryBuilder를 둘로 나눌까? 한 클래스가 "조건을 더하는 일"과 "완성된 쿼리"를 겸하면 반쯤 만든 객체가 검증 없이 어디로든 돌아다닌다. 둘로 나누면 Query를 받은 쪽은 항상 완성되고 검증된 것만 받는다. ③ 더 단순한 길은 이름=값으로 생성자를 한 번에 부르는 것이다. 값이 한자리에서 다 정해지면 그것으로 충분하고, 5절이 그 이야기다.






  
5. 파이썬다운 변형

  
Java에서 유창한 빌더가 퍼진 가장 큰 이유는 이름 있는 인자와 기본값이 없어서였다. 파이썬에는 둘 다 있다.

  
4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 완성되어 검증된 불변 Query를 얻는 것이다. 4절은 조립 중 상태를 담을 별도 객체(QueryBuilder)를 두고 build()에서 검증한다. 5절은 빌더 없이 생성자를 한 번 불러 그 직후 __post_init__에서 검증한다. 그래서 값이 한자리에서 다 정해질 때는 5절이 간단하다. 조각이 반복문·조건문 속에서 조금씩 쌓일 때는 쌓아 둘 자리가 필요하므로 4절의 빌더가 낫다.

  
아래 코드는 빌더 없이 같은 Query를 만든다. kw_only=True는 데이터클래스의 생성자를 키워드 전용 인자로, 곧 이름=값으로만 넘길 수 있게 만드는 옵션이다. __post_init__이 build()의 검증을 대신한다. dataclasses.replace는 기존 인스턴스에서 일부 필드만 바꾼 새 인스턴스를 만드는 함수다. 데모 [2]의 # type: ignore[misc]는 일부러 틀리게 부른 그 줄에서 정적 타입 검사기의 경고를 끄는 주석이다. 데모 [3]에서 검증이 다시 도는지 보라.

  

  
데모 [2]처럼 위치 인자 호출이 막히므로 점층적 생성자 문제는 사라진다. 데모 [3]의 replace()는 내부에서 생성자를 다시 부르므로 __post_init__ 검증도 다시 돈다. 불변 객체에서 조금 바꾼 객체를 파생하는 데는 빌더가 필요 없다. 이런 Query처럼 담긴 값만으로 의미가 정해지는 작은 불변 객체를 값 객체라 한다(같은 값을 담았으면 같은 것으로 본다).

  
경계는 패턴 코드의 데모 [2] 같은 조립이다. 조각이 조건문과 반복문 속에서 하나씩 정해지면, 생성자를 한 번에 부르려고 임시 리스트에 먼저 모아야 한다. 그 임시 리스트가 바로 손으로 만든 빌더다. 그런 조립이 여러 곳에서 반복되면 QueryBuilder로 묶는다.






  
6. 트레이드오프와 관련 패턴

  
얻는 것.

  
    
    
  • 선택 사항이 많은 객체의 생성 코드가 읽히고, 완성품은 검증된 불변 상태로만 존재한다.
    • 
    
  • 조건에 따라 단계를 붙였다 뺐다 하는 조립이 자연스럽다.
    • 
    
  • GoF 형태에서는 절차가 한 곳에 있어 표현이 늘어도 어긋나지 않는다.
    • 
  

  

    이 패턴을 쓰지 말아야 할 때
    
    
      
  • 키워드 인자로 끝나는 경우. 선택 인자가 많다는 것만으로는 이유가 되지 않는다. 빌더를 쓰면 같은 필드 목록을 두 곳에서 관리하게 된다.
    • 
      
  • 표현이 하나뿐인데 Director를 둘 때. SQL만 낸다면 to_sql() 하나로 족하다. 두 번째 표현이 실제로 생길 때 나눠도 늦지 않다.
    • 
      
  • 조합이 몇 개로 고정된 경우. 이름 붙은 팩토리 함수 몇 개가 더 분명하다.
    • 
    

  

  
헷갈리는 패턴과의 차이.

  
    
    
  • 추상 팩토리(2장): 함께 쓰는 여러 객체를 즉시 돌려준다. 빌더는 하나의 복잡한 객체를 단계적으로 조립해 마지막에 돌려준다.
    • 
    
  • 템플릿 메서드(14장): Director의 construct()도 고정된 절차다. 차이는 바뀌는 부분을 상속으로 받는가(템플릿 메서드), 건네받은 객체로 받는가(빌더)다.
    • 
  






  
7. 연습문제


  

    
개념 문제 1. dataclass면 충분한가

    
@dataclass 하나로 충분한 경우와 빌더가 필요한 경우를 가르는 기준 세 가지를 들고, 기준마다 이 장의 쿼리 도메인이 아닌 예를 하나씩 제시하라.

    

      해설 보기
      
기준 1. 조립이 여러 코드 지점에 걸쳐 조건부·누적적으로 일어나는가. 값이 한자리에서 모두 정해지면 키워드 인자로 충분하다. 반복문이나 여러 함수를 거치며 조각이 쌓이면 빌더가 그 중간 상태를 맡는다. 예: 이메일 메시지. 수신자·첨부를 플러그인들이 하나씩 추가한다면 MessageBuilder.add_recipient(), attach()가 자연스럽다.

      
기준 2. 검증이 단일 필드가 아니라 조립 결과 전체에 걸쳐 있고, 조립 순서가 자유로워야 하는가. 교차 검증 자체는 __post_init__으로도 된다. 빌더가 필요한 것은 기준 1과 결합할 때, 즉 "중간에는 불완전해도 되고 마지막에만 유효하면 되는" 경우다. 예: 시험 문제지 조립. 문항을 아무 순서로 넣되, 완성 시 총점이 100점이고 단원별 비율이 맞아야 한다.

      
기준 3. 같은 조립 절차에서 여러 표현이 필요한가. 이것은 GoF 빌더의 고유 영역으로 dataclass와 무관하다. 예: 하나의 문서 구조에서 HTML·Markdown·PDF 출력.

      
흔한 오답은 "필드가 많으면 빌더"다. 필드 수는 파이썬에서 기준이 되지 않는다. 필드가 20개여도 한 번에 정해지고 불변이면 dataclass(kw_only=True, frozen=True)가 낫다. 또 "검증이 필요하면 빌더"도 오답이다. __post_init__이 생성 시점 검증을 이미 제공한다.

    

  


  

    
리팩터링 문제 2. HTTP 요청 빌더

    
BI 팀의 데이터 수집 스크립트는 외부 광고 플랫폼 API를 아래처럼 부른다. 이것을 유창한 빌더로 바꾸라. GET(또는 HEAD)에 본문이 있으면 build()에서 예외를 내야 하고, 완성된 요청 객체는 불변이어야 한다. 코드 주석의 "일부 프록시"는 클라이언트와 서버 사이에서 HTTP 요청을 중계하는 네트워크 서버를 말한다(9장의 프록시 패턴과는 다른 뜻이다).

    
from dataclasses import dataclass

@dataclass
class Request:
    """가변 dataclass — 만든 뒤에도 누구나 필드를 바꿀 수 있다."""
    method: str
    url: str
    headers: dict | None = None
    params: dict | None = None
    body: bytes | None = None
    timeout: float | None = None
    retries: int | None = None
    auth: str | None = None

# 문제 1: 위치 인자 None 행렬 — 무엇이 timeout이고 무엇이 retries인가?
r1 = Request("GET", "https://ads.example.com/v2/reports", None, None, None, 10, 3, "tok-123")

# 문제 2: 실제로 났던 사고 — GET 본문은 일부 프록시가 버린다.
#   필터가 적용되지 않은 전체 데이터가 내려왔다.
r2 = Request("GET", "https://ads.example.com/v2/reports",
             body=b'{"from": "2026-09-01"}', auth="tok-123")

# 문제 3: 타임아웃 없는 재시도 — '영원히 기다리기'를 5번
r3 = Request("POST", "https://ads.example.com/v2/jobs", body=b"{}", retries=5)

    

      해설 보기
      
필수 값(메서드, URL)만 빌더 생성자로 받고 나머지는 이름 붙은 단계로 만든다. auth 문자열 대신 bearer(token)이라는 도메인 어휘(Bearer 토큰: 가진 사람에게 권한을 주는 접근 토큰으로, Authorization: Bearer <토큰> 헤더로 보낸다)를 더할 수 있다는 것도 빌더의 이점이다. "GET에 본문 금지"와 "재시도에는 타임아웃 필수"는 두 필드 이상에 걸친 제약이므로 build()에서 검사한다. 재시도 제약이 좋은 예다. .retries(3).timeout(10)처럼 재시도를 먼저 지정하는 것도 정당한 조립 순서인데, retries() 단계에서 "타임아웃이 아직 없다"며 거부하면 이 정당한 조립을 막게 된다. GET 본문 검사는 이 해설 코드에서는 메서드가 생성자에서 고정되므로 body() 단계에서 해도 동작은 같다. 그래도 build()에 두는 이유는 교차 제약을 한 곳에 모아 "완성 조건"을 한눈에 읽히게 하려는 것이다.

      
불변성은 frozen=True만으로는 부족하다. headers가 dict이면 req.headers["Authorization"] = ...처럼 내부를 바꿀 수 있다. 해설은 MappingProxyType으로 읽기 전용 뷰를 씌우고, 빌더의 dict를 복사해서 넘겨 빌더를 재사용해도 완성품이 영향받지 않게 했다. MappingProxyType은 딕셔너리를 감싸 읽기 전용으로 보여 주는 뷰라서, 원본이 바뀌면 그 변화를 그대로 비춰 보인다. 복사본을 감싸야 하는 이유다. 코드 docstring의 쿼리 문자열은 URL의 ? 뒤에 이름=값&…으로 붙는 요청 매개변수다.

      
흔한 오답 두 가지. 첫째, 기존 가변 Request를 그대로 두고 빌더만 얹는 것. build()를 통과한 뒤 누군가 r.body = ...를 하면 검증이 무의미해진다. 빌더의 검증은 제품이 불변일 때만 보장이 된다. 둘째, 각 단계에서 self가 아니라 새 빌더를 돌려주게 만들고 일부 호출부만 반환값을 받는 것. 반환값을 버리는 호출의 단계가 조용히 사라진다.

      

    

  


  

    
판단 문제 3. 쿼리가 다섯 종류로 고정이라면

    
다른 팀의 대시보드는 쿼리가 다섯 종류(일별 매출, 월별 매출, 카테고리 Top 10, 지역별 주문 수, VIP 재구매율)로 고정되어 있고, 각 쿼리의 매개변수는 기간뿐이다. 이 팀에 QueryBuilder를 권하겠는가, 아니면 "이름 붙은 팩토리 함수 다섯 개"가 나은가? 근거를 쓰고, 결론이 바뀌는 조건도 쓰라.

    

      해설 보기
      
이름 붙은 팩토리 함수 다섯 개가 낫다. 예: daily_sales(start, end) -> Query. 근거는 세 가지다. (1) 조립에 변이가 없다. 매개변수가 기간뿐이면 "조건부로 단계를 붙인다"는 빌더의 핵심 이점이 쓰이지 않는다. (2) 이름이 의도를 전달한다. 호출부의 category_top10(...)은 일곱 줄짜리 빌더 체인보다 무엇을 하는지 바로 말해 준다. (3) 허용되는 조합이 다섯 개뿐이라는 사실이 API 자체로 표현된다. 빌더를 공개하면 아무 조합이나 만들 수 있게 되어 오히려 표면이 넓어진다.

      
이것은 빌더를 버리라는 뜻이 아니다. 다섯 함수의 내부 구현에서 QueryBuilder를 쓰는 것은 좋은 선택이다. 주입 방어와 교차 검증을 그대로 재사용할 수 있다. 공개 API(바깥 사용자에게 쓰라고 약속한 이름들. 그 밖은 내부 구현으로 취급한다)는 함수, 구현 도구는 빌더다.

      
결론이 바뀌는 조건: 사용자가 필터를 자유롭게 조합하는 "탐색형" 대시보드가 생기면 조합의 수가 폭발하므로 빌더를 공개해야 한다. 또 같은 쿼리를 SQL과 요약 둘 다로 내야 한다면 함수 다섯 개 각각이 두 표현을 만들게 하지 말고, 함수는 Query만 돌려주고 렌더링은 Director와 렌더러에 맡긴다.

      
흔한 오답은 "나중에 늘어날 수 있으니 빌더"다. 팩토리 함수 안에서 이미 빌더를 쓰고 있다면, 나중에 빌더를 공개하는 비용은 거의 없다. 미리 넓은 API를 열어 두는 비용이 더 크다.
