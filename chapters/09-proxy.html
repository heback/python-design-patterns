학습 목표

  1. 실제 객체와 같은 인터페이스를 가진 대리인으로 접근을 통제하는 프록시의 종류(가상, 보호, 캐싱, 원격)를 구분할 수 있다.
  2. 가상 프록시와 보호 프록시를 구현하고, 프록시가 실제 객체의 생성을 쥔다는 점에서 데코레이터와 구별할 수 있다.
  3. 파이썬의 cached_property, lru_cache로 프록시 없이 같은 효과를 내는 방법과 그 조건을 설명할 수 있다.
핵심 한 줄 고칠 수 없는 객체에 "언제 만들지, 누구에게 보여 줄지, 무엇을 재사용할지"를 정해야 하는데 그 검사가 쓰는 곳마다 흩어진다면 프록시를 떠올린다.
처음이라면 이 그림부터 도서관 사서를 떠올려 보자. 이용자는 "이 책을 보여 주세요"라고만 말한다. 사서는 책 이름은 카드로 바로 알려 주고, 두꺼운 본문은 창고에서 정말 필요할 때 가져온다. 열람 제한 자료는 자격을 확인하고, 이미 꺼내 둔 책은 다시 가져오지 않고 카운터에서 건넨다. 이용자 입장에서는 늘 같은 방식으로 책을 달라고 할 뿐이다. 프록시가 이것이다. 진짜 객체와 같은 얼굴로 앞에 서서, 언제 만들고 누구에게 보여 주고 무엇을 재사용할지를 대신 정한다. 아래 위성 사진 이야기는 이 그림을 코드로 옮긴 것이다.
이 장에서 무엇을 챙길까
  • 꼭 알아야 하는 것 ① 프록시는 진짜 객체와 같은 인터페이스라서 쓰는 쪽이 둘을 구별하지 않고, 접근을 통제한다. ② 통제의 이유에 따라 가상(필요할 때 만든다)·보호(누구에게 허용하나)·캐싱(받은 것을 재사용한다)으로 나뉜다. ③ 데코레이터와 달리 프록시는 진짜 객체를 받아 감싸지 않고 스스로 만들 수 있어서 "언제 만들지"를 정할 수 있다.
  • 알면 좋은 것 프록시를 겹치는 순서(보호가 가상의 바깥이어야 다운로드 전에 막는다), 진짜 객체로 가는 통로를 하나로 만드는 이유, 클래스를 직접 고칠 수 있으면 cached_property·lru_cache로 충분하다는 것(5절).
  • 처음 읽을 때는 몰라도 되는 것 원격 프록시, UML 스테레오타입(«create»), lru_cache가 무엇을 버리는지의 세부. 연습문제를 풀 때 다시 찾아보면 된다.

1. 상황

개발자 수아는 위성 사진 뷰어를 맡았다. 사진 한 장의 원본은 400MB이고 저장소에는 수만 장이 있다. 외부 라이브러리의 SatelliteImage는 만들어지는 순간 원본을 내려받는다.

문제는 목록 화면이었다. 분석관은 수천 장의 제목을 훑고 그중 몇 장만 확대한다. 그런데 목록을 그리려고 사진 객체를 만드는 순간 모든 원본이 다운로드되었다. 요구도 더 있었다. 보안 시설이 찍힌 사진은 허가받은 사람만 확대할 수 있어야 하고, 같은 사진을 여러 화면에서 열 때마다 400MB를 다시 받을 수는 없었다.

수아는 목록 화면에 "권한 있나? 이미 받았나?" 검사를 넣었다. 그러나 비교 화면 담당자는 권한 검사를 복사하는 것을 잊었고, 내보내기 화면은 자기 캐시(다시 받지 않으려고 결과를 가까이에 저장해 둔 것)를 따로 만들었다.

2. 순진한 설계와 그 한계

수아의 첫 시도다. 실제로 내려받지는 않고 받은 MB를 더해 비용을 숫자로 보인다. SatelliteImage.__init__의 archive.fetch() 한 줄이 데모 [1]에서 어떤 숫자가 되는지, 그리고 CatalogScreen.open()의 검사가 이 화면에만 있다는 점을 보라.



데모 [1]의 800,000MB는 제목을 보여 주려고 만든 객체 2,000개의 대가다.


    
  
  • 만드는 것과 쓰는 것이 붙어 있다. 목록에 올리는 일과 확대하는 일은 시점이 다른데, 생성자가 둘을 묶었다.
    • 
  
  • 접근 규칙이 화면에 흩어진다. 권한 검사는 사진을 여는 모든 길에 있어야 한다. 한 곳만 빠져도 무너진다.
    • 
  
  • 캐시가 잘못된 층에 있다. 화면의 필드인 캐시는 다른 화면과 나눠 쓰지 못한다.
    • 



SatelliteImage는 고칠 수 없으니, 사진과 똑같이 보이면서 길목에서 이 일들을 맡는 대리인이 필요하다.







3. 패턴의 구조


GoF의 의도: "다른 객체에 대한 접근을 통제하기 위해 대리자를 제공한다." 연예인의 매니저처럼, 연락은 대리인이 받고 만날지 말지를 정한다. 통제하는 이유에 따라 종류가 나뉜다. 아래 그림에서 UML(클래스 관계를 그림으로 그리는 표기법)의 스테레오타입은 상자나 선에 꺾쇠로 붙이는 꼬리표로, 그 종류나 관계를 알려 준다(예: 생성 관계를 나타내는 «create»).


    
  
  • 가상 프록시: 비싼 객체를 정말 필요할 때까지 만들지 않는다(LazyImageProxy).
    • 
  
  • 보호 프록시: 호출자에 따라 허용하거나 막는다(ProtectedImageProxy).
    • 
  
  • 캐싱 프록시: 한 번 얻은 결과를 기억해 두었다가 재사용한다(CachingArchiveProxy).
    • 
  
  • 원격 프록시: 다른 컴퓨터에 있는 객체를 내 컴퓨터의 객체처럼 부르게 해 준다.
    •

4. 패턴 적용


수아는 프록시를 두 층에 두었다. 저장소 층의 CachingArchiveProxy가 재사용을, 사진 층의 두 프록시가 지연과 권한을 맡는다. 데모 [3]의 캐시 적중은 요청한 원본이 이미 캐시에 있어 다시 받지 않은 경우다. open_image()가 왜 있는지도 보라. 코드에 처음 나오는 모양을 미리 읽어 두자. RealSatelliteImage | None은 "진짜 사진이거나 아직 없음(None)"이고, 가상 프록시는 처음에 None으로 두었다가 필요할 때 채운다. ALLOWED = {"분석관"}은 허용할 사용자를 담은 집합이다. f"K3-{i:04}"는 숫자를 네 자리로 0을 채워 적는다(K3-0007). 데모의 [open_image(...) for i in range(2000)]는 사진 2,000장을 만드는데, i == 0일 때만 보안 사진(secret)이다.




어디를 보면 되는가.


    
  
  • LazyImageProxy: 진짜 객체 대신 만드는 데 필요한 재료(번호, 제목, 저장소)를 들고 있다. 진짜 객체를 생성자 인자로 받으면 이미 다운로드가 끝난 뒤이므로, 만드는 일 자체가 프록시 안에 있어야 한다. 데모 [1]의 목록은 0MB로 그려진다.
    • 
  
  • ProtectedImageProxy가 가상 프록시의 바깥에 있다: 데모 [2]에서 인턴의 요청은 다운로드 전에 막힌다. 순서를 뒤집으면 400MB를 받은 뒤에 거부한다.
    • 
  
  • CachingArchiveProxy가 저장소 앞에 있다: 데모 [3]에서 다른 화면이 새 프록시로 열어도 원격 다운로드는 늘지 않는다.
    • 
  
  • open_image(): 사진을 얻는 유일한 통로다. 화면이 RealSatelliteImage를 직접 만들 수 있으면 보호 프록시를 우회할 수 있다.
    • 



데모 [2]와 [3]을 한 줄씩 풀면 (images[0]은 보호 프록시가 가상 프록시를 감싼 것이다)
  
    
    
  1. zoom("중심부", "분석관"): 바깥 보호 프록시가 사용자를 확인하고 통과시킨다. 안쪽 가상 프록시는 _real이 None이라 그제야 RealSatelliteImage를 만든다. 그 생성자가 저장소를 불러 원본을 받으므로 400MB가 올라간다.
    2. 
    
  2. zoom("중심부", "인턴"): 보호 프록시에서 PermissionError가 나고 안쪽으로 넘어가지 않는다. 가상 프록시와 저장소에 닿지 않으니 "다운로드 전에" 막힌 것이다.
    3. 
    
  3. again = open_image("K3-0000", ...): 새 프록시 둘을 만들 뿐, 진짜 사진은 아직 없다. again.zoom(...)이 진짜 사진을 새로 만들며 저장소에 원본을 달라고 한다.
    4. 
    
  4. 그런데 저장소 앞에는 CachingArchiveProxy가 있고 이미 그 사진을 기억하고 있다. 그래서 캐시 적중이 1회 늘고 누적 다운로드는 400MB 그대로다. 캐시가 화면이 아니라 저장소 앞에 있어서 새 화면도 같은 캐시를 쓴다.
    5. 
  




왜 프록시를 진짜 객체와 같은 모양으로 만들까? 그냥 "지연 로더" 함수를 따로 두면 안 될까? 같은 모양이어야 화면이 "이게 진짜 사진인가, 대리인인가"를 구별하지 않고 똑같이 zoom()을 부른다. 함수를 따로 두면 화면마다 "아직 로더인가, 사진이 되었나"를 따져야 하고, 권한 검사를 빼먹는 길이 다시 생긴다. 같은 모양이면 나중에 프록시를 빼거나 다른 프록시로 바꿔 끼워도 화면은 한 줄도 바뀌지 않는다.







5. 파이썬다운 변형


프록시는 고칠 수 없는 객체 앞에 서는 해법이다. 클래스를 우리가 직접 설계한다면 바깥에 대리인을 세우지 않아도 된다.


4절(패턴 적용)과 5절(파이썬다운 변형)은 무엇이 다를까 목적은 같다. 지연·재사용 같은 접근 규칙을 쓰는 쪽에서 떼어 놓는 것이다. 4절은 고칠 수 없는 클래스 앞에 대리인 객체(프록시 클래스)를 세운다. 5절은 클래스를 우리가 고칠 수 있다면 객체 안에서 해결한다. 대리인 객체가 없으니 타입도 그대로고 코드도 짧다. 고칠 수 없으면 5절의 방법을 쓸 수 없다.


지연 로딩은 비싼 데이터를 미리 만들지 않고 처음 필요할 때 불러오는 방식이다. 프록시 없이도 이것을 얻을 수 있다. 아래 코드는 두 도구를 보인다. cached_property는 첫 접근 때 한 번 계산한 값을 인스턴스에 저장해 두고 이후에는 보통 속성처럼 읽히게 하는 도구다. lru_cache는 함수의 인자를 열쇠로 결과를 기억하고, 가득 차면 가장 오래 쓰이지 않은 것부터 버리는 도구다. LOADS 목록이 무거운 로딩이 언제 일어났는지 보여 준다. 둘 다 함수나 메서드 위에 @로 붙이는 데코레이터(6장)다. @cached_property를 붙인 data는 메서드로 정의했지만 scene.data처럼 괄호 없이 속성으로 읽고, 처음 읽을 때만 본문이 실행된다. 데모에서 scene.data만 적힌 줄은 값을 쓰려는 것이 아니라 접근해서 로딩을 일으키는 것이다.




    
  
  • cached_property는 가상 프록시를 대신한다. 데모 [1]에서 만든 직후에는 아무것도 로딩하지 않고, data에 처음 접근할 때 한 번만 로딩한다. 별도 객체가 없으니 타입도 그대로다. 조건은 하나, 그 클래스를 우리가 고칠 수 있어야 한다. SatelliteImage처럼 생성자가 이미 다운로드하는 외부 클래스라면 프록시가 필요하다.
    • 
  
  • lru_cache는 함수 하나짜리 캐싱 프록시다. 데모 [2]에서 A는 재사용되고, C가 들어오며 B가 밀려나 마지막 B는 다시 받는다. 특정 사진만 지우는 등 세밀한 관리가 필요하면 객체로 된 캐싱 프록시가 낫다.
    • 



데모 [2]의 A B A C A B를 풀면 (maxsize=2, 기억 칸이 둘)
  
    
    
  1. A: 처음이라 로딩한다. 기억 {A}. B: 로딩한다. 기억 {A, B}.
    2. 
    
  2. A: 기억에 있어 재사용(로딩 없음). 이때 A가 "방금 쓴 것"이 되어 B가 가장 오래 안 쓴 것이 된다.
    3. 
    
  3. C: 처음이라 로딩하고, 칸이 가득 차서 가장 오래 안 쓴 B를 버린다. 기억 {A, C}.
    4. 
    
  4. A: 재사용. 마지막 B: 버려졌으므로 다시 로딩한다. 그래서 실제 로딩은 ['A', 'B', 'C', 'B']이고, 적중 2회(A 두 번)·실패 4회다.
    5. 
  









6. 트레이드오프와 관련 패턴


얻는 것


    
  
  • 지연·권한·캐시 같은 접근 규칙을 진짜 객체와 화면 양쪽에서 떼어 낸다.
    • 



쓰지 말아야 할 때


    
  
  • 클래스를 고칠 수 있을 때. 지연 로딩이라면 cached_property가 더 단순하다.
    • 
  
  • 객체가 가벼울 때. 만드는 비용이 작으면 가상 프록시는 복잡함만 더한다.
    • 
  
  • 비용을 숨기면 해로울 때. 몇 초 걸리는 네트워크 요청을 평범한 메서드처럼 보이게 하면 호출자가 반복문 안에서 부른다. 이럴 때는 load()처럼 비용이 이름에 드러나는 API가 낫다.
    • 



또 같은 프로그램 안의 코드는 proxy._inner로 진짜 객체에 닿을 수 있다. 보호 프록시는 실수를 막는 장치이지, 악의적인 코드를 막는 벽이 아니다.


헷갈리는 패턴


    
  
  • 데코레이터(6장)는 구조가 같지만 목적이 기능 덧붙이기이고, 쓰는 쪽이 객체를 만들어 넘긴다. 프록시는 접근 통제가 목적이고, 흔히 진짜 객체를 스스로 만든다.
    • 
  
  • 어댑터(5장)는 인터페이스를 바꾸고, 프록시는 같은 인터페이스를 지킨다.
    • 
  
  • 퍼사드(8장)는 다른 길을 막지 않는다. 길을 막아야 한다면 보호 프록시와 하나뿐인 생성 통로가 필요하다.

7. 연습문제




  
개념 문제 1. 캐싱 프록시와 캐싱 데코레이터

  
패턴 코드의 CachingArchiveProxy와 똑같은 코드를 CachingArchiveDecorator라는 이름으로 써도 한 글자도 다르지 않을 수 있다. 그렇다면 둘을 구분하는 것은 의미 있는 일인가? 설계 의도와 생성 책임의 관점에서 논하라.

  

    해설 보기
    
의미 있다. 다만 구분의 대상은 클래스 코드가 아니라 그 클래스가 놓인 설계 맥락이다. 패턴은 코드 모양이 아니라 "왜 이 구조인가"의 이름이기 때문이다.

    
    
      
  • 설계 의도: 데코레이터로 읽으면 캐시는 클라이언트가 필요에 따라 붙이고 떼는 선택적 기능이다. 어떤 화면은 압축·로그와 함께, 어떤 화면은 캐시 없이 쓴다. 프록시로 읽으면 캐시는 "원격 저장소로 가는 접근을 통제한다"는 시스템 정책이며, 클라이언트는 캐시의 존재를 알 필요도 선택할 권한도 없다.
    • 
      
  • 생성 책임: 데코레이터 맥락에서는 클라이언트가 RemoteArchive를 만들어 직접 감싼다. 클라이언트가 실제 객체의 참조를 가지므로 캐시를 우회할 수도 있다. 프록시 맥락에서는 조립 지점(open_image 같은 팩토리)이 실제 저장소를 만들어 프록시 뒤에 숨기고, 클라이언트는 프록시만 받는다.
    • 
    

    
이 구분은 실질적인 결과를 낳는다. 프록시로 설계했다면 "모든 경로가 캐시를 거친다"는 불변식(어떤 연산 전후에도 항상 참으로 유지되어야 하는 조건)을 보장해야 하므로, 실제 저장소 생성을 팩토리로 단일화하고 리뷰에서 RemoteArchive()의 직접 생성을 찾아낸다. 데코레이터로 설계했다면 그런 불변식은 없고 대신 조합의 유연성을 보장한다. 같은 코드라도 무엇을 보장해야 하는지가 다르다.

    
흔한 오답: "코드가 같으니 구분은 학술적 말장난이다." 코드가 같아도 그 코드에 대한 약속(누가 만들고, 우회가 허용되는가)이 다르다. 그 약속이 테스트, 코드 리뷰, 조립 코드의 모양을 결정한다.

  






  
리팩터링 문제 2. 메서드마다 반복되는 권한 검사

  
관측 기관의 문서 관리 서비스다. 최근 추가된 export()에서 권한 검사 줄이 빠져 일반 직원이 기밀 보고서를 반출할 수 있었다. 보호 프록시로 리팩터링하라. 열람은 직원도 가능하고, 수정과 반출은 관리자만 가능하다.


class DocumentService:
    def __init__(self):
        self._docs = {"R-17": "북부 해안 관측 보고서"}

    def read(self, user, doc_id):
        # 열람은 모두 허용 — 그런데 이 사실은 '검사가 없음'으로만 표현된다
        return self._docs[doc_id]

    def update(self, user, doc_id, body):
        if user.role != "admin":            # 복사된 검사 1
            raise PermissionError("admin only")
        self._docs[doc_id] = body

    def delete(self, user, doc_id):
        if user.role != "admin":            # 복사된 검사 2
            raise PermissionError("admin only")
        del self._docs[doc_id]

    def export(self, user, doc_id):
        # 새로 추가된 메서드 — 검사를 복사하는 것을 잊었다
        return self._docs[doc_id].encode()


  

    해설 보기
    
업무 로직은 RealDocumentService에, 권한 정책은 ProtectedDocumentService에 둔다. 핵심은 정책을 메서드별 if가 아니라 표(POLICY) 하나로 선언하고, 표에 없는 동작은 기본 거부(명시적으로 허용되지 않은 것은 모두 거부)하는 것이다. 원래 사고는 "검사가 없으면 허용"이라는 기본값 때문에 생겼다. 기본 거부라면 새 메서드를 만들고 표 갱신을 잊어도 유출이 아니라 거부로 끝나고, 그것은 테스트에서 바로 드러난다. 단, 기본 거부가 막는 것은 '표 갱신 누락'뿐이다. 프록시에 새 위임 메서드를 쓰면서 _check() 호출 자체를 빠뜨리면 원래 사고와 같은 유출이 생긴다. 해설 코드는 이를 두 가지로 막는다. check_policy_complete()가 Subject의 모든 추상 메서드가 표에 있는지 확인하고(ABC가 추상 메서드 이름을 모아 두는 집합 __abstractmethods__를 쓴다), 데모 [3]이 권한 없는 사용자로 각 메서드를 호출해 하나라도 통과하면 드러나게 한다(실무에서는 이 순회를 테스트로 둔다).

    
해설 코드는 delete()를 생략했다. update()와 똑같이 표에 "delete": {"admin"} 한 줄과 위임 메서드 하나를 더하면 된다.

    
또 하나, 원래 코드에서 "열람은 모두 허용"은 '검사가 없음'으로만 표현되었다. 의도적으로 열어 둔 것인지 빠뜨린 것인지 코드만으로는 알 수 없었다. 표에서는 "read": {"admin", "staff"}로 명시된다.

    
마지막으로 보호 프록시가 실제로 보호하려면 클라이언트가 RealDocumentService를 직접 만들지 못하게 생성 경로를 단일화해야 한다(패턴 코드의 open_image()와 같은 이유). 해설 코드는 생략했지만, 실제 시스템에서는 의존성 주입 설정에서 DocumentService로 항상 프록시를 주입한다.

    
흔한 오답: 메서드마다 @admin_only 함수 데코레이터를 붙이는 것. 복사된 if보다는 낫지만 "새 메서드에 붙이는 것을 잊는다"는 원래 문제는 그대로다(6장 연습문제 3의 함수 데코레이터 vs 미들웨어 논의와 같다).
