학습 목표

  • 상태에 따라 달라지는 행동을 상태 객체로 나누고, 전이 규칙을 상태 클래스 안에 둘 수 있다.
  • 전이를 누가 정하는가로 상태 패턴과 전략 패턴(10장)을 구별할 수 있다.
  • 상태 패턴과 Enum + 전이표 가운데 무엇이 맞는지 판단할 수 있다.
핵심 한 줄 메서드마다 "지금 무슨 상태냐"를 묻는 if가 되풀이되면, 상태를 객체로 만들고 그 객체에게 묻지 말고 맡긴다.

1. 상황

공유 킥보드 '킥고'의 개발자 서진은 처음에 킥보드를 두 상태로만 관리했다. 대여 가능과 주행 중이다. status 문자열 하나와 if 몇 줄이면 됐다.

석 달 뒤 상태가 늘었다. 예약됨, 배터리 부족, 정비 중. 서진은 메서드마다 분기를 덧붙였다. 그러다 사고가 났다. 정비 기사가 브레이크를 분해해 둔 킥보드를 누군가 앱으로 열었고, 주행이 시작됐다. 범인은 상태가 둘일 때 쓴 unlock()의 else 한 줄이었다. 그때 else는 "대여 가능"이라는 뜻이었는데, 새 상태가 모두 그리로 흘러 들어갔다.

2. 순진한 설계와 그 한계

사고가 난 시점의 Scooter다. 메서드마다 상태를 묻는 모양과 unlock()의 else를 보라. 현재 상태에서 허용되지 않는 동작이 받아들여져 생기면 안 되는 상태 변화가 일어나는 것을 불법 전이라 한다.


  
실행하면 데모 [1]에서 반납 뒤에도 예약자가 남고, 데모 [2]에서 정비 중인 킥보드가 주행 중이 된다.

  
    
    
  • 기본값이 '허용'이다. else는 새 상태를 모르던 시절에 쓰였다. 새 상태는 조용히 허용된다.
    • 
    
  • 규칙이 메서드마다 흩어져 있다. "정비 중이면 무엇이 되는가"를 알려면 모든 메서드를 읽어야 한다. 상태가 하나 늘면 모든 메서드를 다시 연다.
    • 
    
  • 상태별 데이터가 늘 붙어 있다. reserved_by는 예약 중에만 뜻이 있는데, 지우기를 잊으면 찌꺼기가 남는다.
    • 
  






  
3. 패턴의 구조

  
GoF의 의도는 이렇다. "객체의 내부 상태가 바뀌면 행동도 바뀌게 한다. 객체는 마치 클래스가 바뀐 것처럼 보인다." 상태마다 클래스를 하나 두고, 동작은 현재 상태 객체에 맡긴다. 상태가 바뀐다는 것은 들고 있는 상태 객체를 갈아 끼운다는 뜻이다.

  
  

    
역할이 장의 클래스하는 일

    
      
컨텍스트(Context)Scooter상태를 묻지 않고 맡기기만 한다. 모든 전이가 change_state()를 지난다.

      
상태(State)ScooterState동작 목록을 정하고, 기본 구현은 모두 거부한다.

      
구체 상태(Concrete State)Available, Reserved, Riding, LowBattery, Maintenance허용하는 동작만 재정의하고 다음 상태를 스스로 고른다.

    
  






  
4. 패턴 적용

  
서진은 분기를 상태 클래스로 옮겼다. Maintenance에 unlock()이 없다는 점이 사고의 해답이다. Reserved.unlock()의 if는 가드 조건이다. 사건이 와도 추가 조건(여기서는 "예약자 본인")이 맞아야 전이가 일어난다.

  

  
    
    
  • ScooterState: 기본이 거부다. 새 상태에서 unlock()을 깜빡 잊어도 데모 [2]처럼 거부된다. 잊어버림이 안전한 쪽으로 실패한다.
    • 
    
  • Riding.end_ride(): 반납 뒤 LowBattery로 갈지 Available로 갈지를 상태 객체가 직접 고른다.
    • 
    
  • Reserved.user: 예약자는 이 객체에만 있다. 상태를 떠나면 함께 사라져 찌꺼기가 남지 않는다.
    • 
    
  • Scooter: 공개 메서드는 한 줄짜리 위임이다. 새 상태를 넣을 때 고칠 곳은 새 클래스와 그 상태로 들어가는 이웃뿐이다.
    • 
  

  
전략 패턴과 무엇이 다른가

  
그림 13-1은 10장의 전략 그림과 모양이 같다. 다른 것은 누가, 언제 교체하는가다. 상태를 바꾸는 사건에는 GPS(위성 신호로 위치를 재는 장치)가 알려 주는 위치 변화도 있다.

  

    
관점전략상태

언제 교체되나바깥이 정책을 바꿀 때사건(잠금 해제, 반납, 위치 변화)에 반응해서

      
구체 클래스끼리 아나모른다안다. 다음 상태를 직접 만든다

      
아무 값으로나 바꿔도 되나된다안 된다. 허용된 전이만

    
  

  
판별 질문은 하나다. "다음 것을 고르는 지식이 바뀌는 객체들 자신에게 있는가?" 있으면 상태, 바깥에 있으면 전략이다. 이름이 XxxState이고 set_state()가 있어도, 바깥만 그것을 부른다면 전략이다. 

  
두 패턴은 한 객체 안에서 함께 쓸 수 있다. 아래 Scooter는 요금 정책 슬롯(전략)과 대여 단계 슬롯(상태)을 함께 가진다. set_pricing()은 바깥이 부르고, change_state()는 상태 객체만 부른다는 차이를 보라.

  

  
데모 [1]에서 주행 중 야간 정책으로 바꿔도 주간 요금이 나온다. Riding이 출발 때의 정책을 붙잡아 두었기 때문이다. 두 종류의 변화는 이렇게 슬롯 두 개로 나눈다.






  
5. 파이썬다운 변형

  
관제팀장 유나가 물었다. "전이 규칙 전체를 한 장으로 볼 수 없나요?" 패턴 코드는 규칙을 상태 클래스 다섯 개에 나눠 둔다. 반대로 규칙을 표 하나에 모을 수도 있다. 상태들과 "(현재 상태, 사건) → 다음 상태" 규칙으로 동작을 적는 모델을 상태 기계라 하는데, 상태 패턴은 이것을 객체로, 아래 코드는 표로 만든다. 상태는 Enum 값이 되고, 전이는 다시 Scooter가 표를 보고 정한다.

  
아래 코드에서 "기본은 거부"는 TRANSITIONS에 키가 없음으로 표현된다. _enter()는 진입 동작이다. 어떤 상태에 들어갈 때마다 실행되는 동작으로, 여기서는 찌꺼기 정리와 정비 입고 때의 충전을 맡는다.

  

  
    
    
  • 얻는 것: 규칙 전체가 데모 [1]처럼 한 장에 보이고, 데이터라서 검사할 수도 있다. 상태끼리는 서로를 모른다.
    • 
    
  • 잃는 것: 가드(예약자 확인)는 표에 담기지 않아 unlock()의 if로 남는다. 예약자도 다시 Scooter 필드가 되었다. 조건부 전이 end_ride는 사건 두 개로 쪼개져, 데모 [2]처럼 방전 반납이 잠깐 '대여 가능'을 거친다.
    • 
  

  
상태마다 행동이 크게 다를수록 상태 패턴이, 전이 구조가 핵심일수록 표가 유리하다.






  
6. 트레이드오프와 관련 패턴

  
얻는 것

  
    
    
  • 상태별 행동이 한 클래스에 모이고, Scooter는 그대로다.
    • 
    
  • 기본이 거부라서 깜빡한 동작이 사고가 되지 않는다.
    • 
  

  
전이를 누가 정하는가

  

    
설계전이 결정행동맞는 경우

    
      
상태 클래스(패턴 코드)각 상태 객체각 상태 객체상태마다 행동과 데이터가 크게 다르다

      
상태 클래스 + 중앙 전이표(혼합)컨텍스트의 표각 상태 객체행동은 다르지만 규칙을 한눈에 봐야 한다

      
Enum + 전이표(전이표 변형)컨텍스트의 표컨텍스트의 if행동 차이는 작고 전이 구조가 핵심이다

    
  

  
쓰지 말아야 할 때

  
    
    
  • 상태가 둘이고 늘 기미가 없을 때. bool 하나면 된다.
    • 
    
  • 상태마다 다른 것이 문구나 색뿐일 때. 다형성이 할 일이 없다. Enum 값에 속성을 붙인다.
    • 
  

  
헷갈리는 패턴

  
    
    
  • 전략(10장)은 모양이 같지만 바깥이 교체한다. 상태는 객체 스스로 바꾼다.
    • 
    
  • 옵저버(11장)를 change_state()에 붙이면 상태 클래스를 건드리지 않고 앱 알림이나 지표 수집(동작 수치를 모아 지켜보는 일)을 더할 수 있다.
    • 
  

  
연습문제 전에 알아 둘 말. @property는 메서드를 속성처럼 읽게 해 주는 데코레이터다. 바이트코드는 파이썬 소스를 번역해 만든 중간 명령어이고, 함수의 __code__.co_names에는 그 함수가 쓰는 전역 이름이 담긴다. 상태 그래프에서 상태와 상태를 잇는 연결을 간선이라 한다.






  
7. 연습문제


  

    
개념 문제 1. 전이를 누가 정하는가

    
킥고에 '재배치 중(Relocating)' 상태가 생긴다. 배터리 부족 기기를 트럭이 수거해 충전소로 옮기는 동안의 상태로, LowBattery → Relocating → Available 경로가 추가된다. (a) 상태 객체가 다음 상태를 직접 만드는 방식(패턴 코드)과 (b) 컨텍스트가 전이표로 결정하는 방식(전이표 변형) 각각에서 무엇을 고쳐야 하는지 나열하라. 그리고 두 방식의 결합도 차이를 "누가 누구를 아는가"로 설명하라.

    

      해설 보기
      
(a) 분산 방식에서는 새 클래스 Relocating과 함께 새 상태로 들어가는 이웃인 LowBattery를 고쳐야 한다. 새 사건(relocate, arrive)이 생기므로 기본 클래스와 컨텍스트의 위임 메서드도 늘어난다. (b) 집중 방식에서는 상태 Enum에 한 줄, 사건 Enum에 두 줄, 표에 두 줄을 추가하면 끝나고 다른 상태는 전혀 바뀌지 않는다. 상태가 서로를 모르기 때문이다.

      
결합도로 보면, (a)에서는 상태 그래프의 간선이 그대로 클래스 의존이다. 아래 코드가 co_names로 측정한 의존 목록이 바로 그 간선이다. (b)에서는 모든 간선이 표라는 한 객체에 모이고, 상태 사이의 의존은 0이다. 그렇다고 (b)가 언제나 낫지는 않다. 조건부 전이(end_ride)와 진입 동작(배터리 100으로 갱신)이 컨텍스트로 돌아온 것을 보라. 흔한 오답은 "표 방식이 결합도가 낮으니 항상 더 좋다"이다. 결합이 사라진 것이 아니라 컨텍스트 한곳으로 집중된 것이다. 상태별 행동이 많다면 그 집중이 곧 순진한 코드의 거대 if로 되돌아가는 길이다.

      

    

  


  

    
리팩터링 문제 2. 전자결재 문서

    
전자결재는 문서를 시스템 안에서 올리고 승인받는 방식이고, 작성한 문서를 결재권자에게 올리는 일을 상신이라 한다. 아래 Document를 상태 패턴으로 바꿔라. 리팩터링 과정에서 원래 코드에 숨어 있는 버그 두 가지를 찾아 설명하라.

    
class Document:
    """사내 전자결재 문서. status: draft / submitted / approved / rejected"""

    def __init__(self, title):
        self.title, self.body = title, ""
        self.status = "draft"
        self.reject_reason = None      # rejected일 때만 의미가 있다

    def edit(self, text):
        # 상신 중에는 수정을 막는다(그 밖의 경우는 허용)
        if self.status == "submitted":
            raise ValueError("상신 중에는 수정할 수 없습니다")
        self.body = text
        if self.status == "rejected":
            self.status = "draft"      # 반려 문서를 고치면 다시 작성 중

    def submit(self):
        if self.status != "draft":
            raise ValueError("작성 중 문서만 상신할 수 있습니다")
        self.status = "submitted"

    def approve(self, approver):
        if self.status != "submitted":
            raise ValueError("상신된 문서만 승인할 수 있습니다")
        self.status, self.approver = "approved", approver

    def reject(self, reason):
        if self.status != "submitted":
            raise ValueError("상신된 문서만 반려할 수 있습니다")
        self.status, self.reject_reason = "rejected", reason

    

      해설 보기
      
버그 1: edit()는 "상신 중"만 막고 나머지를 허용한다. 그래서 승인된 문서도 수정된다. 이는 킥보드의 else와 같은 '기본값이 허용'인 결함이다. 버그 2: 재상신 뒤에도 reject_reason이 남아, 화면이 승인된 문서에 옛 반려 사유를 보여 줄 수 있다. 상태별 데이터가 객체 전체에 깔려 있어서 생기는 찌꺼기다.

      
해설 코드는 두 버그를 구조로 없앤다. edit()는 Draft와 Rejected만 재정의하므로 Approved에서는 자동으로 거부된다. 반려 사유는 Rejected 객체의 필드이므로, 그 상태를 떠나는 순간 사라진다. 빈 문서 상신을 막는 가드는 Draft.submit() 안에 넣었다. 흔한 오답은 상태 클래스를 만든 뒤에도 Document.edit()에 if isinstance(self._state, Approved)를 남기는 것이다. 그렇게 하면 분기가 사라지지 않고 모양만 바뀐다.

      

    

  


  

    
판단 문제 3. 회의실 표시등

    
킥고 사무실 회의실 앞 태블릿은 '비어 있음 / 예약됨 / 사용 중'을 색과 문구로 보여 준다. 상태마다 다른 것은 색과 문구뿐이고, 중요한 것은 어떤 전이가 허용되는가다(예: 사용 중인 방은 예약할 수 없다). 상태 패턴과 Enum + 전이표 가운데 무엇을 택하겠는가? 어떤 변화가 생기면 판단을 뒤집겠는가?

    

      해설 보기
      
Enum + 전이표를 택한다. 상태 패턴의 이득은 "상태별로 다른 행동"을 다형성으로 나누는 데서 오는데, 여기서는 나눌 행동이 없다. 클래스 세 개의 본문이 "다음은 X, 색은 Y" 한두 줄씩일 것이다. 반면 전이표는 규칙 전체를 다섯 줄에 보여 주고, 표시 속성은 Enum 값에 붙이면 된다.

      
판단을 뒤집을 신호는 특정 상태에만 무거운 행동이 생길 때다. 예를 들어 '사용 중'에만 연장 결제와 다음 예약자 알림이 붙는 경우다. 그때도 전체를 갈아엎을 필요는 없다. 그 상태만 객체로 승격하는 혼합형(6절 표의 가운데 줄)으로 충분하다. 흔한 오답은 "확장될지 모르니 처음부터 상태 패턴"이다. 확장 방향을 모르는 채로 미리 깐 계층은 대개 엉뚱한 축으로 나뉘어 있다.

      

    

  


  

    
비교 문제 4. 이름만 상태인 코드

    
킥고 앱에는 주행 모드 버튼(에코/일반/스포츠)이 있다. 개발자는 아래처럼 "상태 패턴"으로 구현했다고 말한다. 이것은 상태 패턴인가, 전략 패턴인가? 그리고 "어린이 보호구역에 들어가면 자동으로 에코 모드가 되고, 나오면 이전 모드로 돌아간다"는 요구가 추가되면 답이 어떻게 달라지는가?

    
class SpeedState:
    """주행 모드의 공통 인터페이스 — 이름은 State다."""
    max_kmh = 0

class EcoState(SpeedState):    max_kmh = 15
class NormalState(SpeedState): max_kmh = 20
class SportState(SpeedState):  max_kmh = 25

class Scooter:
    def __init__(self):
        self.mode = NormalState()

    def set_state(self, mode):
        # 앱의 모드 버튼 핸들러만 이 메서드를 부른다
        self.mode = mode

    def limit_speed(self, requested):
        # 모터 제어기는 현재 모드의 최고 속도로 자른다
        return min(requested, self.mode.max_kmh)

    

      해설 보기
      
현재 코드는 전략이다. 교체하는 주체가 사용자(바깥)이고, 아무 모드에서 아무 모드로나 바꿀 수 있으며, 모드 객체들은 서로를 모른다. 4절 비교표의 모든 행이 전략 쪽을 가리킨다. 사실 모드마다 다른 것이 숫자 하나뿐이므로, 전략 클래스조차 과하다. Enum이나 dict 값으로도 충분하다. 흔한 오답은 이름이 State이고 set_state가 있으니 상태 패턴이라고 답하는 것이다. 패턴은 이름이 아니라 책임의 배치로 판별한다.

      
보호구역 요구가 추가되면 이야기가 달라진다. 이제 사건(GPS 진입/이탈)에 반응해 객체 스스로 모드를 바꿔야 하고, "이전 모드로 복귀"라는 전이 규칙이 생긴다. 보호구역 안에서는 사용자의 스포츠 모드 요청을 거부해야 하므로 불법 전이도 생긴다. 이 부분은 상태 패턴이 맞다. 다만 사용자 선택 모드(전략)와 보호구역 여부(상태)를 한 계층에 섞지 말고, 전략·상태 비교 코드처럼 두 슬롯으로 분리하는 것이 좋다. SchoolZone 상태는 진입 시 사용자 모드를 기억해 두고, limit_speed()는 상태가 허용하는 상한과 사용자 전략의 상한 중 작은 값을 쓴다. 한 축에 두 종류의 변화를 섞으면 '에코+보호구역', '스포츠+보호구역' 같은 조합 클래스가 폭발한다.
