학습 목표

  1. "함께 쓰여야 하는 객체 제품군(product family)"의 일관성 문제를 식별하고, 추상 팩토리로 그 일관성을 사람의 기억이 아닌 객체 구조로 보장할 수 있다.
  2. 새 제품군(벤더) 추가는 쉽고 새 제품 종류(인터페이스) 추가는 어렵다는 비대칭 트레이드오프를 설명할 수 있다.
  3. 파이썬에서 Protocol과 생성 함수 번들로 제품군을 가볍게 표현하는 변형을 구현하고, 그 대가로 무엇을 잃는지 판단할 수 있다.

1. 상황

파일 공유 스타트업 '구름다리'의 플랫폼 엔지니어 도현은 AWS 위에 업로드 서비스를 만들었다. 업로드 API는 사용자가 올린 파일을 S3에 저장하고, 작업 대기열인 큐에 "썸네일을 만들어 달라"는 메시지를 넣는다. 이 큐는 AWS가 제공하는 메시지 큐 서비스 SQS다. 별도 프로세스로 도는 썸네일 워커는 큐에서 메시지를 꺼내 원본을 S3에서 내려받는다. 둘 다 API 키를 Secrets Manager에서 꺼낸다. 코드 곳곳에서 S3Storage(), SqsQueue(), SecretsManagerVault()를 그냥 생성했고, AWS 하나뿐일 때는 아무 문제가 없었다.

용어 AWS와 GCP(Google Cloud Platform)는 대표적인 퍼블릭 클라우드 두 곳이다. API는 프로그램이 다른 프로그램·서비스의 기능을 부르도록 약속한 인터페이스다. S3는 파일을 키로 식별되는 객체로 보관하는 AWS의 객체 저장소이고, GCP의 대응물은 GCS(Cloud Storage)다. 큐는 먼저 넣은 것을 먼저 꺼내는 대기열이고, 메시지 큐는 보내는 쪽이 넣은 메시지를 받는 쪽이 나중에 꺼내 처리하게 하는 전달 통로다. SQS는 AWS의, Pub/Sub는 GCP의 메시지 큐 서비스다. 워커는 큐의 작업을 받아 처리하는 별도 프로세스이고, Secrets Manager는 API 키·비밀번호 같은 비밀 값을 보관했다가 꺼내 주는 AWS 서비스다.

그러다 첫 대형 고객사인 한 증권사가 계약 조건으로 "GCP 전용 배포"를 내걸었다. 사내 보안 정책상 데이터가 자사 GCP 조직 밖으로 나가면 안 된다는 것이다. GCS, Pub/Sub, GCP Secret Manager를 써야 한다. 신입 동료가 생성 지점마다 if CLOUD == "gcp" 삼항 연산자를 붙여 나갔는데, 썸네일 워커의 저장소 한 줄을 빠뜨렸다. 배포는 성공했고 헬스 체크(서비스가 살아 있는지 주기적으로 확인하는 점검 요청)도 통과했다. 첫 사용자가 파일을 올리자 업로드는 gs://로 시작하는 URL(자원의 주소)을 큐에 넣었고, 워커는 S3 SDK로 그 URL을 읽으려다 실패했다. URL 맨 앞의 s3://, gs:// 같은 부분은 URL 스킴으로, 어느 시스템이 그 주소를 해석하는지를 나타낸다. 장애는 배포 세 시간 뒤 고객사 담당자의 전화로 알려졌다.

설상가상으로 프런트엔드 개발자들은 노트북에서 클라우드 없이 백엔드(화면 뒤에서 데이터와 업무 처리를 맡는 서버 쪽 코드)를 돌리고 싶어 한다. 파일 시스템 저장소, 인메모리 큐, .env 파일(개발 환경의 설정과 비밀 값을 이름=값 줄로 적어 두는 파일)의 시크릿으로 된 세 번째 조합이 필요하다. 이제 생성 지점마다 세 갈래 분기가 필요하고, 조합 하나라도 어긋나면 같은 종류의 장애가 다시 난다.

이 장애의 본질은 "생성 코드가 흩어져 있다"는 데서 끝나지 않는다. 저장소·큐·시크릿은 서로의 결과물을 이해해야 하는 객체들이다. 저장소가 낸 URL을 다른 프로세스의 저장소가 읽고, 같은 자격 증명(시스템에 접근할 권한을 증명하는 키·토큰·계정) 체계 안에서 동작해야 한다. 이 "섞이면 안 된다"는 제약이 코드 어디에도 표현되어 있지 않고, 사람이 기억해야 하는 규칙으로만 존재했다.

2. 순진한 설계와 그 한계

GCP 전환을 반쯤 끝낸 시점의 코드다. 벤더 래퍼(다른 객체를 감싸 호출을 받아 전달하는 객체)는 실제 SDK 대신 메모리로 흉내 냈다. 코드 주석의 os.environ은 프로세스 바깥에서 주어지는 이름=값 설정인 환경 변수를 읽는 통로이고, Pub/Sub 래퍼 docstring의 토픽은 발행-구독 방식의 수신 주소다. 발행자가 토픽에 메시지를 내보내면 그 토픽을 구독한 쪽들이 받아 가고, 발행자는 누가 받는지 모른다. UploadService.__init__의 세 줄이 "같은 환경이어야 한다"는 규칙을 어떻게 암묵적으로 지키는지, 그리고 ThumbnailWorker.__init__에서 무엇이 빠졌는지 보라. 데모 [2]에서는 실패가 언제 드러나는지가 핵심이다.


  
[2]의 "서비스 시작 OK" 줄이 이 설계의 가장 위험한 성질을 보여준다. GcsStorage와 S3Storage는 둘 다 put/get을 가진 멀쩡한 객체라서, 덕 타이핑에서도 정적 타입 검사에서도 "틀린 조합"이 아니다. 조합의 오류는 두 객체가 서로의 결과물(URL)을 주고받는 순간, 즉 런타임 한참 뒤에야 드러난다.

  
문제를 둘로 나눌 수 있다. 첫째는 분산이다. 환경 수 × 생성 지점 수만큼 수정해야 하고(OCP 위반), 서비스 클래스들이 벤더 구체 클래스를 직접 안다(DIP 위반). 이것만이라면 1장의 팩토리 메서드나 단순 팩토리로도 해결된다. 둘째가 이 장의 고유한 문제인 일관성이다. 생성 함수를 저장소용·큐용·시크릿용으로 따로 만들면 분산은 해결되지만, 여전히 호출자가 make_storage("gcp")와 make_queue("aws")를 섞어 부를 수 있다. 필요한 것은 "어느 제품군인가"라는 결정을 단 한 번만 내리게 하는 구조다.






  
3. 패턴의 구조

  
GoF의 의도는 이렇다. "구체 클래스를 지정하지 않고, 서로 관련되거나 의존하는 객체들의 군(family)을 생성하기 위한 인터페이스를 제공한다." 1장의 팩토리 메서드가 "제품 하나"의 생성을 미뤘다면, 추상 팩토리는 제품군에 속한 모든 제품의 생성 메서드를 한 객체에 묶는다. 묶었기 때문에 클라이언트는 팩토리 하나만 받고, 팩토리 하나를 고르는 순간 제품군 전체가 정해진다.

  
  

    
역할이 장의 클래스책임

    
      
추상 팩토리(Abstract Factory)CloudFactory제품군에 속한 제품 종류마다 생성 메서드를 하나씩 선언한다.

      
구체 팩토리(Concrete Factory)AwsFactory, GcpFactory, LocalFactory한 제품군의 제품만 만든다. 제품군이 공유하는 설정(리전(클라우드 데이터센터의 지리적 구역), 프로젝트, 계정)을 소유한다.

      
추상 제품(Abstract Product)BlobStorage, MessageQueue, SecretVault클라이언트가 아는 유일한 제품 타입.

      
구체 제품(Concrete Product)S3Storage, GcsStorage 등 9개벤더 SDK 래퍼.

      
클라이언트(Client)UploadService, ThumbnailWorker팩토리 하나를 받아 필요한 제품을 꺼낸다.

    
  

  
그림의 모양에서 이 패턴의 비대칭이 이미 보인다. 제품군을 하나 더하는 것은 그림에 열을 하나 추가하는 일(구체 팩토리 1개 + 구체 제품들)이고 기존 클래스는 건드리지 않는다. 반면 제품 종류를 하나 더하는 것(예: CDN, 콘텐츠를 사용자 가까운 서버에 복제해 빠르게 전달하는 분산 네트워크)은 행을 추가하는 일인데, CloudFactory에 메서드를 넣는 순간 모든 구체 팩토리를 고쳐야 한다.






  
4. 패턴 적용

  
이제 제품군을 CloudFactory 계층으로 묶는다. 파일이 길므로 다음 순서로 읽기를 권한다. (1) 맨 위의 CloudAccount: 제품군이 일관되어야 하는 실제 이유인 "공유 컨텍스트"다. 한 제품군의 제품들이 함께 써야 하는 자격 증명·리전·프로젝트 같은 공통 설정과 상태를 말하며, 구체 팩토리가 소유해 모든 제품에 나눠 준다. 주석의 boto3는 AWS의 공식 파이썬 SDK이고, 버킷은 객체 저장소에서 객체들을 담는 최상위 그릇이다. (2) CloudFactory와 세 구체 팩토리: 각 팩토리가 계정 컨텍스트를 한 번 만들어 모든 제품에 나눠 주는 방식. (3) 클라이언트인 UploadService, ThumbnailWorker: 구체 클래스 이름이 하나라도 남아 있는지. (4) make_cloud_factory(): 분기가 남아 있는 유일한 곳.

  
  

  
[1]에서 같은 클라이언트 코드가 세 환경에서 그대로 돈다. naive 버전에서 장애를 냈던 ThumbnailWorker는 이제 저장소와 큐를 같은 팩토리에서 받으므로, 다른 제품군의 저장소를 가질 길이 없다. 섞인 조합을 만들려면 GcpFactory.create_storage()가 S3Storage를 반환하도록 제품군 정의 자체를 틀리게 써야 하는데, 그것은 코드 리뷰에서 한 곳만 보면 잡힌다. 일관성 규칙이 "모든 생성 지점에서 지켜야 할 약속"에서 "한 클래스의 정의"로 좁혀진 것이다. 다만 UploadService와 ThumbnailWorker에 서로 다른 팩토리를 넘기면 클라이언트 사이의 불일치는 여전히 가능하다. 그것을 막는 것이 아래에서 말할 composition root다.

  
UploadService가 제품 세 개를 따로 주입받지 않고 팩토리를 받는다는 점도 의도적이다. 제품을 개별 인자로 받으면 의존성 주입으로서는 더 순수하지만, 호출자가 다시 GCS와 SQS를 섞어 넘길 수 있다. 추상 팩토리는 "결정을 한 번만 내리게 한다"는 제약 자체를 인터페이스로 만든 것이다.

  
make_cloud_factory()에는 if가 남아 있다. 이것은 실패가 아니다. naive 버전의 문제는 분기가 존재했다는 것이 아니라 생성 지점마다 복제되었다는 것이었다. 구체 팩토리를 고르는 일은 프로그램 시작 지점(composition root) 한 곳에서 한 번 일어난다. 마지막 [3]은 이 "한 번"이 중요한 이유를 보여준다. 로컬 제품군의 인메모리 큐는 팩토리 인스턴스에 묶여 있어서, 서비스마다 팩토리를 따로 만들면 같은 앱 안에서도 서로 다른 큐를 본다. (예제의 시뮬레이션에서는 AwsFactory와 GcpFactory도 인스턴스마다 계정을 새로 만들어 같은 현상이 나지만, 실제 클라우드에서는 계정이 외부 상태라 공유된다. 로컬 제품군에서는 이것이 실제 동작이다.) composition root가 팩토리를 하나 만들어 모두에게 나눠 주어야 한다. "팩토리는 하나면 된다"는 이 관찰은 흔히 "그러니 싱글턴으로 만들자"로 이어지는데, 그것이 왜 불필요한지는 4장에서 다룬다.

  

    핵심 정리
    추상 팩토리의 가치는 생성 코드를 모으는 데 있지 않다. 그것은 팩토리 메서드로도 된다. 고유한 가치는 제품군의 일관성 제약을 "팩토리 하나를 고른다"는 단일 결정으로 캡슐화하는 데 있다. 제품들이 서로 독립적이라면 이 패턴은 필요 없다.
  






  
5. 파이썬다운 변형

  
02의 클래스 수를 세어 보면 추상 4개, 구체 팩토리 3개, 구체 제품 9개다. 파이썬에는 이 무게를 줄일 도구가 둘 있다. 제품 인터페이스를 typing.Protocol로 정의하면 벤더 SDK 래퍼가 우리 ABC를 상속하지 않아도 된다. 그리고 팩토리를 "생성 함수 몇 개의 묶음"으로 보면 클래스 계층 대신 불변 값 하나로 표현할 수 있다. 같은 이름의 함수(create_storage, create_queue)를 가진 모듈 aws.py, gcp.py를 두고 모듈 객체 자체를 팩토리로 넘기는 방법도 같은 발상이다.

  
아래 코드는 팩토리를 @dataclass(frozen=True) 번들 CloudKit으로, 구체 팩토리를 그 번들을 만드는 함수 aws_kit() 등으로 바꾼다. 환경 변수를 읽는 composition_root()가 하나뿐이라는 점과, 무엇보다 __post_init__이 왜 필요한지에 주목하라. 데모 [2]와 [3]이 그 답이다. __post_init__은 데이터클래스가 자동으로 만든 생성자가 필드를 채운 직후 불러 주는 메서드로, 여러 필드에 걸친 검증을 넣는 자리다. 데모 [3]의 dataclasses.replace는 기존 인스턴스에서 일부 필드만 바꾼 새 인스턴스를 만드는 함수인데, 내부적으로 생성자를 다시 부르므로 __post_init__ 검증도 다시 돈다.

  
  

  
[1]은 가벼워진 대가로 잃은 것이 없어 보인다. 그러나 [2]가 중요하다. 번들은 데이터이므로 CloudKit("gcp", storage=gcp.storage, queue=aws.queue)처럼 누구나 필드를 섞어 새 번들을 만들 수 있다. 클래스 계층에서는 GcpFactory라는 타입이 제품군 정의를 독점했기 때문에 이런 일이 구조적으로 불가능했다. 번들 방식은 그 보장을 __post_init__의 실행 시 검사로 되찾아야 하고, 그 검사도 제품이 정직하게 provider를 밝힌다는 약속에 기댄다. 검사를 위해 생성 함수를 미리 호출해야 하므로 생성이 비싼 제품에는 적용하기 어렵다는 한계도 있다.

  
그렇다면 클래스 계층은 언제 여전히 필요한가? (1) 구체 팩토리가 리전·자격 증명·연결 풀(비싼 네트워크 연결을 미리 만들어 두고 재사용하는 연결 묶음) 같은 공유 상태를 소유해야 할 때(02의 CloudAccount), (2) 제품군 정의를 여러 팀이 독립적으로 추가하며 타입으로 일관성을 강제하고 싶을 때, (3) 제품 생성에 제품군 공통 로직(재시도 정책(실패한 요청을 언제, 몇 번 다시 시도할지 정한 규칙), 계측 래핑(실행 시간·호출 수 같은 지표를 모으는 측정 코드를 덧씌우는 것))이 붙을 때다. 반대로 제품군이 두세 개이고 composition root에서만 조립된다면, 번들이나 모듈 방식이 읽기 쉽고 충분하다.

  

    ABC냐 Protocol이냐
    제품 인터페이스는 대개 Protocol이 맞다. 벤더 SDK나 테스트 가짜 객체는 우리 계층을 상속하지 않는 편이 자연스럽다. 팩토리 인터페이스는 반대로 ABC가 맞는 경우가 많다. 팩토리는 우리가 소유하는 확장 지점이고, 새 제품 종류를 추가했을 때 구현을 빠뜨린 구체 팩토리를 인스턴스화 시점에 잡아 주기 때문이다.
  






  
6. 트레이드오프와 관련 패턴

  
얻는 것. 클라이언트가 구체 클래스를 모른다(DIP). 제품군 교체가 팩토리 하나를 바꾸는 일로 끝난다. 그리고 이 패턴만의 이득으로, 제품군 내부의 일관성이 구조로 보장된다.

  
치르는 것. 3절 끝에서 본 비대칭이 가장 크다. 새 제품군은 기존 코드 수정 없이 추가되지만(OCP 충족), 새 제품 종류는 추상 팩토리와 모든 구체 팩토리를 수정해야 한다(그 축에서는 OCP가 깨진다). 따라서 이 패턴은 "제품 종류는 안정적이고 제품군은 늘어난다"는 예측에 거는 설계다. 예측이 반대라면 잘못된 축으로 확장성을 산 셈이다. 클래스 수가 제품 종류 × 제품군으로 늘어나는 것도 비용이다.

  

    이 패턴을 쓰지 말아야 할 때
    
    
      
  • 제품들 사이에 일관성 제약이 없을 때. 저장소와 큐를 서로 다른 벤더로 섞어도 아무 문제가 없다면(예: 로그 저장소와 이메일 발송기), 각각을 독립적으로 주입하는 편이 단순하다. 묶을 이유가 없는 것을 묶으면 한쪽만 바꾸고 싶을 때 오히려 방해가 된다.
    • 
      
  • 제품군이 하나뿐이고 테스트 대역만 필요할 때. "AWS 하나 + 테스트용 가짜"라면 추상 팩토리 계층보다 생성자 주입으로 가짜 객체를 넣는 것으로 충분하다(연습문제 3).
    • 
      
  • 제품 종류가 자주 바뀔 때. 매 분기마다 새 서비스 종류(CDN, 캐시, 검색…)가 붙는 팀이라면 추상 팩토리의 비대칭 비용을 매번 치른다.
    • 
      
  • 제품이 하나뿐일 때. 그것은 1장의 팩토리 메서드나 그냥 팩토리 함수의 영역이다.
    • 
    

  

  
관련 패턴.

  
    
    
  • 팩토리 메서드(1장): 추상 팩토리의 각 create_*는 팩토리 메서드다. 팩토리 메서드가 "Creator의 흐름 안에서 생성 한 단계를 미룬다"면, 추상 팩토리는 그런 메서드들을 별도 객체로 떼어 내 클라이언트에 합성으로 넘긴다.
    • 
    
  • 빌더(3장): 대비가 유용하다. 추상 팩토리는 "함께 쓰여야 하는 여러 객체를 즉시" 만들고, 빌더는 "한 번에 만들기 어려운 하나의 복합 객체를 단계적으로" 만든다.
    • 
    
  • 싱글턴(4장): 구체 팩토리는 보통 애플리케이션에 하나면 충분하다. 그러나 "하나면 충분하다"와 "하나만 존재할 수 있어야 한다"는 다른 요구다. composition root에서 하나 만들어 나눠 주면 된다.
    • 
    
  • 퍼사드(8장): 제품군 위에 "파일 업로드" 같은 단순한 API를 얹으면 퍼사드가 된다. 둘은 자주 함께 쓰인다.
    • 
  






  
7. 연습문제


  

    
개념 문제 1. CDN을 추가하면

    
본문 02의 설계에 제품 종류 "CDN"(create_cdn(), AWS는 CloudFront, GCP는 Cloud CDN, 로컬은 정적 파일 서버)을 추가하려 한다. (1) 새로 만들어야 하는 클래스와 수정해야 하는 기존 클래스를 각각 세라. (2) 비교를 위해 새 제품군 "Azure"를 추가할 때의 수를 같은 방식으로 세라. (3) 두 결과의 차이가 GoF가 말하는 이 패턴의 어떤 결과(consequence)인지 설명하라.

    

      해설 보기
      
(1) CDN 추가: 새 클래스 4개(추상 제품 Cdn 1 + 구체 제품 CloudFrontCdn, CloudCdn, LocalStaticCdn 3). 수정할 기존 클래스 4개(CloudFactory에 추상 메서드 추가 + 구체 팩토리 3개 모두에 구현 추가). (2) Azure 추가: 새 클래스 4개(AzureFactory 1 + 구체 제품 3), 수정할 기존 클래스 0개. composition root의 분기 한 줄만 바뀐다.

      
(3) 만드는 클래스 수는 비슷하지만 수정의 수가 0 대 4로 갈린다. GoF는 이것을 "새로운 종류의 제품을 지원하기가 어렵다(Supporting new kinds of products is difficult)"는 결과로 명시한다. 추상 팩토리 인터페이스가 만들 수 있는 제품의 집합을 고정하기 때문이다. 즉 이 패턴은 제품군 축으로는 열려 있고 제품 종류 축으로는 닫혀 있다.

      
흔한 오답은 "클래스가 4개씩 생기니 비용이 같다"는 결론이다. 비용의 핵심은 새로 쓰는 코드량이 아니라 기존 코드를 건드리는 범위다. 수정은 다른 팀의 구체 팩토리(외부 저장소에 있을 수도 있다)까지 퍼지고, ABC를 썼다면 구현을 미처 추가하지 못한 구체 팩토리는 인스턴스화부터 실패한다. 이 실패는 사실 좋은 성질이다. 누락이 배포 후가 아니라 시작 시점에 드러나기 때문이다.

    

  


  

    
리팩터링 문제 2. 테마별 CLI 위젯

    
사내 배포 도구의 CLI(터미널에서 텍스트 명령으로 쓰는 프로그램)는 터미널 테마에 따라 버튼과 대화상자를 다르게 그린다. 아래 코드는 위젯을 만드는 곳마다 테마를 검사한다. 이것을 추상 팩토리로 리팩터링하고, 클라이언트 함수에 테마 분기가 하나도 남지 않게 하라.

    
def render_button(theme: str, label: str) -> str:
    # 문제: 테마 검사가 위젯 종류마다 복제된다
    if theme == "dark":
        return f"▐ {label} ▌"
    return f"[ {label} ]"

def render_dialog(theme: str, message: str, button_html: str) -> str:
    if theme == "dark":
        return f"┏ {message} ┓  {button_html}"
    return f"┌ {message} ┐  {button_html}"

def confirm_deploy(theme: str, target: str) -> str:
    # 문제: 대화상자와 버튼의 테마를 '같게' 넘기는 것은 호출자의 기억에 달려 있다
    button = render_button(theme, "확인")
    return render_dialog(theme, f"{target}에 배포할까요?", button)

def confirm_rollback(theme: str, target: str) -> str:
    # 실제로 났던 버그: 버튼에 하드코딩된 "light" — 다크 대화상자 안의 라이트 버튼
    button = render_button("light", "되돌리기")
    return render_dialog(theme, f"{target}을 되돌릴까요?", button)

    

      해설 보기
      
"함께 쓰여야 하는 제품"은 버튼과 대화상자다. 대화상자가 버튼을 안에 담기 때문에 두 테마가 섞이면 화면에서 바로 드러나는, 본문 클라우드 예제와 똑같은 일관성 제약이다. WidgetFactory(추상 팩토리)에 create_button(label)과 create_dialog()를 두고, DarkWidgets/LightWidgets가 각 제품군을 만든다. 책임 배분에 주의하라. 버튼의 모양(테마)은 팩토리가 정하고, 버튼의 라벨("확인", "되돌리기")은 클라이언트가 정해 create_button()에 넘긴다. 대화상자는 받은 버튼의 render()만 부른다. 두 클라이언트 confirm_deploy()와 confirm_rollback()은 테마 문자열 대신 팩토리 하나만 받는다. 그래서 원래 confirm_rollback에서 났던 "버튼만 라이트로 하드코딩" 버그는 다시 쓸 방법이 없다. 버튼을 얻는 유일한 경로가 대화상자와 같은 팩토리이기 때문이다. 실행 결과에서 두 테마 × 두 클라이언트의 네 화면 모두 대화상자와 버튼의 테마가 일치한다. 테마 판단은 시작 시 THEMES 표 조회 한 번뿐이다.

      
흔한 오답 두 가지. 첫째, Button과 Dialog를 각각 클래스로 만들고 make_button(theme), make_dialog(theme) 두 팩토리 함수를 두는 것. 분기는 모였지만 호출자가 여전히 두 함수에 서로 다른 테마를 넘길 수 있어 일관성 문제가 남는다. 둘째, Dialog가 버튼을 직접 만들거나 버튼 라벨을 정하게 하는 것. 이 예에서는 동작하는 것처럼 보이지만 대화상자가 버튼의 구체 클래스나 라벨을 알게 되어, "확인" 말고 "되돌리기" 버튼이 필요한 confirm_rollback 같은 클라이언트를 만들 수 없게 된다. 리팩터링하면서 기능이 사라지는 것이다.

      

    

  


  

    
판단 문제 3. AWS 하나에 테스트용 가짜만

    
다른 팀은 앞으로도 AWS만 쓸 예정이고, 추상화가 필요한 이유는 단위 테스트에서 S3·SQS 대신 가짜 객체를 쓰기 위해서뿐이다. 이 팀에 추상 팩토리를 권하겠는가, 아니면 생성자 주입만으로 충분한가? 판단 근거를 쓰고, 어떤 조건이 생기면 추상 팩토리로 옮겨 갈지도 쓰라.

    

      해설 보기
      
생성자 주입으로 충분하다. 서비스가 BlobStorage, MessageQueue를 (Protocol 타입으로) 생성자 인자로 받고, 운영 코드의 composition root에서 S3Storage와 SqsQueue를 만들어 넘기면 된다. 테스트는 인메모리 가짜를 넘긴다. 추상 팩토리가 주는 고유한 이득은 "제품군을 섞지 못하게 하는 것"인데, 운영 제품군이 하나뿐이면 섞을 대상이 없다. 테스트에서 가짜 저장소와 실제 큐를 섞어 쓰는 것은 오히려 원하는 유연성일 수 있다(통합 테스트, 곧 여러 구성 요소나 실제 외부 시스템을 함께 연결해 검증하는 테스트에서 일부만 실제로).

      
옮겨 갈 조건: (1) 두 번째 운영 제품군(다른 클라우드, 온프레미스, 곧 조직이 직접 보유·운영하는 서버 환경)이 생길 때, (2) 제품들이 같은 세션(여기서는 SDK가 자격 증명과 설정을 묶어 들고 있는 연결 단위)·자격 증명·리전을 공유해 "같이 만들어져야" 할 때, (3) 제품 생성 지점이 composition root 밖으로 퍼져 나갈 때(예: 요청마다 새 큐 클라이언트를 만들어야 하는 구조). 이 중 하나라도 생기면 생성 결정을 묶을 이유가 생긴다.

      
흔한 오답은 "테스트 가짜도 하나의 제품군이니 FakeFactory를 만들자"이다. 형식적으로는 맞지만, 테스트마다 일부 제품만 바꾸고 싶을 때 팩토리 전체를 새로 정의해야 하므로 테스트가 더 번거로워진다. 패턴이 "가능하다"는 것과 "이득이 있다"는 것은 다르다.
