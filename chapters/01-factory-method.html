학습 목표

  1. 상위 클래스(프레임워크)가 객체를 언제 만들지 결정하고 하위 클래스가 무엇을 만들지 결정하는 역할 분담을 설명할 수 있다.
  2. 단순 팩토리(Simple Factory, 조건문으로 고르는 함수)와 팩토리 메서드(상속 기반 생성 훅)를 구별하고, 각각에서 "새 종류 추가"의 비용을 누가 치르는지 비교할 수 있다.
  3. 파이썬에서 생성 함수 주입, classmethod 대체 생성자, __init_subclass__ 자동 등록으로 같은 의도를 구현하고, 각각이 GoF 의도에서 얼마나 멀어지는지 판단할 수 있다.

1. 상황

한빛대학교 화학과 분석화학 연구실의 박사과정생 서윤은 실험 자동화를 맡았다. 첫 과제는 단순했다. 연구실의 UV-Vis 분광광도계(자외선·가시광선을 시료에 비춰 파장별 흡광도를 재는 분석 장비)는 측정이 끝나면 CSV(쉼표로 필드를 구분하고 한 줄에 한 레코드를 적는 텍스트 표 형식) 파일을 내보내는데, 그것을 읽어 세기를 정규화하고(장비마다 다른 세기 단위를 비교할 수 있게 최댓값을 1.0에 맞추는 것) 연구실 데이터 아카이브에 저장하는 작업을 매번 손으로 하고 있었다. 서윤은 AcquisitionJob이라는 클래스를 만들고, run() 하나에 "장비 연결 → 측정 데이터 읽기 → 정규화 → 저장"을 순서대로 넣었다. 읽기는 run() 안에서 CsvSpectrumReader()를 직접 만들어 처리했다. 장비가 하나뿐이니 이것으로 충분했다.

석 달 뒤 공동 연구를 하는 생화학 연구실에서 질량분석기(시료를 이온화해 질량 대 전하비 m/z별 세기를 재는 장비)를 들여왔다. 이 장비는 CSV가 아니라 제조사 고유의 바이너리 포맷을 쓴다. 같은 시기에 새로 산 장비는 시리얼 포트(장비를 연결해 데이터를 한 비트씩 차례로 주고받는 단자)로 JSON(키와 값의 쌍으로 된 객체와 배열을 텍스트로 적는 데이터 형식) 프레임을 흘려보낸다. 서윤은 가장 빠른 길을 택했다. run() 안에 if device == "uv-vis" / elif device == "mass-spec" / elif device == "serial-json" 분기를 넣었고, 시리얼 장비에만 필요한 port 인자를 AcquisitionJob의 생성자에 추가했다.

문제는 그다음에 왔다. 학과가 이 코드를 공용 저장소로 옮겨 다섯 개 연구실이 함께 쓰기로 한 것이다. 재료공학 연구실은 X선 회절계(XRD)(X선을 쏘아 회절 각도별 세기로 결정 구조를 분석하는 장비)를 붙이고 싶어 했지만, 그러려면 공용 프레임워크(전체 흐름을 쥐고 각 연구실의 코드를 정해진 자리에서 불러 주는 공용 골격 코드)의 run()을 고치는 PR(pull request: 공유 저장소에 변경을 합쳐 달라고 리뷰와 함께 요청하는 단위)을 보내야 했다. 다른 연구실의 장비 분기와 같은 메서드를 건드리니 리뷰는 늘 늦었고, 한 번은 다른 연구실의 PR이 분기 조건 문자열을 잘못 고쳐, 질량분석 작업이 else로 떨어져 야간 측정 전체가 멈추는 사고도 났다. 게다가 정규화 로직에 대한 단위 테스트(함수·클래스 같은 작은 단위를 실제 장비 없이 따로 검증하는 테스트)를 쓰려던 학부 연구생은 run()이 실제 리더를 이름으로 직접 만드는 탓에, 모듈 전역 이름을 바꿔치기(monkeypatch)하는 것 외에는 가짜 리더를 끼울 방법을 찾지 못했다. 몽키패치는 실행 중에 모듈이나 클래스의 이름이 가리키는 대상을 다른 것으로 갈아 끼우는 기법으로, 테스트에서 의존 대상을 바꾸는 데 쓰이지만 같은 이름을 쓰는 다른 코드까지 영향을 받는다.

정리하면 아픈 곳은 세 군데다. 측정 흐름과 리더 생성이 한 메서드에 엉켜 있어서 (1) 새 장비마다 공용 코드를 수정해야 하고, (2) 장비별 생성 인자가 모든 작업의 생성자로 새어 나오며, (3) 테스트가 끼어들 이음새(seam), 곧 코드를 고치지 않고도 다른 구현을 끼워 넣을 수 있는 지점이 없다. 흐름은 모든 장비에 공통이고 변하지 않는다. 변하는 것은 "어떤 리더를 만드는가" 단 하나다.

2. 순진한 설계와 그 한계

서윤이 분기를 추가한 직후의 코드다. 리더 클래스들 자체는 멀쩡하다. 주목할 곳은 AcquisitionJob.__init__의 port와 run() 맨 앞의 분기, 그리고 데모 [3]에서 테스트가 전역 이름을 바꿔치기하는 대목이다. 코드에 처음 나오는 표준 라이브러리 도구 몇 가지를 짚어 둔다. io.StringIO는 문자열을 파일처럼 읽고 쓰게 해 주는 메모리 버퍼이고, struct.pack은 파이썬 값을 형식 문자열(예: "<6d")에 따라 바이트열로 바꾸는 struct 모듈의 함수다. 질량분석기 포맷의 리틀엔디언은 여러 바이트로 된 수를 낮은 자리 바이트부터 저장하는 순서이고, float64는 8바이트 배정밀도 부동소수점 수다. 데모의 globals()는 현재 모듈의 전역 이름공간을 딕셔너리로 돌려주는 내장 함수로, 여기에 대입하면 모듈 전역 이름을 바꿔치기할 수 있다.


  
데모 [1]만 보면 아무 문제가 없다. 이 설계가 "틀린" 것이 아니라 변경에 대해 닫혀 있지 않다는 점이 핵심이다. [2]의 실패 메시지는 확장의 주체가 누구인지를 드러낸다. 재료공학 연구실은 자기 장비를 붙이는 데 필요한 모든 지식(포맷, 연결 방식)을 갖고 있지만, 그 지식을 꽂을 자리가 공용 코드의 if 사슬 안에만 있다. 확장할 능력이 있는 쪽과 확장할 권한이 있는 쪽이 어긋난 것이다.

  
[3]은 더 은밀한 문제다. 테스트는 통과했지만 globals()를 직접 고쳐야 했다. run()이 CsvSpectrumReader라는 이름에 정적으로 묶여 있으므로, 다른 리더를 쓰게 하려면 그 이름이 가리키는 대상을 바꾸는 수밖에 없다. DIP 관점에서 보면 상위 정책(측정 흐름)이 하위 세부(CSV 파싱 클래스, 곧 텍스트를 해석해 구조화된 데이터로 바꾸는 코드)에 직접 의존하고 있다.

  

    흔한 첫 시도와 그 한계
    분기를 make_reader(device)라는 별도 함수로 빼내는 것은 좋은 첫걸음이다. 이것을 단순 팩토리(Simple Factory)라 부른다. 생성 지식이 한곳에 모이고 run()은 깨끗해진다. 그러나 새 장비를 추가하려면 여전히 그 함수를 고쳐야 한다. 생성 코드를 옮겼을 뿐, 확장의 주도권은 여전히 프레임워크 소유자에게 있다.
  






  
3. 패턴의 구조

  
GoF는 팩토리 메서드의 의도를 이렇게 쓴다. "객체를 생성하기 위한 인터페이스를 정의하되, 어떤 클래스의 인스턴스를 만들지는 서브클래스가 결정하게 한다. 팩토리 메서드는 클래스의 인스턴스화를 서브클래스로 미룬다." 여기서 눈여겨볼 단어는 미룬다(defer)이다. 생성 자체는 여전히 상위 클래스의 흐름 안에서 일어난다. 상위 클래스는 생성이 필요한 시점을 알고, 하위 클래스는 만들 대상을 안다. 아래 그림에 나오는 UML 스테레오타입, 곧 «create»처럼 꺾쇠로 붙인 꼬리표는 관계나 요소의 의미를 덧붙여 표시한다(«create»는 "이 클래스가 저 클래스를 생성한다").

  
  

    
역할이 장의 클래스책임

    
      
제품(Product)Reader흐름이 의존하는 추상. 장비 고유 포맷을 공통 Sample로 번역하는 계약.

      
구체 제품(Concrete Product)CsvSpectrumReader 등장비 하나의 포맷 지식.

      
생성자(Creator)AcquisitionJob흐름(run())을 소유하고, 그 안에서 팩토리 메서드 create_reader()를 호출한다.

      
구체 생성자(Concrete Creator)UvVisJob, MassSpecJob 등create_reader()를 오버라이드해 어느 구체 제품을 만들지 결정한다.

    
  

  
그림에서 두 계층이 평행하게 자라는 것을 볼 수 있다. Creator 계층과 Product 계층이 같은 축(장비 종류)을 따라 나란히 늘어나는 이 모양을 평행 클래스 계층(parallel class hierarchies)이라 부르며, 팩토리 메서드의 대표적인 결과이자 비용이다. 또 하나 짚을 점: run()은 구조적으로 템플릿 메서드(14장)다. 고정된 알고리즘의 한 단계를 하위 클래스에 맡기는데, 그 단계가 마침 "생성"인 경우가 팩토리 메서드다.






  
4. 패턴 적용

  
이제 run()에서 분기를 걷어 내고 "리더를 만든다"는 단계를 추상 메서드 create_reader()로 떼어 낸다. 읽을 때 세 가지를 확인하라. run() 본문에 구체 리더 이름이 하나라도 남아 있는가? port는 어디로 옮겨 갔는가? 파일 아래쪽 "다른 연구실의 코드" 구획이 위쪽 프레임워크를 한 줄이라도 고치는가? Sample docstring의 "불변"은 생성된 뒤 상태를 바꿀 수 없다는 뜻이다(frozen=True가 그것을 보장한다). 데모 [3]의 assert는 조건이 거짓이면 AssertionError를 내는 개발용 확인 문장인데, python -O로 실행하면 통째로 제거되므로 테스트 확인에는 쓰되 입력 검증에는 쓰지 않는다.

  
  

  
[1]에서 호출자는 job.run()만 부른다. 장비를 고르는 결정은 "어떤 작업 클래스를 인스턴스화하는가"로 한 번, 맨 바깥에서 내려졌고, 그 뒤로는 다형성이 일을 한다. naive 버전의 if 사슬은 사라진 것이 아니라 클래스 선택으로 대체되었다. 이 차이가 중요하다. if 사슬은 닫힌 목록이지만 하위 클래스 집합은 열린 목록이다.

  
[2]가 이 장의 요점이다. 재료공학 연구실은 XrdReader와 XrdJob을 추가했을 뿐 공용 프레임워크는 그대로다. 확장할 지식을 가진 쪽이 자기 코드 안에서 확장을 끝낸다. 동시에 port는 그것이 필요한 유일한 곳인 SerialJsonJob으로 옮겨 갔다. 생성 지식이 제자리를 찾으면 생성 인자도 함께 제자리를 찾는다.

  
[3]의 테스트는 naive 버전의 전역 바꿔치기와 비교해 보라. 테스트는 프레임워크가 공식적으로 열어 둔 확장 지점, 즉 create_reader()를 통해 들어온다. 이음새가 설계의 일부가 된 것이다. [4]는 ABC를 고른 이유를 보여준다. 팩토리 메서드 구현을 잊은 Concrete Creator는 첫 측정 때가 아니라 인스턴스를 만드는 순간 실패한다.

  

    핵심 정리
    팩토리 메서드는 "생성 코드를 어딘가로 옮기는" 기법이 아니다. 생성 결정을 상속 계층의 확장 지점으로 만드는 기법이다. 그래서 판별 질문은 하나다. "새 제품을 추가할 때, 기존 클래스를 수정하는가, 하위 클래스를 추가하는가?"
  






  
5. 파이썬다운 변형

  
02의 Concrete Creator들을 다시 보면 하는 일이 create_reader() 한 줄뿐이다. Java 같은 언어에서는 "생성 방법"을 값으로 넘기기가 번거로웠기 때문에 메서드 하나를 바꾸려고 클래스를 하나 만드는 것이 자연스러웠다. 파이썬에서는 클래스 자체가 호출 가능한 객체이고, 함수도 일급 값이다. 그렇다면 하위 클래스 계층 없이 같은 분담을 얻을 수 있지 않을까?

  
생성 함수 주입과 대체 생성자

  
대체 생성자는 같은 타입을 다른 입력 형식(설정 dict, 타임스탬프 등)에서 만드는 이름 붙은 생성 진입점이다. 생성자 오버로딩이 없는 파이썬에서는 흔히 @classmethod로 만든다. @classmethod를 붙인 메서드는 인스턴스 대신 클래스 자체를 첫 인자 cls로 받으므로, 하위 클래스에서 부르면 cls가 그 하위 클래스가 된다. 아래 코드는 create_reader() 오버라이드를 생성자 인자 reader_factory로 바꾼다. 리더 인스턴스가 아니라 만드는 방법을 받는다는 점, Reader가 Protocol이 되어 리더들이 아무것도 상속하지 않는다는 점, 그리고 from_config()의 docstring이 그것을 "GoF 팩토리 메서드가 아니다"라고 말하는 이유에 주목하라. 새로 나오는 도구도 있다. functools.partial은 함수의 인자 일부를 미리 채운 새 호출 가능 객체를 만든다. 타입 힌트의 ClassVar는 그 속성이 인스턴스가 아니라 클래스 전체에 속한다고 표시하고, Any는 어떤 타입이든 허용한다는 표시로 그 자리의 타입 검사를 사실상 끈다. docstring의 "런타임"은 프로그램이 실제로 실행되는 시점을 말하며, 코드를 실행하지 않고 검사하는 정적 검사 시점과 대비된다.

  
  

  
[1]과 [2]에서 클래스 CsvSpectrumReader와 partial(SerialJsonReader, port=...)가 똑같이 "인자 없이 호출하면 리더가 나오는 것"으로 취급된다. [3]의 생성 기록은 이 변형이 팩토리 메서드의 본질 하나를 지킨다는 것을 보여준다. 리더가 만들어지는 시점은 여전히 run()이 결정한다. 인스턴스를 바로 넘기게 했다면 이 통제가 호출자에게 넘어갔을 것이다(장비 연결처럼 생성이 비싸거나 부수 효과, 곧 값을 돌려주는 것 외에 바깥 상태를 바꾸는 일이 있을 때 결정적인 차이다).

  
이것은 구조적으로 전략 패턴(10장)이다. 상속으로 변이를 다루던 것을 합성으로 바꿨고, 변이의 내용이 "생성"일 뿐이다. 그렇다면 02의 하위 클래스 방식은 언제 여전히 필요한가? Concrete Creator가 create_reader() 말고도 normalize()나 save() 같은 다른 단계도 함께 바꿔야 할 때다. 여러 훅을 일관되게 묶어 바꾸는 단위로는 클래스가 함수 여러 개를 따로 넘기는 것보다 낫다. 또 프레임워크 사용자가 "XrdJob"이라는 이름 붙은 개념을 문서·IDE(편집·실행·디버깅·자동 완성을 한데 묶은 통합 개발 환경)에서 발견할 수 있다는 점도 가치다.

  
[4]의 from_config()는 이름 때문에 혼동이 잦다. 파이썬 커뮤니티에서는 @classmethod 대체 생성자를 흔히 "팩토리 메서드"라 부르지만, 무엇을 만들지 결정하는 것이 하위 클래스가 아니라 데이터(설정의 device 키)이고, 내부는 표를 조회하는 단순 팩토리다. 그래서 "xrd"를 지원하려면 결국 DEVICES 표를 고쳐야 한다. 확장의 주도권 문제로 되돌아온 것이다.


  
정의하는 순간 등록되는 레지스트리

  
레지스트리는 이름(키)과 클래스·함수를 짝지어 둔 표다. 호출자는 분기 대신 표를 조회하고, 새 항목은 표에 등록만 하면 추가된다. 설정 문자열로 장비를 고르고 싶으면서도 "추가만으로 확장"을 지키려면, 표를 프레임워크가 쥐고 있지 않으면 된다. 다음 코드는 __init_subclass__로 Reader 하위 클래스가 class XrdReader(TextColumnReader, device="xrd")처럼 정의되는 순간 스스로 등록되게 한다. device 없이 상속한 중간 클래스 TextColumnReader가 등록되지 않는 것, 중복 키를 정의 시점에 거부하는 것, 그리고 마지막 [5]의 함정을 눈여겨보라.

  

    용어
    코드 주석에 처음 나오는 말들이다. 메타클래스는 클래스를 만들어 내는 클래스(기본은 type)로, 클래스가 생성되고 호출되는 방식을 바꿀 수 있지만 상속 계층 전체에 전파되고 다른 메타클래스와 충돌할 수 있다. 키워드 전용 인자는 매개변수 목록의 * 뒤에 두어 반드시 이름=값으로만 넘길 수 있게 한 인자다. 선언적이라는 말은 "어떻게"의 절차 대신 "무엇"을 원하는지를 적는 방식을 뜻한다. 협력적 다중 상속은 계층의 각 클래스가 super()로 다음 클래스에 호출을 넘겨, 여러 부모의 같은 메서드가 빠짐없이 차례로 실행되게 하는 관례다. raise … from None은 예외 연쇄 문법의 한 형태다. raise 새예외 from e는 원인 예외 e를 새 예외에 기록하고, from None은 원인 표시를 숨겨 사용자에게 필요한 메시지만 남긴다. 마지막 데모의 진입점(entry points)은 설치된 패키지가 "이 이름으로 이 객체를 제공한다"고 메타데이터에 선언해, 다른 프로그램이 직접 import하지 않고도 플러그인을 찾게 하는 파이썬 패키징 장치다.
  

  
  

  
[2]와 [3]을 나란히 보면 레지스트리의 성격이 드러난다. 프레임워크 코드는 한 글자도 바뀌지 않았는데, 클래스 정의가 실행되자 장비 목록이 늘었다. __init_subclass__는 파이썬 3.6에서 들어온 훅으로, 예전에는 메타클래스로 하던 일을 훨씬 가볍게 해 준다. 특히 Reader가 이미 ABCMeta를 쓰고 있어서 별도 메타클래스를 섞으면 충돌을 해결해야 하는데, __init_subclass__는 그 문제가 없다.

  
엄밀히 말해 이것은 더 이상 GoF 팩토리 메서드가 아니다. Creator의 하위 클래스가 생성을 결정하지 않고, AcquisitionJob은 상속 계층조차 갖지 않는다. 남은 것은 팩토리 메서드가 노리던 결과, 즉 "새 제품은 추가만으로"다. [5]가 대가다. 등록이 import라는 부수 효과에 기대므로, 누군가 그 모듈을 import하지 않으면 코드가 분명히 있는데도 장비가 "없다". 명시적 상속 계층에서는 생길 수 없는 종류의 버그다.

  

    
방식무엇을 만들지 결정하는 주체새 장비 추가 비용GoF 의도와의 거리

    
      
naive / 단순 팩토리프레임워크의 조건문공용 코드 수정패턴 아님

6. 트레이드오프와 관련 패턴

  
얻는 것. 흐름을 가진 코드가 구체 클래스를 모르게 된다(DIP). 새 제품은 하위 클래스 추가로 끝난다(OCP). 생성 인자가 그것을 아는 클래스로 모인다. 테스트용 이음새가 설계의 일부로 생긴다.

  
치르는 것. 제품 하나를 위해 Creator 하위 클래스가 하나 더 생긴다(평행 계층). 상속은 정적이므로 실행 중에 생성 방식을 바꿀 수 없다. 그리고 "이 작업은 무엇을 만드는가"를 알려면 하위 클래스를 따라 내려가야 하므로 코드 추적이 한 단계 간접적이 된다.

  

    이 패턴을 쓰지 말아야 할 때
    
    
      
  • 제품 종류가 닫혀 있고 확장 주체가 내부 팀뿐일 때. 장비가 두 종류이고 앞으로 늘 계획이 없다면 단순 팩토리 함수 하나가 더 읽기 쉽다. 평행 계층은 "제3자가 확장한다"는 전제가 있을 때 값을 한다.
    • 
      
  • 변하는 것이 생성 하나뿐이고 흐름을 상속할 이유가 없을 때. 파이썬에서는 생성 함수를 주입하는 편(03)이 싸다. 하위 클래스 하나가 메서드 한 줄을 위해 존재한다면 설계가 언어를 거스르고 있다는 신호다.
    • 
      
  • 생성 흐름을 소유한 상위 클래스가 없을 때. 그냥 "객체를 만들어 주는 함수"가 필요하다면 그것은 팩토리 함수이지 팩토리 메서드가 아니다. 패턴 이름을 붙이려고 추상 클래스를 만들지 않는다.
    • 
      
  • 테스트 때문에만 도입하려 할 때. 테스트 이음새가 유일한 동기라면 생성자 주입이 더 직접적이다.
    • 
    

  

  
관련 패턴.

  
    
    
  • 추상 팩토리(2장): 팩토리 메서드가 "제품 하나"의 생성을 미룬다면, 추상 팩토리는 함께 쓰여야 하는 제품 여러 개의 생성 메서드를 한 객체에 묶는다. 추상 팩토리의 각 create_*는 대개 팩토리 메서드로 구현된다.

7. 연습문제


  

    
개념 문제 1. 표준 라이브러리의 "팩토리 메서드"

    
datetime.fromtimestamp()와 dict.fromkeys()는 문서와 블로그에서 흔히 팩토리 메서드라 불린다. GoF의 의도("어떤 클래스의 인스턴스를 만들지는 서브클래스가 결정한다")를 기준으로 이 둘이 GoF 팩토리 메서드인지 판별하라. 하위 클래스에서 이 메서드를 호출하면 무엇이 반환되는지 실험해 보고, 그 결과가 판별에 어떤 영향을 주는지도 논하라.

    

      해설 보기
      
둘 다 GoF 팩토리 메서드가 아니라 대체 생성자다. 판별 근거는 두 가지다. 첫째, 만들 클래스는 호출자가 수신 클래스(Cls.method()에서 점 앞에 온 클래스, 곧 @classmethod의 cls로 전달되는 클래스)를 고르는 순간 정해진다. datetime.fromtimestamp(...)라고 쓴 코드는 이미 "datetime을 달라"고 말했다. 프레임워크의 흐름이 훅을 부르고 하위 클래스가 답하는 간접층이 없다. 둘째, 생성된 객체를 사용하는 Creator 쪽 연산(02의 run())이 없다. 이 메서드들의 목적은 "같은 타입을 다른 입력 형식에서 만들기", 즉 생성자 오버로딩이 없는 파이썬에서 이름 붙은 생성자를 제공하는 것이다.

      
흔한 오답은 "하위 클래스에서 부르면 하위 클래스 인스턴스가 나오니 서브클래스가 결정한다"는 논리다. 아래 실험처럼 실제로 하위 클래스 인스턴스가 나온다. 그러나 그것은 cls를 통해 생성하는 classmethod의 일반적 성질일 뿐, 하위 클래스가 생성 결정을 오버라이드한 결과가 아니다. 결정은 여전히 호출자의 몫이다.

      

    

  


  

    
리팩터링 문제 2. 로그 수집기

    
연구실 서버 관리자가 쓴 다음 로그 수집기를 (1) GoF 팩토리 메서드로, (2) 이어서 __init_subclass__ 레지스트리로 리팩터링하라. 두 번째 단계에서는 "nginx"(널리 쓰이는 웹 서버로, 요청마다 접근 로그를 남긴다), "apache" 같은 설정 문자열로 수집기를 고를 수 있어야 하고, 새 형식은 프레임워크 수정 없이 클래스 정의만으로 추가되어야 한다. 코드의 re.match는 문자열 패턴을 기술하는 작은 언어인 정규식을 다루는 re 모듈 함수이고, 5xx는 웹에서 요청과 응답을 주고받는 프로토콜인 HTTP의 응답 상태 코드(결과를 나타내는 세 자리 숫자) 중 서버 오류(500번대)를 뜻한다.

    
import re

class LogCollector:
    """웹 서버 접근 로그에서 IP별 5xx 오류 수를 센다."""

    def __init__(self, fmt: str) -> None:
        self.fmt = fmt  # "nginx" 또는 "apache"

    def collect(self, lines: list[str]) -> dict[str, int]:
        errors: dict[str, int] = {}
        for line in lines:
            # 문제: 줄마다 형식 분기 — 흐름과 파싱 결정이 엉켜 있다
            if self.fmt == "nginx":
                m = re.match(r'^(\S+) .*?" (\d{3}) ', line)
                ip, status = m.group(1), int(m.group(2))
            elif self.fmt == "apache":
                status_s, ip, _ = line.split("|")
                status = int(status_s)
            else:
                raise ValueError(self.fmt)
            if status >= 500:
                errors[ip] = errors.get(ip, 0) + 1
        return errors

    

      해설 보기
      
먼저 변하는 것(한 줄을 해석하는 방법)과 변하지 않는 것(줄을 돌며 5xx를 세는 흐름)을 가른다. 변하는 것을 LogParser 제품 계층으로 빼내고, collect()는 그 안에서 팩토리 메서드 create_parser()를 부른다. 원래 코드는 줄마다 분기했지만 이제 파서는 collect() 시작 시 한 번 만들어진다. 생성 시점이 흐름 안에 명확히 자리 잡은 것이다. 데모의 nginx 로그 줄에 보이는 GET·POST는 HTTP 요청의 동작 종류(GET은 조회, POST는 생성·변경)다.

      
2단계에서는 Product가 아니라 Concrete Creator를 등록했다. 본문 04는 리더(Product)를 등록했다. 어느 쪽이든 된다. 판단 기준은 "설정 문자열이 고르는 단위가 무엇인가"다. 형식마다 수집 흐름의 다른 단계까지 바뀔 가능성이 있다면 Creator를 등록하는 편이 낫다.

      
흔한 오답은 create_parser() 안에 if self.fmt == ...를 그대로 옮기는 것이다. 메서드 이름은 팩토리 메서드지만 하위 클래스가 결정하지 않으므로 단순 팩토리를 메서드로 옮긴 것에 불과하다. 또 하나 따져 볼 변형은 __init__에서 self.parser = self.create_parser()로 파서를 미리 만들어 두는 것이다. 오버라이드는 그대로 동작하므로 하위 클래스로 바꿔 끼우는 데는 문제가 없다. 진짜 함정은 두 가지다. 첫째, 생성자에서 팩토리 메서드를 부르면 하위 클래스가 super().__init__() 뒤에 설정하는 상태가 아직 없다. 본문의 SerialJsonJob처럼 port를 super().__init__() 다음에 저장하는 하위 클래스라면 create_reader()가 AttributeError를 낸다. 둘째, 생성 시점이 "실행할 때"에서 "객체를 만들 때"로 당겨진다. 장비 연결처럼 생성이 비싸거나 부수 효과가 있으면, 실행되지 않을 작업까지 자원을 잡는다(본문 03 데모 [3]이 지킨 성질이다).

      

    

  


  

    
판단 문제 3. 장비가 두 종류뿐이라면

    
서윤의 연구실만 쓰는 프레임워크이고 장비는 UV-Vis와 질량분석기 두 종류뿐이다. 앞으로 늘릴 계획도 없다. 이때 단순 팩토리 함수(make_reader(device))와 팩토리 메서드 중 무엇을 고르겠는가? (a) 확장 주체가 내부 팀인가 외부 연구실인가, (b) 테스트 용이성, 두 관점에서 근거를 들어 논하라. 상황이 어떻게 바뀌면 결론이 뒤집히는지도 쓰라.

    

      해설 보기
      
단순 팩토리 함수가 낫다. (a) 확장 주체가 내부 팀뿐이면 "공용 코드를 수정해야 한다"는 비용이 사실상 없다. 고치는 사람과 코드 소유자가 같기 때문이다. 팩토리 메서드의 평행 계층은 제3자가 프레임워크를 수정하지 않고 확장해야 할 때 비용을 회수하는데, 그 전제가 없다. 닫힌 두 갈래 분기는 한 화면에 다 보이는 편이 오히려 읽기 쉽다. (b) 테스트 용이성은 팩토리 메서드만의 장점이 아니다. AcquisitionJob이 생성 함수나 리더를 생성자 인자로 받게 하면(03의 방식) 단순 팩토리와 함께 써도 이음새가 생긴다. 즉 "테스트를 위해 팩토리 메서드가 필요하다"는 논리는 성립하지 않는다.

      
결론이 뒤집히는 조건: 다른 연구실이 같은 코드를 쓰기 시작해 확장 주체가 외부로 넘어갈 때, 또는 장비마다 정규화·저장 같은 다른 단계도 함께 달라져 "생성 + 다른 훅"을 한 단위로 묶어 바꿀 필요가 생길 때다. 앞의 경우는 레지스트리(04)도 후보이고, 뒤의 경우는 하위 클래스 방식(02)이 가장 자연스럽다.

      
흔한 오답은 "나중에 늘 수도 있으니 미리 패턴을 적용한다"이다. 두 갈래 if를 팩토리 메서드로 바꾸는 데는 몇 분이면 충분하다. 바꾸는 비용이 낮은 결정을 미리 내려 두는 것은 YAGNI("You Aren't Gonna Need It": 실제로 필요해지기 전에는 기능이나 추상화를 미리 만들지 말라는 원칙) 위반이고, 그동안 모든 독자가 불필요한 간접층을 읽는 비용을 치른다.
