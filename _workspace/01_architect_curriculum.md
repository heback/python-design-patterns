# 커리큘럼 설계서 — 파이썬으로 배우는 디자인 패턴

## 전제와 가정
- 대상: 객체지향 개념(캡슐화, 다형성, SOLID, 합성 vs 상속)을 깊이 이해한 학생. OOP 기초 설명은 넣지 않는다.
- 범위: `pattern-chapter-writing` 스킬 "장 목록" 표의 15개 패턴 + 서론(00) + 종합(99). 번호·슬러그·경로는 표를 그대로 따른다.
  - 원고 `chapters/{nn}-{slug}.html`, 코드 `src/{nn}_{slug_with_underscores}/`
- 공통 요구: 코드는 반드시 맥락(상황) 뒤에 제시, 모든 코드에 "왜"를 말하는 자세한 주석, 장마다 연습문제 3~4개 + 해설.
- 연습문제 아이디어는 아래 3유형을 기본으로 한다: (a) 개념/판단, (b) 리팩터링, (c) 패턴 선택 판단. 집필자는 스킬 형식에 맞춰 "확장" 또는 "비교" 문제를 1개 더해도 된다.
- 시나리오 인물·회사명은 가상이다. 17개 장의 도메인은 서로 겹치지 않는다(아래 도메인 배정표).

## 장 간 연결 지도 (집필자 공통 참고)
- 생성: 팩토리 메서드(01) → 추상 팩토리(02)는 "팩토리 메서드의 묶음"으로 발전. 빌더(03)는 "한 번에 만들기 어려운 하나의 객체", 추상 팩토리는 "함께 쓰여야 하는 여러 객체". 싱글턴(04)은 "팩토리가 하나만 있으면 될 때" 흔히 오남용되는 지점으로 연결.
- 구조: 어댑터(05)·데코레이터(06)·프록시(09)는 모두 "다른 객체를 감싼다". 차이는 의도: 인터페이스 변환 / 동일 인터페이스로 책임 추가 / 동일 인터페이스로 접근 제어. 컴포지트(07)는 데코레이터와 재귀 합성 구조를 공유. 퍼사드(08)는 "인터페이스 단순화"로 어댑터와 대비.
- 행위: 전략(10) ↔ 상태(13)는 구조가 같고 "누가 교체를 결정하는가"가 다르다. 전략(10) ↔ 템플릿 메서드(14)는 합성 vs 상속으로 알고리즘 변이를 다루는 두 방법. 커맨드(12)는 "요청의 객체화", 옵저버(11)는 "통지의 분리"로, 커맨드+옵저버 조합(이벤트 → 명령 실행)을 99에서 다룬다. 반복자(15)는 컴포지트(07) 순회와 직접 연결.
- 파이썬 관점 축: "언어가 패턴을 흡수하는 정도"를 장마다 판단하게 하고, 99에서 표로 총정리한다(일급 함수 → 전략/커맨드, 제너레이터 → 반복자, 모듈 → 싱글턴/퍼사드, `__getattr__` → 어댑터/프록시, 데코레이터 문법 → 데코레이터 패턴(같은 이름, 다른 개념)).

## 00 서론: OOP 원리에서 패턴으로

- **번호/슬러그/패턴명/분류**: 00 / intro / 서론: OOP 원리에서 패턴으로 / —
- **학습목표 3개**
  1. 디자인 패턴을 "OOP 원리가 반복되는 설계 문제에서 굳어진 해법"으로 설명하고, GoF의 의도(intent)·참여자·결과(consequences) 틀을 읽을 수 있다.
  2. "변하는 것을 찾아 캡슐화하라", "구현이 아닌 인터페이스에 프로그래밍하라", "상속보다 합성" 세 원칙이 이후 15개 패턴의 공통 뿌리임을 사례로 보일 수 있다.
  3. 파이썬의 언어 기능(일급 함수, 덕 타이핑, 프로토콜, 모듈)이 일부 패턴을 단순화·소거한다는 관점을 갖고, 이 교재의 장 구성(상황 → 순진한 설계 → 구조 → 적용 → 파이썬다운 변형 → 트레이드오프 → 연습문제)을 이해한다.
- **시나리오**
  - 도메인: 공공 도서관 대출 시스템
  - 초기 요구: 사서 지민이 반납일을 넘긴 도서의 연체료(일당 100원)를 계산하는 스크립트를 만든다. 함수 하나로 충분하다.
  - 변경 요구 1: 아동 회원은 50% 감면, DVD는 일당 500원, 시험 기간에는 대학생 연체료 면제.
  - 변경 요구 2: 시청이 "구립 도서관 3곳의 정책을 각자 다르게" 운영하겠다고 한다.
  - 고통 지점: `if/elif`가 자료 유형 × 회원 유형 × 기간 × 지점으로 곱해진다. 새 규칙마다 같은 함수를 수정하고 기존 규칙이 깨진다(OCP 위반, 변경 이유가 여럿인 함수 — SRP 위반).
- **실현하는 OOP 원칙**: 서론 자체가 원칙 정리 장이다. 위 사례를 "변하는 것(요율 규칙)을 분리 → 인터페이스 뒤로 숨김 → 합성으로 조립"의 3단계로 리팩터링해, 이것이 곧 전략 패턴의 씨앗임을 보이고 10장으로 예고한다.
- **파이썬다운 변형 주제**: `abc.ABC` vs `typing.Protocol`(명목적 vs 구조적 타이핑)의 선택 기준을 이 장에서 한 번 정리해 이후 장이 재설명하지 않게 한다. 일급 함수로 규칙을 넘기는 버전도 짧게 보이고 "클래스가 필요한 순간은 언제인가"라는 질문을 교재 전체의 반복 질문으로 제시한다.
- **관련 패턴**: 전략(10, 직접 예고), 템플릿 메서드(14, 상속 기반 대안), 팩토리 메서드(01, 규칙 객체를 누가 만드는가).
- **섹션 구성안** (`goals` 필수, 나머지 id 영문 자유)
  1. `goals` 학습 목표

  4. `gof-anatomy` 패턴을 읽는 법: 의도·동기·참여자·협력·결과, 그리고 분류(생성/구조/행위)

  6. `how-to-read` 이 교재의 구성과 장별 도메인 지도(위 배정표를 요약한 표, 장 간 연결 지도 SVG 1개 권장)

## 01 팩토리 메서드

- **번호/슬러그/패턴명/분류**: 01 / factory-method / 팩토리 메서드 (Factory Method) / 생성
- **학습목표 3개**
  1. 프레임워크(상위 클래스)가 "언제" 만들지 결정하고 하위 클래스가 "무엇을" 만들지 결정하는 역할 분담을 설명할 수 있다.
  2. 단순 팩토리(Simple Factory, 조건문 함수)와 팩토리 메서드(상속 기반 훅)를 구별하고 각각의 확장 비용을 비교할 수 있다.
  3. 파이썬에서 `classmethod` 대체 생성자·레지스트리·`__init_subclass__` 자동 등록으로 같은 의도를 구현하고 그 득실을 판단할 수 있다.
- **시나리오**
  - 도메인: 대학 화학 연구실의 측정 장비 데이터 수집 프레임워크
  - 초기 요구: 박사과정 서윤이 분광광도계(UV-Vis) 한 대의 CSV 출력을 읽어 정규화·저장하는 `AcquisitionJob`을 만든다. 작업 흐름(연결 → 측정 데이터 읽기 → 단위 정규화 → 저장)은 `run()` 안에 고정돼 있고, 내부에서 `CsvSpectrumReader()`를 직접 생성한다.
  - 변경 요구 1: 공동 연구실에서 들여온 질량분석기는 장비 고유 바이너리 포맷, 신형 장비는 JSON over 시리얼을 쓴다.
  - 변경 요구 2: 연구실마다 자기 장비 리더를 추가하고 싶지만 프레임워크 코드는 공용 저장소라 함부로 못 고친다.
  - 고통 지점: `run()` 안에 `if device == ...` 분기가 생기고, 새 장비마다 공용 프레임워크를 수정해야 한다. 흐름 로직과 생성 로직이 한 메서드에 엉켜 테스트 시 가짜 리더를 끼울 수도 없다.
- **실현하는 OOP 원칙**: DIP — 상위 흐름(`AcquisitionJob.run`)은 추상 `Reader`에만 의존하고 구체 클래스 생성은 하위 클래스의 `create_reader()`로 미룬다. OCP — 새 장비는 하위 클래스 추가로 끝난다.
- **파이썬다운 변형 주제**: (1) 생성 함수(callable)를 생성자 인자로 주입해 상속을 없애는 방법, (2) `dict[str, type[Reader]]` 레지스트리, (3) `__init_subclass__(device=...)`로 하위 클래스가 정의되는 순간 자동 등록, (4) `@classmethod from_config()` 대체 생성자 — 이것도 "팩토리 메서드"라고 불리지만 GoF의 의도와 다르다는 점을 짚는다.
- **관련 패턴**: 추상 팩토리(02, 팩토리 메서드의 묶음으로 발전), 템플릿 메서드(14, 팩토리 메서드는 템플릿 메서드의 한 단계가 "생성"인 특수 사례), 전략(10, 생성 함수 주입은 생성 전략).
- **연습문제 아이디어 3개**
  1. (개념) `datetime.fromtimestamp`, `dict.fromkeys`는 GoF 팩토리 메서드인가? 의도(하위 클래스가 생성 결정)를 기준으로 판별하고 이유를 쓰기.
  2. (리팩터링) 로그 수집기에서 `if fmt == "nginx": ... elif fmt == "apache": ...`로 파서를 만드는 20줄 코드를 팩토리 메서드로, 이어서 `__init_subclass__` 레지스트리로 바꾸기.
  3. (판단) 장비가 두 종류뿐이고 앞으로 늘 계획이 없다면 단순 팩토리 함수와 팩토리 메서드 중 무엇을 고를지, 테스트 용이성·확장 주체(내부 팀 vs 외부 연구실) 관점에서 논하기.

## 02 추상 팩토리

- **번호/슬러그/패턴명/분류**: 02 / abstract-factory / 추상 팩토리 (Abstract Factory) / 생성
- **학습목표 3개**
  1. "함께 쓰여야 하는 객체 제품군(product family)"의 일관성을 보장하는 문제를 식별하고 추상 팩토리로 해결할 수 있다.
  2. 제품군 추가(새 벤더)는 쉽고 제품 종류 추가(새 인터페이스)는 어렵다는 비대칭 트레이드오프를 설명할 수 있다.
  3. 파이썬에서 모듈·네임스페이스·`Protocol`로 제품군을 표현하는 경량 변형을 구현하고, 클래스 계층이 여전히 필요한 경우를 판단할 수 있다.
- **시나리오**
  - 도메인: 스타트업의 멀티 클라우드 인프라 계층
  - 초기 요구: 플랫폼 엔지니어 도현이 AWS 위에서 파일 업로드 서비스를 만든다. 코드 곳곳에서 `S3Storage()`, `SqsQueue()`, `SecretsManagerVault()`를 직접 생성한다.
  - 변경 요구 1: 대형 고객사가 GCP 전용 배포를 요구한다(GCS, Pub/Sub, Secret Manager).
  - 변경 요구 2: 개발자 노트북에서는 클라우드 없이 돌아가는 로컬 구현(파일 시스템, 인메모리 큐, `.env` 시크릿)이 필요하다.
  - 고통 지점: 생성 지점이 수십 곳에 흩어져 있어 환경 전환 시 모두 수정해야 하고, 실수로 `GcsStorage`와 `SqsQueue`를 섞으면 자격 증명 체계가 달라 런타임에야 실패한다. 즉 "섞이면 안 되는 조합"을 타입 구조로 막지 못한다.
- **실현하는 OOP 원칙**: DIP — 서비스 코드는 `CloudFactory`와 제품 추상(`BlobStorage`, `MessageQueue`, `SecretVault`)에만 의존. 일관성 제약을 "팩토리 하나를 고르면 제품군 전체가 정해지는" 구조로 캡슐화.
- **파이썬다운 변형 주제**: `typing.Protocol`로 제품 인터페이스를 구조적으로 정의(벤더 SDK 래퍼가 상속 없이 만족), 팩토리를 클래스 대신 "같은 이름의 함수를 가진 모듈"이나 `dataclass(frozen=True)`로 묶은 생성 함수 번들로 표현, 환경 변수로 팩토리를 고르는 진입점 1곳(composition root) 패턴.
- **관련 패턴**: 팩토리 메서드(01, 각 `create_*`가 팩토리 메서드), 싱글턴(04, 구체 팩토리는 보통 하나면 되지만 싱글턴으로 만들 필요는 없음 — 04장 예고), 퍼사드(08, 제품군 위에 단순 API를 얹는 조합), 빌더(03, 대비).
- **연습문제 아이디어 3개**
  1. (개념) 제품 종류에 "CDN"을 추가할 때 변경되는 클래스 수를 세고, 이것이 이 패턴의 어떤 결과(consequence)인지 설명하기.
  2. (리팩터링) 다크/라이트 테마에 따라 `Button`, `Dialog`를 `if theme == "dark"`로 각각 생성하는 CLI 위젯 코드(20줄)를 추상 팩토리로 바꾸기.
  3. (판단) "클라우드는 AWS 하나, 테스트용 가짜 객체만 필요"한 팀에 추상 팩토리를 권할지, 아니면 의존성 주입만으로 충분한지 판단하기.

## 03 빌더

- **번호/슬러그/패턴명/분류**: 03 / builder / 빌더 (Builder) / 생성
- **학습목표 3개**
  1. 점층적 생성자(telescoping constructor)와 반쯤 만들어진 가변 객체가 만드는 문제를 진단하고, 단계적 조립과 최종 검증을 분리하는 빌더를 적용할 수 있다.
  2. GoF 빌더(Director + Builder로 같은 절차에서 다른 표현 생성)와 유창한 인터페이스(fluent) 빌더의 차이를 설명할 수 있다.
  3. 파이썬의 키워드 인자·기본값·`dataclass`가 빌더 수요를 얼마나 줄이는지, 그럼에도 빌더가 필요한 조건(순서 제약, 교차 검증, 다중 표현)을 판단할 수 있다.
- **시나리오**
  - 도메인: 이커머스 회사 사내 BI 대시보드의 SQL 쿼리 생성
  - 초기 요구: 데이터 분석가 하은이 "기간별 매출" 차트를 위해 문자열 포매팅으로 `SELECT ... FROM orders WHERE ...`를 만든다.
  - 변경 요구 1: 필터(지역, 카테고리, 회원 등급)가 선택적으로 붙고, `GROUP BY`·`HAVING`·`ORDER BY`·`LIMIT` 조합이 대시보드마다 다르다. `HAVING`은 `GROUP BY` 없이는 무의미하다.
  - 변경 요구 2: 같은 쿼리 정의를 운영 DB(PostgreSQL)용 SQL과 분석 팀의 데이터프레임 필터 설명(사람이 읽는 요약)으로 둘 다 출력해야 한다.
  - 고통 지점: 생성자 매개변수가 10개 이상, `None` 투성이 호출, 문자열 이어 붙이기로 인한 `WHERE AND` 같은 문법 오류, 주입 위험(값을 문자열에 직접 삽입). 같은 정의를 두 표현으로 내는 코드가 중복된다.
- **실현하는 OOP 원칙**: SRP — "무엇을 질의하는가(조립 단계)"와 "어떻게 표현하는가(SQL/요약)"를 분리. 캡슐화 — 불변 결과 객체(`Query`)는 완성·검증된 상태로만 존재한다.
- **파이썬다운 변형 주제**: `return self` 체이닝의 득실(디버깅·타입 힌트 `Self`), 결과 객체는 `dataclass(frozen=True)`, `dataclasses.replace`로 불변 객체의 단계적 파생(빌더 없이도 되는 경우), `build()` 시점 교차 검증, 매개변수 바인딩으로 값과 SQL 분리.
- **관련 패턴**: 추상 팩토리(02, 대비 — 제품군 vs 단일 복합 객체), 컴포지트(07, 빌더로 트리 조립), 템플릿 메서드(14, Director의 고정 절차).
- **연습문제 아이디어 3개**
  1. (개념) `@dataclass` 하나로 충분한 경우와 빌더가 필요한 경우를 가르는 기준 3가지를 들고, 각 기준에 해당하는 예를 들기.
  2. (리팩터링) HTTP 요청을 만드는 `Request(method, url, headers=None, params=None, body=None, timeout=None, retries=None, auth=None)` 사용 코드(20줄)를 유창한 빌더로 바꾸고, `GET`에 본문이 있으면 `build()`에서 예외를 내도록 하기.
  3. (판단) 쿼리가 5종류로 고정되어 있다면 빌더 대신 "이름 붙은 팩토리 함수 5개"가 나은지 판단하기.

## 04 싱글턴

- **번호/슬러그/패턴명/분류**: 04 / singleton / 싱글턴 (Singleton) / 생성
- **학습목표 3개**
  1. "인스턴스가 하나여야 한다"와 "전역 접근점이 필요하다"는 두 요구를 분리해서 분석하고, 싱글턴이 둘을 결합할 때 생기는 비용(숨은 의존성, 테스트 격리 붕괴)을 설명할 수 있다.
  2. 파이썬의 여러 구현(`__new__`, 메타클래스, Borg, 모듈 수준 객체, `functools.cache`)을 비교하고 스레드 안전성 문제를 다룰 수 있다.
  3. 싱글턴 대신 composition root에서 하나만 만들어 주입하는 설계로 바꿀 수 있고, 싱글턴이 정당한 경우를 판단할 수 있다.
- **시나리오**
  - 도메인: 종합병원 전자의무기록(EMR) 시스템의 감사 로그
  - 초기 요구: 의료정보팀 개발자 태윤이 "누가 언제 어떤 환자 기록을 열람했는가"를 법적 요건에 따라 하나의 해시 체인 파일에 순서대로 기록하는 `AuditLogger`를 만든다. 체인 무결성을 위해 기록기는 반드시 하나여야 한다.
  - 변경 요구 1: 처방·검사·원무 모듈 모두가 감사 로그를 남겨야 한다. 각 모듈이 `AuditLogger()`를 새로 만들자 해시 체인이 갈라진다 → 싱글턴 도입.
  - 변경 요구 2: QA 팀이 모듈별 단위 테스트를 병렬로 돌리자 테스트끼리 같은 로그 인스턴스를 공유해 상태가 오염되고, 멀티스레드 웹 서버에서 초기화 경쟁이 발생한다.
  - 고통 지점: 1차 고통(인스턴스 중복)은 싱글턴이 해결하지만 2차 고통(테스트 격리, 숨은 의존성, 스레드 경쟁)은 싱글턴이 만든다. 이 장은 "해결 → 그 해결의 부작용 → 더 나은 대안"의 2단 서사로 쓴다.
- **실현하는 OOP 원칙**: 캡슐화(생성 통제)를 실현하지만 DIP와 충돌한다(구체 클래스에 대한 정적 의존). 원칙 간 긴장을 정면으로 다루는 장.
- **파이썬다운 변형 주제**: 모듈은 이미 싱글턴이다(`import` 캐시), `__new__` 재정의와 `__init__` 재호출 함정, 메타클래스 싱글턴, Borg(상태 공유), `threading.Lock` 이중 검사, `functools.cache`를 붙인 접근 함수, 테스트용 리셋 훅의 냄새.
- **관련 패턴**: 추상 팩토리(02, 구체 팩토리는 하나면 충분), 퍼사드(08, 퍼사드 객체도 흔히 하나), 프록시(09, 지연 초기화 대안), 옵저버(11, 전역 이벤트 버스가 싱글턴이 되는 흔한 경로).
- **연습문제 아이디어 3개**
  1. (개념) `__new__` 기반 싱글턴에서 `__init__`이 매번 다시 호출되어 상태가 초기화되는 버그를 재현 코드로 보이고 원인 설명하기.
  2. (리팩터링) 세 모듈이 `Config.instance()`를 직접 호출하는 코드(20줄)를 생성자 주입으로 바꾸고, 테스트에서 가짜 설정을 넣는 예를 보이기.
  3. (판단) 로깅 설정, DB 커넥션 풀, 애플리케이션 설정, 난수 생성기 — 각각 싱글턴/모듈 객체/주입 중 무엇이 적절한지 근거와 함께 고르기.

## 05 어댑터

- **번호/슬러그/패턴명/분류**: 05 / adapter / 어댑터 (Adapter) / 구조
- **학습목표 3개**
  1. 수정할 수 없는 외부 인터페이스(adaptee)를 클라이언트가 기대하는 인터페이스(target)로 변환하는 어댑터를 설계·구현할 수 있다.
  2. 객체 어댑터(합성)와 클래스 어댑터(다중 상속)의 차이를 파이썬 맥락에서 비교할 수 있다.
  3. 어댑터가 숨겨야 하는 차이(이름, 단위, 예외 체계, 동기/비동기, 오류 코드)를 목록화하고, 변환 책임의 경계를 정할 수 있다.
- **시나리오**
  - 도메인: 중소 온라인 쇼핑몰의 결제 연동
  - 초기 요구: 백엔드 개발자 예린이 PG사 A의 SDK(`charge(amount_krw: int, card_token)` → dict 반환)로 결제를 붙인다. 주문 서비스 곳곳이 이 SDK를 직접 호출한다.
  - 변경 요구 1: 수수료 협상 결과 PG사 B를 추가한다. B는 `create_payment(PaymentRequest(amount=Decimal, currency="KRW"))`이며 실패 시 예외 대신 `status_code`를 돌려준다.
  - 변경 요구 2: 해외 간편결제 C가 들어온다. 금액 단위가 센트이고 결과를 콜백으로 준다.
  - 고통 지점: 주문 서비스 안에 PG별 분기·단위 변환·오류 해석이 퍼진다. 환불 로직에도 같은 분기가 복제된다. PG SDK는 외부 코드라 수정 불가.
- **실현하는 OOP 원칙**: DIP — 주문 서비스는 자체 정의한 `PaymentGateway` 포트에만 의존(헥사고날의 포트/어댑터 관점 간단 언급). SRP — 외부 체계의 번역 책임을 어댑터 한 곳에 격리.
- **파이썬다운 변형 주제**: `typing.Protocol` target(어댑터가 target을 상속할 필요 없음), `__getattr__`로 나머지 메서드 위임(편리하지만 인터페이스를 흐리게 하는 위험), 함수 하나짜리 인터페이스는 함수 어댑터(`lambda`/`functools.partial`)로 충분, 예외 변환(`raise ... from`).
- **관련 패턴**: 퍼사드(08, 변환 vs 단순화), 데코레이터(06, 인터페이스를 바꾸지 않음), 프록시(09, 같은 인터페이스), 브리지(범위 밖 — 사전 설계 vs 사후 통합으로 한 줄 언급).
- **연습문제 아이디어 3개**
  1. (개념) 클래스 어댑터(`class BAdapter(PaymentGateway, PgBClient)`)가 파이썬에서 가능하지만 권하지 않는 이유를 MRO와 인터페이스 오염 관점에서 설명하기.
  2. (리팩터링) 레거시 온도 센서 라이브러리(화씨, `read_f()`)와 신형(섭씨, `get_celsius()`)을 `if isinstance` 로 분기하는 코드(15줄)를 어댑터로 바꾸기.
  3. (판단) 외부 SDK가 우리 target과 메서드 이름만 다르고 의미가 완전히 같다면 클래스 어댑터, `__getattr__` 위임, 별도 함수 중 무엇을 택할지 판단하기.

## 06 데코레이터

- **번호/슬러그/패턴명/분류**: 06 / decorator / 데코레이터 (Decorator) / 구조
- **학습목표 3개**
  1. 같은 인터페이스를 유지하며 책임을 동적으로 덧붙이는 데코레이터를 구현하고, 서브클래스 폭발(조합 수만큼 클래스)을 피하는 원리를 설명할 수 있다.
  2. 데코레이터 체인의 순서가 의미를 바꾼다는 점(압축→암호화 vs 암호화→압축)을 분석할 수 있다.
  3. GoF 데코레이터 패턴과 파이썬 `@decorator` 문법의 관계(겹치는 부분과 다른 부분)를 정확히 구분할 수 있다.
- **시나리오**
  - 도메인: 스마트 농장 IoT 센서 게이트웨이의 텔레메트리 전송
  - 초기 요구: 임베디드 개발자 준호가 토양 수분 센서 값을 MQTT 브로커로 보내는 `MqttChannel.send(payload: bytes)`를 만든다.
  - 변경 요구 1: LTE 데이터 요금 때문에 압축이 필요하다. 일부 농장은 보안 감사 때문에 암호화를 요구한다.
  - 변경 요구 2: 배터리 절약을 위해 10건씩 모아 보내는 배치, 장애 진단을 위한 전송 로그가 추가된다. 농장마다 조합이 다르고 현장에서 설정 파일로 바꾸고 싶어 한다.
  - 고통 지점: `CompressedEncryptedBatchedMqttChannel` 같은 상속 조합 클래스가 2^n개로 늘어나거나, `send()` 안이 플래그 `if`로 뒤덮인다. 순서 의존성(압축은 암호화 전에 해야 효과)이 코드에 드러나지 않는다.
- **실현하는 OOP 원칙**: 상속보다 합성, OCP(새 기능은 새 래퍼), SRP(래퍼 하나에 책임 하나).
- **파이썬다운 변형 주제**: 함수 데코레이터와 `functools.wraps`로 동일 의도 구현(전송 함수를 감싸기), 설정 리스트로부터 `functools.reduce`로 체인 조립, 인터페이스 메서드가 많을 때 `__getattr__` 투명 위임과 그 함정(`isinstance`, 특수 메서드는 `__getattr__`을 타지 않음).

  1. 구조가 비슷한 패턴 쌍(전략/상태, 데코레이터/프록시/어댑터, 팩토리 메서드/추상 팩토리/빌더, 퍼사드/어댑터, 전략/템플릿 메서드)을 의도 기준으로 구별할 수 있다.
  2. 하나의 시스템에서 여러 패턴이 맞물리는 방식을 설계하고, 각 패턴이 해결하는 "변경 축"을 짚을 수 있다.
  3. 파이썬이 각 패턴을 얼마나 흡수하는지 정리하고, 패턴 과잉 적용을 판단하는 체크리스트를 쓸 수 있다.
- **시나리오**
  - 도메인: 중견 물류 기업의 로봇 창고 관리 시스템(WMS)
  - 초기 요구: 입고된 상품을 선반에 배치하고 주문이 들어오면 피킹 로봇에게 작업을 지시하는 단순한 프로토타입.
  - 변경 요구 1: 로봇 제조사가 둘(서로 다른 SDK, 어댑터), 피킹 경로 최적화 알고리즘 교체(전략), 로봇 상태(대기/이동/충전/고장, 상태), 작업 지시의 큐잉·취소(커맨드), 대시보드 실시간 갱신(옵저버).
  - 변경 요구 2: 창고 구역 → 랙 → 선반 → 칸의 계층 재고 집계(컴포지트 + 반복자), 운영자용 단순 API(퍼사드), 시뮬레이션 환경과 실제 환경 전환(추상 팩토리).
  - 고통 지점: 패턴을 모두 넣으면 오히려 복잡해진다 — "어디까지 넣을 것인가"를 판단하는 것이 이 장의 핵심 고통. 최종 코드는 6~7개 패턴만 쓰고, 넣지 않은 패턴과 그 이유를 명시한다.
- **실현하는 OOP 원칙**: 원칙 전체의 종합 — 각 패턴이 어떤 원칙을 실현했는지 표로 되짚고, 원칙 간 충돌(싱글턴 vs DIP, 템플릿 메서드 vs 합성 우선)을 정리.
- **파이썬다운 변형 주제**: "언어 기능이 패턴을 흡수하는 정도" 총정리 표(완전 흡수: 반복자 / 대부분 흡수: 전략·커맨드 / 대체 수단 있음: 싱글턴(모듈)·퍼사드(모듈)·어댑터·프록시(`__getattr__`) / 여전히 클래스가 필요: 상태·컴포지트·빌더(교차 검증)), `functools.singledispatch`를 이용한 연산 추가 기법 재조명.
- **관련 패턴**: 15개 전체.
- **섹션 구성안** (`goals` 필수, 나머지 id 영문 자유)
  1. `goals` 학습 목표
  2. `look-alikes` 닮은 패턴 구별하기: 쌍별 비교표 + "누가 무엇을 결정하는가" 판별 질문 (짧은 비교 코드 `01_lookalikes.py`: 같은 구조의 전략/상태, 데코레이터/프록시)
  3. `case-study` 사례 연구: 로봇 창고 — 상황(코드 없음) → 순진한 프로토타입 `02_naive_wms.py` → 패턴 조합 설계 SVG(어느 클래스가 어느 패턴의 어느 역할인지 주석) → `03_wms.py` → 실행 결과
  4. `combinations` 자주 쓰이는 조합: 컴포지트+반복자, 커맨드+컴포지트(매크로), 옵저버+커맨드, 추상 팩토리+퍼사드, 전략+팩토리(등록부)
  5. `python-absorption` 파이썬이 흡수한 패턴들: 총정리 표
  6. `anti-patterns` 패턴 과잉 체크리스트: "변경이 실제로 일어났는가", "구현이 하나뿐인 인터페이스", "추상화 비용 > 변경 비용"
  7. `exercises` 연습문제
- **연습문제 아이디어 3개**
  1. (개념) 제시된 클래스 다이어그램 4개(구조 동일, 이름·설명만 다름)를 보고 각각 전략/상태/데코레이터/프록시 중 무엇인지 의도 근거로 판별하기.
  2. (리팩터링) 400줄 대신 40줄로 압축한 "스마트 주차장" 순진한 코드에서 변경 축 3개를 찾아 각각에 맞는 패턴을 적용하기(해설 코드 제공).
  3. (판단) 사례 연구에서 쓰지 않은 패턴(싱글턴, 템플릿 메서드, 빌더) 각각을 넣자는 동료 제안에 찬반 의견서를 쓰기 — 변경 축 존재 여부로 판단.
